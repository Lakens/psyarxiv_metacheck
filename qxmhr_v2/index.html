Power analyses need to contain the following information to be interpretable: the type of power analysis, the statistical test, the software used, sample size, critical alpha criterion, power level, effect size, and an effect size metric. How Power Analysis Check works

This module uses regular expressions to identify sentences that contain a statistical power analysis. If specified by the user, it also uses a large language model (LLM) to extract information reported in power analyses, including the statistical test, sample size, alpha level, desired level of power, and magnitude and type of effect size.

The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. Without the use of an LLM, the module uses regular expressions to classify the power analysis as a-priori, sensitivity or post-hoc. The Statcheck module runs Statcheck. Statcheck searches for regular expressions that match a predefined pattern, and identifies APA reported statistical tests. More information on the package can be found at https://github.com/cran/statcheck. How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

A Handle link (hdl.handle.net/...) that leads to a repository read here is checked as a link to that repository ([handle_links()]).

Listing a repository’s files never requires an API key, but some hosts answer faster or more completely with one: OSF allows 100 requests/hour unauthenticated versus 10,000/day with a token (see [osf_pat()]), and Dryad enforces a strict per-IP daily quota on repeated listing (see cache below). Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Since this module only lists files and never downloads their contents itself, that limitation applies to data_check and code_check (which do download content), not here – see their own documentation.

When a linked OSF page is a registration, its registered_from project (the one it was registered from, which the manuscript itself may never link directly) is also checked: if that project is public its files are listed under its own URL, and if it is closed or otherwise inaccessible the report flags it explicitly, since some registrations only describe their content rather than mirroring it.

Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). On a round of labelled links the rules had not been written from, the three groups were right for 98% of links in the main text (93 of 95) and 90% in reference lists (74 of 82); the labels were made by Claude agents from each link’s evidence, and disputed ones checked against the deposits. Telling this paper’s own deposit from the authors’ earlier one is less certain.

Only the deposits that are this paper’s own are checked. A deposit linked in the text that holds other people’s work (others_data, others_code) or the authors’ earlier work (own_earlier_data, own_earlier_code) is listed in the report, with the reason, but its files are left out of table and kept in table_not_checked: they count toward nothing here (files that do not belong in a repository, naming, READMEs, studies, the traffic light), and code_check, data_check and reproducibility_check, which read table, do not check them either. reproducibility_check still puts the files of theirs that the paper’s code names in the folder the code runs in, as a re-analysis needs the data it re-analyses. How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability).

Provenance, kept so that a TRACE Research Object (TRO) declaration of the run can be written later from a stored result (metacheck #404; the helpers are in R/provenance.R). Only when code was run (execute = TRUE): * run_results$started_at, run_results$ended_at: when each run of a script started and ended (ISO 8601, UTC, milliseconds); NA for a script that was not started. A script run again in a later pass has the times of its last run. A TRO uses them for each trov:TransparentResearchPerformance. * run_results$exit_status: the exit status of the process that ran the script (0 = ended normally); NA when the process did not report one (a time limit, or Docker failing to start the container). * artifacts: one row per file, with stage (deposit: as downloaded from the repository, hashed from the downloaded file; before_run: the run folder just before the first script ran, after metacheck’s own changes, such as rewritten paths and unpacked archives; after_run: only the files the scripts made (status new), changed (changed) or removed (removed), as an unchanged file is the one listed before the run), path (relative to the run folder, as valid UTF-8, a byte of another encoding written as <xx>), size (bytes), sha256, mime_type (by extension, NA when unknown), source (the file’s address in the repository, for deposit). The package libraries metacheck installs in the run folder are left out, as are metacheck’s own files there (a script’s runner, and the statistical output it writes in statistical_output/). Files metacheck itself copied or made between passes (see modifications, output_copied, file_placed) show in after_run too. A TRO uses the rows as trov:ResearchArtifacts and each stage as a trov:ArtifactArrangement. * modifications$sha256_before, modifications$sha256_after: the hash of the changed script as downloaded and as it ran; NA when the script is not at the same path in both (a script made from an R Markdown file). * environment: the system that ran the code (trov:TransparentResearchSystem in a TRO): metacheck_version, started_at, ended_at, host (R version, platform, operating system), sandbox, network_isolated (TRUE only when every Docker run had --network none; the process sandbox does not stop the network), internet, timeout_per_script, total_timeout, python_local (the Python run outside Docker and its version), and docker: runs (for each kind of run, r_run, r_install, python_run, python_install, the image and the docker run arguments, such as --network none, --read-only, --cap-drop ALL, no-new-privileges, the process limit and the memory and processor limits) and images (for each image, its ID and digests from docker image inspect, its creation time and the R and Python versions its environment declares).

run_results$checked says what the run of each script shows about the code, in five groups, so that a script that does not reproduce is kept apart from one the check could not test: ran (it ran to the end); code_error (it did not reproduce: it stopped with an error of the code or the deposit, could not be read, or needs a file the deposit does not hold); dependency (a package or program was not available: a package that could not be installed or was not loaded, a program outside R and Python, a system library, or R crashing in a package’s compiled code); time (it did not finish within the time limit for one script, or was not started because the time for all scripts had run out); and not_checkable (it could not be checked automatically: it needs a person, the internet, a key or another setting of the authors’ computer, one platform such as Google Colab, Windows or OpenSAFELY, more memory than the run allows, a file that was not downloaded, a screen, or a program that runs it, or it is a file of a package of the code that Python runs only as a module of that package). It is NA for files run inside another script, files that are not an analysis, files not read, and a Docker failure. summary_table counts each group (repro_ran_n, repro_code_error_n, repro_dependency_n, repro_time_n, repro_not_checkable_n), and the report’s first sentence gives them. The traffic light reflects the static readiness signals by default; a script in code_error that stopped with an error makes it red, as a script that crashes on its own analysis is a genuine reproduction failure, and a script in one of the other three groups keeps it from being green. Calls that need a screen, which the run does not have (dev.print(), dev.copy2pdf(), dev.copy2eps(), savePlot(), windows(), win.graph(), x11(), quartz(), View()), are replaced before the run by calls that need none, which modifications records as screen_call_replaced. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Biomedical literature projects commonly begin in PubMed but require data from several additional National Institutes of Health and National Library of Medicine services. These services differ in their interfaces, response formats, batching rules, and data structures. The puremoe package provides a PMID-centered R interface for searching PubMed and retrieving article metadata, iCite metrics and citation links, PubTator3 annotations and relations, and open-access PubMed Central full text. It keeps remote retrieval explicit and provides source-specific local workflows for MeSH keyness, citation snowballing and network construction, and sentence-level context for biomedical entities and relations. We describe the package's design, compare its scope with adjacent R clients, and demonstrate the workflow with a dated corpus on buprenorphine and opioid use disorder. puremoe is intended for moderately sized literature projects that require a structured NIH/NLM-centered corpus without maintaining separate API clients or a local literature index.

1. Introduction

PubMed is the principal public gateway to the biomedical journal literature, but searching it is only one part of many literature-analysis workflows (Lu, 2011). PubMed records provide bibliographic metadata and Medical Subject Headings (MeSH), the controlled vocabulary used to index MEDLINE (Lipscomb, 2000). Complementary NIH and NLM services add other forms of evidence: iCite supplies article-level citation measures and citation links (Hutchins et al., 2016), PubTator3 identifies biomedical entities and relations in text (Wei et al., 2024), and PubMed Central (PMC) distributes open-access full text. PMIDs connect these resources conceptually, yet the resources do not share a single programming interface.

The resulting integration work is substantial even when the scientific question is modest. Each service has distinct request conventions, batch sizes, rate limits, response formats, and data models.

3. Package design

Three choices organize the package: PMIDs provide the common key, remote retrieval is explicit, and one compact dispatcher exposes endpoint-specific operations. Retrieved objects then enter source-specific local workflows rather than a general analysis framework.

3.1 PMIDs as the common key

PMIDs are the organizing key rather than an incidental field. Users may begin with search_pubmed() or supply identifiers collected elsewhere. The same character vector is then reusable across PubMed, iCite, and PubTator3. PMC is the one qualified case: PMIDs are first resolved to open-access XML locations. This organization minimizes identifier reconciliation and makes joins across returned tables explicit. 3.2 Retrieval and local workflows

The public retrieval layer consists primarily of search_pubmed() and get_records(). The former resolves a PubMed query to PMIDs; the latter dispatches a PMID vector or endpoint-specific identifiers to a selected source. Endpointspecific batching, requests, and parsing remain behind this shared surface. The returned tables and lists then enter local workflows designed for their source structures, without making additional API requests (Timm, 2026).

Each local workflow follows the structure of its source. mesh_keyness() uses retrieved PubMed records, citation_network() uses an iCite result already in memory, and the PubTator3 context functions use a previously returned entity/relation object. These functions accept retrieved data and make no further service requests. They return tables that users can save, filter, join, or pass to other R tools. Users can therefore revise a threshold, network, or display without sending new requests to an upstream service.

3.3 Endpoint schemas

The supported endpoints differ in both their accepted inputs and returned objects.

Table 2 is generated from endpoint_info() rather than maintained as a separate handwritten schema, so it describes the installed package version. As Table 2 shows, the endpoint argument keeps the public retrieval surface small while allowing the implementation to use service-specific request and parsing strategies. endpoint_info() makes those differences inspectable: for each endpoint it reports the upstream source, accepted input, returned object, relevant parameters, rate-limit guidance, and endpoint-specific notes. This metadata is part of the interface rather than a substitute for it; returned objects use stable package-level column names even though the remote representations differ.

4. Worked example: Buprenorphine and opioid use disorder

The example corpus contains PubMed records explicitly centered on buprenorphine and opioid use disorder (OUD). Requiring both concepts in article titles supplies a transparent precision rule and keeps the live workflow manageable. Buprenorphine is well established in maintenance treatment, and comparisons with methadone and other treatment strategies provide a literature with chemical, disease, intervention, and outcome concepts (Mattick et al., 2014). The example follows one corpus through a connected sequence: PubMed defines it, MeSH characterizes it, iCite tests what its title wording leaves outside, PubTator3 makes predicted relations inspectable in text, and PMC supplies selected full text for deeper reading. The query does not define a systematic-review search: in particular, its contemporary title wording underrepresents older literature described with terms such as opioid dependence.

4.1 Corpus definition and article metadata

The workflow first defines a transparent seed set in a reusable form. It begins with the literal PubMed query; search_pubmed() returns the PMID vector that serves as the input to every subsequent enrichment.

query <-'buprenorphine[Title] AND "opioid use disorder"[Title]' pmids <-puremoe::search_pubmed(query)

The query returned 784 identifiers on 2026-09-11. Recording both the literal query and date is necessary because PubMed is a changing index. The example intentionally favors a transparent selection rule over maximal recall; later citation expansion provides an empirical view of what this narrow wording leaves outside the seed set.

The seed PMIDs are passed to the shared retrieval function with the PubMed metadata endpoint. The parallelism and delay are explicit retrieval parameters, not global package state.

Table 3 shows five returned records and the principal article-level fields used later in the workflow. abstracts <-puremoe::get_records( pmids, endpoint = "pubmed_abstracts", cores = 3L, sleep = 1.05 ) In Table 3, each returned article occupies one row, while nested annotations such as MeSH descriptors are retained in list-columns rather than flattened into duplicated article rows. This representation preserves an article-level unit for joins and is also the input subsequently consumed by mesh_keyness().

The same seeds can acquire complementary evidence without identifier reconciliation. Changing only endpoint enriches them with citation and biomedical text-mining data. Keeping both calls together emphasizes the common retrieval pattern and the reuse of one identifier vector.

icites <-puremoe::get_records( pmids, endpoint = "icites", cores = 3L, sleep = 0.25 ) pubtator <-puremoe::get_records( pmids, endpoint = "pubtator", cores = 3L, sleep = 0.34 )

The iCite result retains one row per seed returned by the upstream service, with metrics and citation links in article-level fields and list-columns; it becomes the input to both expansion and within-corpus network construction. In the reported snapshot, PubMed returned records for 779 and iCite for 778 of the 784 requested PMIDs; corpus percentages below use the returned PubMed records. The absent identifiers are recorded in the retrieval audit supplied with the article; get_records() binds the records supplied by the endpoint rather than manufacturing placeholder rows. PubTator3 instead returns BioC JSON in which passages contain nested entity annotations and a separate document-level list contains typed relation assertions. get_records() parses that structure into two PMID-linked tables: one row per entity mention and one row per predicted relation. Entity rows preserve labels, identifiers, offsets, and source passages, while relation rows identify their endpoints through mention indices. Sentence context is added locally later in the workflow.

4.2 MeSH descriptors and corpus keyness

MeSH characterizes the seeds in controlled-vocabulary terms that extend beyond the words used in their titles. The workflow first inspects the vocabulary attached to individual records and then compares its corpus prevalence with a PubMed-wide reference. puremoe supplies the vocabulary, hierarchy, and frequency resources needed for both steps as local R objects.

puremoe exposes the MeSH vocabulary and its tree placements as two tabular resources. The first supports term-to-descriptor lookup; the second preserves the potentially multiple hierarchical locations of each descriptor. Tables 4 and 5 show these two representations for the concepts defining the example. mesh_thesaurus <-puremoe::data_mesh_thesaurus() mesh_trees <-puremoe::data_mesh_trees() Table 4 connects preferred descriptors to entry terms and supplementary concepts. In this example, Dependence, Opioid appears as an entry term for Opioid-Related Disorders, making a terminological bridge that the literal title query does not provide. Table 5 represents hierarchical placement separately: buprenorphine occupies several chemical branches, while opioid-related disorders appears under both disease and psychiatry/psychology branches. A single descriptor-to-parent column would lose that multiplicity. Keeping both resources as ordinary tables permits direct lookup, joining, and aggregation with other R tools. mesh_keyness() compares the proportion of corpus articles indexed with each descriptor against its prevalence across PubMed. By default, it uses the package's bundled data_mesh_frequencies snapshot, making the comparison a local operation. In the package version used for this article, that baseline was constructed in April 2026 from 39,703,112 distinct PMIDs in a local PubMed mirror; descriptor metadata came from the contemporaneous NLM MeSH thesaurus. Users may supply another frequency table when appropriate.

The baseline distinguishes descriptors characteristic of the corpus from broad headings that are frequent throughout PubMed, while min_count excludes very rare corpus descriptors from the ranking.

keyness <-puremoe::mesh_keyness( abstracts, measure = "log_odds", min_count = 5L )

The most frequent MeSH descriptors in this archived corpus were Humans (626), Opioid-Related Disorders (623), Buprenorphine (589), Opiate Substitution Treatment (434), Female (322), and Adult ( 302). Frequency alone therefore mixes descriptors central to the topic with broad indexing categories.

4.3 Citation-based corpus exploration

Citation data expose connected literature omitted by the deliberately narrow title wording and show how its addition changes the corpus. The iCite result already in memory supports two local views: an auditable expansion beyond the seeds and a graph of citations within them.

Following references and citing articles is a well-established complement to database searching, especially when terminology changes or evidence crosses indexing boundaries (Greenhalgh & Peacock, 2005). Here, candidates must have at least two links to the seed neighborhood, and the total returned set is capped at 2,000 records.

snowball <-puremoe::citation_snowball( icites, direction = "both", min_links = 2L, max_nodes = 2000L )

The configured threshold produced 778 seeds and 1222 candidates, filling the 2,000-record cap. The cap is a computational and screening decision, not a claim that the neighborhood is exhausted. Separate cited and citing counts expose why each candidate was admitted and allow alternative thresholds without another iCite request.

Candidate PMIDs can be sent back through the same PubMed metadata endpoint. Table 7 joins those records to their admission counts and lists the strongest links to the seed neighborhood. The ordinary joins, sorting, and display code are hidden because they are not additional puremoe operations. How citation expansion changes the MeSH profile Table 7 exposes each candidate's admission counts. Several highly connected records are trials, reviews, and guidelines that predate most seeds; titles using opioid dependence appear prominently. Citation expansion thus recovers historically connected work that a literal title condition misses. Figure 2 complements the ranked candidates by comparing MeSH prevalence in the seeds and the citation-discovered set: positive values identify descriptors more common among candidates, while negative values identify descriptors concentrated in the seeds. Neither link rank nor vocabulary shift establishes relevance on its own, but both provide inspectable signals for subsequent screening.

The same iCite object can instead be restricted to links within the seed corpus. citation_network() returns conventional node and edge tables; one additional line converts them to an igraph object for standard graph summaries.

citation_net <-puremoe::citation_network(icites) citation_graph <-graph_from_data_frame( citation_net$edges, directed = TRUE, vertices = citation_net$nodes )

The within-corpus graph contains 778 nodes and 1907 directed edges. The presence of 107 isolates and 111 weak components is itself informative: a topically coherent query need not produce a single connected citation community. It also cautions against interpreting this graph as complete scholarly connectivity, because it contains only iCite links among the retained PubMed records. Returning node and edge tables is more useful than printing an unlabeled network; users can pass them to igraph (Csárdi & Nepusz, 2006) and select layouts, filters, or network statistics appropriate to the research question.

4.4 PubTator3 annotations in sentence context

Citation links test the boundary of the seed corpus; the PubTator3 workflow returns attention to concepts and predicted relations inside the retrieved texts. PubTator3 performs biomedical entity and relation extraction and returns its predictions in BioC structures (Wei et al., 2024). get_records() flattens those structures into linked entity mention and relation tables. pubtator_context() then performs a lightweight local NLP operation that attaches sentence context, after which pubtator_cooccurrence() and pubtator_network() construct corpus-level summaries. The package does not train or run a second biomedical extraction model; its contribution here is parsing, alignment, aggregation, and retention of the evidence connecting each summary back to the source PMID and sentence. pubtator_context() takes the entity and relation tables returned by get_records(endpoint = "pubtator"). The BioC response contains passage text and document-relative annotation offsets, so the material needed to reconstruct context is present, but sentences are not supplied as an analytical table and are not attached to relation rows. The function groups passages by PMID and title/abstract location, segments each passage into sentences, and records the resulting sentence spans. It aligns each entity's document offset with a sentence span and adds a sentence identifier plus sentence-relative entity coordinates. It then resolves each relation's two mention indices against the entity table, adding endpoint text, identifiers, passage locations, and sentence identifiers. From those fields it derives same_sentence and sentence_distance. The returned entities, relations, and sentences tables therefore make textual proximity directly queryable without another service request or a user-written BioC and offset-alignment pipeline.

Once that context exists, pubtator_cooccurrence() constructs a local summary from the entity table; it does not use or expand PubTator3's predicted relation rows. It counts mention pairs within a chosen sentence window. Aggregating by = "type" describes broad combinations such as chemical-disease mentions, whereas by = "entity" retains the identifiers and mention labels supplied to the function. The latter makes normalization an explicit composition step: the article joins PubTator3 identifiers to the MeSH descriptor and supplementary concept records loaded for Table 4, while preserving the forms attested in the source text. Identifiers from other vocabularies remain unchanged.

5. Implementation and performance

The implementation uses endpoint-specific adapters, source-specific local workflows, and conventional R data structures.

5.1 Endpoint adapters and execution

get_records() is a dispatcher over endpoint adapters rather than a common HTTP request with different URLs. In the package version used here, PubMed and iCite requests are divided into batches of at most 199 identifiers, PubTator3 requests into 99, and PMC full-text requests into five documents. Each adapter constructs the request expected by its service, parses the response, and returns a stable package-level representation. PubMed XML becomes an article table with nested fields; iCite JSON becomes an article table with citation-link list-columns; PubTator3 BioC data become related entity and relation tables; and PMC's JATS-formatted XML from the public cloud distribution becomes section-level text (National Library of Medicine, 2026). BioC was created specifically to support portable biomedical text and annotation exchange (Comeau et al., 2013), but its document, passage, annotation, and relation hierarchy still requires an R representation suited to downstream analysis.

Independent batches can be evaluated on a user-selected number of parallel workers. The sleep argument remains exposed because parallel execution does not waive an upstream service's request policy. The delay is applied within each worker, so an approximate aggregate ceiling is cores / sleep requests per second; callers must choose both values together. The PubMed calls above use three workers and a 1.05-second delay to remain below NCBI's documented three-request-per-second limit even without a key. The iCite and PubTator3 calls used three workers with delays of 0.25 and 0.34 seconds, approximate aggregate ceilings of 12 and 9 requests per second; users should check each service's current guidance when choosing these values. NCBI API keys are passed through where applicable, and an iCite-specific timeout can be set by argument or package option. These controls are kept at the retrieval boundary; local functions do not need cores, credentials, sleeps, or retry settings. endpoint_info() records these endpoint differences alongside the input and return schemas so that the compact dispatcher does not conceal service-specific behavior.

5.2 Inspectable local workflows

The local workflows remove recurring source-specific wrangling without attempting to supply a general literature-analysis framework. Their functions take explicit retrieved objects as inputs, return tables rather than hidden state, and preserve enough source detail to trace a summary back to the records that produced it. The three workflow families apply that contract to different source structures.

mesh_keyness() compares corpora at the article level, not by counting repeated labels. It contrasts articlelevel descriptor prevalence with a PubMed-wide frequency baseline. The worked example ranks descriptors with a smoothed, standardized log-odds score. Positive values identify descriptors that are unusually prevalent in the selected corpus. These descriptive scores depend on the corpus and baseline version.

The two citation functions retain different links. citation_snowball() ranks records outside the seeds by their cited and citing links to the seed neighborhood. It then applies the requested direction, threshold, and max_nodes limit. citation_network() keeps only links whose endpoints occur inside the retrieved corpus. Both return the links underlying their summaries. Users can thus inspect admissions, change thresholds, or construct a graph without retrieving iCite data again. Edges follow citation flow: from is the citing PMID and to is the cited PMID. Accordingly, cited_links counts seed-to-reference edges and citing_links counts candidate-to-seed edges; link_count is the selected directional count or their sum. Network nodes are the PMIDs returned by iCite, including isolates, while edges are deduplicated links whose two endpoints both belong to that node set.

pubtator_context() restores textual context to upstream PubTator3 predictions. The sentence and offset alignment described in the worked example supports two outputs: co-occurrence summaries calculated from mapped entities and relation networks that aggregate PubTator3 predictions. The relation networks retain separate article-and sentence-level evidence rows. These rows allow users to review useful annotations and extraction errors before substantive interpretation.

5.3 Scale and interoperable representations

Remote work scales primarily with the number of endpoint-specific batches. Parallel workers can process independent batches, but useful concurrency remains bounded by service request policies, network availability, and the configured delay. Local workflows make no additional requests; their cost instead follows the number of article descriptors, citation edges, entity mentions, or relations in the retrieved object. PMC work is optional and potentially more request-intensive, so users should resolve only the subset selected for full-text analysis. These constraints make puremoe appropriate for moderate, investigator-scale corpora rather than reconstruction of PubMed or a global citation graph.

Most retrieval functions return data.table objects (Barrett et al., 2026) with PMIDs stored as character values. This avoids treating identifiers as quantities and permits ordinary joins, grouping, and export. List-columns preserve genuinely nested information, such as per-article MeSH annotations and iCite links, without duplicating article metadata. PubTator3 and network operations return named lists of tables when several related components are required. No hidden session object connects stages: the returned objects are the interface between retrieval, local workflows, and subsequent analysis.

The package likewise does not impose custom graph or visualization classes. citation_network() returns node and edge tables that can be passed directly to igraph, as shown above, or to another graph package. puremoe prepares the literature data while established R tools supply graphical style and statistical modeling.

Intermediate results therefore remain usable even when the rest of an analysis does not use puremoe.

5.4 Reproducibility record

The submitted article renders from the dated object data/puremoe-example.rds by default. The accompanying scripts/retrieve-data.R script records the literal query and retrieval parameters, repeats every remote request displayed in the article, writes an endpoint return audit, and replaces the snapshot when a fresh live run is required. All transformations, tables, and figures are evaluated from the archived objects during the default build. This separates reproducibility of the reported results from availability and later changes in upstream services without concealing how the records were obtained. The submission also includes data/retrieval-sessionInfo.txt, data/render-sessionInfo.txt, and data/retrieval-audit.csv as plain-text records. The first session record describes the original remote retrieval; the second describes the environment used for the submitted render and local workflows. A live build remains available by setting the PUREMOE_LIVE_RETRIEVAL environment variable to true, but it is expected to produce a later state of the upstream indexes rather than reproduce the dated counts exactly.

6. Limitations

puremoe depends on services that the package does not control. Availability, latency, schemas, rate limits, and indexing schedules may change. A valid live workflow can therefore be interrupted by an upstream outage, and the same query can yield different PMIDs on a later date. The article reports its retrieval date rather than presenting the current counts as fixed.

Saving retrieved objects can make downstream local workflows repeatable, but it does not make a changing external index historically immutable.

iCite links describe a PMID-based citation collection rather than a universal scholarly graph, and the PMC endpoint retrieves open-data XML rather than arbitrary publisher full text. These upstream boundaries also bound the local workflows that puremoe can support.

The local summaries reflect upstream metadata and automated annotations; they do not validate them. MeSH keyness depends on MEDLINE indexing and the packaged frequency baseline. Citation counts favor work with more time and opportunity to accumulate links, and expansion thresholds can exclude weakly connected but relevant articles. Same-sentence co-occurrence is not semantic association, and PubTator3 relation labels may contain entity or relation-extraction errors. Evidence rows support review but do not replace domain validation. The package is intended for moderate, investigator-scale corpora. Parallel batching reduces wall-clock time but does not turn remote APIs into bulk data infrastructure; large or repeated analyses may be better served by local archives or bulk datasets. puremoe is not a PubMed mirror, a general interface to every NCBI database, a systematic-review management system, or a global scholarly graph. The worked query is deliberately precise and pedagogical. Its results demonstrate software behavior and corpus exploration, not an exhaustive search or synthesis of buprenorphine evidence.

7. Discussion

puremoe occupies a middle position between individual API clients and large bibliometric infrastructures. Its defining contribution is a reusable PMID corpus that can move through selected NIH/NLM services and then enter source-specific, inspectable local workflows. This supplies more workflow structure and biomedicaldomain support than a generic request client while avoiding the storage and maintenance requirements of a literature mirror. In the worked example, each service response becomes an ordinary R object with an explicit relationship to the seeds.

The example also shows why combining these sources is analytically useful. MeSH descriptors summarize the seed corpus in a controlled vocabulary and link current language to older entry terms. Citation expansion then recovers highly connected trials, reviews, and guidelines outside the literal title query, including work framed as opioid dependence. The seed-candidate MeSH contrast describes how that expansion changes the corpus rather than merely enlarging it. PubTator3 adds a different view based on concepts in text, while retained sentence evidence exposes both potentially useful relations and obvious reasons for caution. A small PMC subset demonstrates sectioned full text without turning that optional endpoint into a corpus-wide download.

These gains occur at the transitions between services. PubMed annotations feed a comparison against a PubMed-wide baseline; iCite links support both a ranked candidate table and a graph; PubTator3 offsets become sentence context before evidence is aggregated. These local workflows go beyond returning upstream JSON, XML, or BioC, yet remain inspectable rather than forming an opaque end-to-end model.

The intended niche also defines when another package is preferable. rentrez is broader across NCBI; pubmedR offers a direct path from PubMed to bibliometrix; europepmc is the appropriate client when Europe PMC is the organizing index; and openalexR offers wider cross-disciplinary graph breadth. These clients can also be combined with puremoe, because an existing PMID vector can enter the workflow and returned tables use conventional R representations. The package is most useful when PMIDs are the organizing key and several NIH/NLM services are required in the same investigator-scale analysis.

Finally, live retrieval and reproducibility should not be conflated. Executable code, literal queries, dates, and parameters make the process transparent, but a future execution queries a future state of each service. Separating retrieval from local work provides a practical response: researchers can retain the retrieved tables associated with a reported analysis while freely rerunning local thresholds, networks, and visualizations. The archived article reproduces the reported analysis, whereas a fresh execution tests the current workflow. Empirical studies should also archive their analysis inputs where licensing and data volume permit.

8. Conclusion

puremoe turns a PubMed-derived or user-supplied PMID set into reusable R objects that can be enriched across selected NIH/NLM services and used in local workflows without hidden retrieval. The worked example showed the practical payoff: controlled vocabulary characterized the seeds, citation links exposed historically connected literature, PubTator3 predictions became traceable to sentence evidence, and a selected subset resolved to section-level PMC text.

The package is best suited to moderate, investigator-scale projects in which PMIDs are the organizing key and two or more of these services are needed in one R workflow. A single-service client is simpler when only one source is required; a broader scholarly graph or bulk archive is preferable when coverage extends beyond the NIH/NLM ecosystem or approaches database scale.
