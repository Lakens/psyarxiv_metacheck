To fix Exact P-Values

What we found

We found 2 imprecise p values out of 15 detected p values.

Show details

Reporting p values imprecisely (e.g., p < .05) reduces transparency, reproducibility, and re-use (e.g., in p value meta-analyses). Best practice is to report exact p-values with three decimal places (e.g., p = .032) unless p values are smaller than 0.001, in which case you can use p < .001.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (e.g., “decreased at the p < .05 significance threshold”).

The APA manual states: Report exact p values (e.g., p = .031) to two or three decimal places. However, report p values less than .001 as p < .001. However, 2 decimals is too imprecise for many use-cases (e.g., a p value meta-analysis), so report p values with three digits.

To check Non-Significant P Value Check

What we found

We found 1 non-significant p value that should be checked for appropriate interpretation.

Show details

Meta-scientific research has shown nonsignificant p values are commonly misinterpreted. It is incorrect to infer that there is ‘no effect’, ‘no difference’, or that groups are ‘the same’ after p > 0.05.

It is possible that there is a true non-zero effect, but that the study did not detect it. Make sure your inference acknowledges that it is possible that there is a non-zero effect. It is correct to include the effect is ‘not significantly’ different, although this just restates that p > 0.05.

Metacheck does not yet analyze automatically whether sentences which include non-significant p-values are correct, but we recommend manually checking the sentences below for possible misinterpreted non-significant p values.

This module uses regular expressions to identify sentences that contain a statistical power analysis. The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. How StatCheck works

Check consistency of p-values and test statistics

The Statcheck module runs Statcheck. Statcheck searches for regular expressions that match a predefined pattern, and identifies APA reported statistical tests. More information on the package can be found at https://github.com/cran/statcheck. The module only returns Statcheck results for t-tests and F-tests, as these are the only tests which have been validated, see https://osf.io/preprints/psyarxiv/tcxaj_v1/.

Statcheck was developed by Michèle Nuijten and Sascha Epskamp.

Statcheck considers p = 0.000 an error, as you should report p < 0.001. Furthermore, p < 0.03 is an error if the p-value was 0.031, and one should simply report exact p-values (p = 0.031). When the sentence of a test says it is one-sided (“one-tailed”, “one-sided” or “directional”), a p-value that fits a one-sided test counts as consistent (statcheck’s OneTailedTxt setting; #695). When the paper says anywhere that its tests are one-sided, a p-value that fits a one-sided test in either direction counts as consistent too: half the two-sided p, or 1 minus that half for an effect against the predicted direction. Equivalence tests (TOST) are left out, as their p-values do not test the difference. A statistic written with “<” or “>” is read as a bound, and in a sentence about equal variances an F-test’s two-sided p (twice the one-tailed p) counts as consistent. For more information, see StatCheck.

This module only checks statistical results reported in the running text of the manuscript. It cannot (yet) process statistics reported only in tables.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Codebook Check works

This module checks whether the data columns in a repository are documented in a codebook or README. It locates codebook/readme files, extracts the variable definitions they contain, matches those definitions against the data columns extracted by data_check, and reports documentation coverage: how many data columns are documented, and which documented variables are never used.

The Codebook Check module consumes the columns and file classification produced by data_check (and, transitively, repo_check). Files classified as codebook or readme are parsed with parse_codebook(), which reads structured tables (CSV/TSV/Excel with a variable-name column and a label column), embedded labels in haven files (SPSS/Stata/SAS), and plain text from rich-text formats (docx/pdf/rtf/odt). Embedded haven labels from data files are also harvested directly.

Each data column is then matched against the parsed variable definitions with match_column_labels(), using normalised-name matching with experiment-group scoping, haven-label priority, and rule-based label-equivalence merging.

This module retrieves information from repositories.

Telling this paper’s own deposit from the authors’ earlier one is less certain.

Only the deposits that are this paper’s own are checked. How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability).

Provenance, kept so that a TRACE Research Object (TRO) declaration of the run can be written later from a stored result (metacheck #404; the helpers are in R/provenance.R). Only when code was run (execute = TRUE): * run_results$started_at, run_results$ended_at: when each run of a script started and ended (ISO 8601, UTC, milliseconds); NA for a script that was not started. A script run again in a later pass has the times of its last run. A TRO uses them for each trov:TransparentResearchPerformance. * run_results$exit_status: the exit status of the process that ran the script (0 = ended normally); NA when the process did not report one (a time limit, or Docker failing to start the container). * artifacts: one row per file, with stage (deposit: as downloaded from the repository, hashed from the downloaded file; before_run: the run folder just before the first script ran, after metacheck’s own changes, such as rewritten paths and unpacked archives; after_run: only the files the scripts made (status new), changed (changed) or removed (removed), as an unchanged file is the one listed before the run), path (relative to the run folder, as valid UTF-8, a byte of another encoding written as <xx>), size (bytes), sha256, mime_type (by extension, NA when unknown), source (the file’s address in the repository, for deposit). The package libraries metacheck installs in the run folder are left out, as are metacheck’s own files there (a script’s runner, and the statistical output it writes in statistical_output/). Files metacheck itself copied or made between passes (see modifications, output_copied, file_placed) show in after_run too. A TRO uses the rows as trov:ResearchArtifacts and each stage as a trov:ArtifactArrangement. * modifications$sha256_before, modifications$sha256_after: the hash of the changed script as downloaded and as it ran; NA when the script is not at the same path in both (a script made from an R Markdown file). * environment: the system that ran the code (trov:TransparentResearchSystem in a TRO): metacheck_version, started_at, ended_at, host (R version, platform, operating system), sandbox, network_isolated (TRUE only when every Docker run had --network none; the process sandbox does not stop the network), internet, timeout_per_script, total_timeout, python_local (the Python run outside Docker and its version), and docker: runs (for each kind of run, r_run, r_install, python_run, python_install, the image and the docker run arguments, such as --network none, --read-only, --cap-drop ALL, no-new-privileges, the process limit and the memory and processor limits) and images (for each image, its ID and digests from docker image inspect, its creation time and the R and Python versions its environment declares).

run_results$checked says what the run of each script shows about the code, in five groups, so that a script that does not reproduce is kept apart from one the check could not test: ran (it ran to the end); code_error (it did not reproduce: it stopped with an error of the code or the deposit, could not be read, or needs a file the deposit does not hold); dependency (a package or program was not available: a package that could not be installed or was not loaded, a program outside R and Python, a system library, or R crashing in a package’s compiled code); time (it did not finish within the time limit for one script, or was not started because the time for all scripts had run out); and not_checkable (it could not be checked automatically: it needs a person, the internet, a key or another setting of the authors’ computer, one platform such as Google Colab, Windows or OpenSAFELY, more memory than the run allows, a file that was not downloaded, a screen, or a program that runs it, or it is a file of a package of the code that Python runs only as a module of that package). It is NA for files run inside another script, files that are not an analysis, files not read, and a Docker failure. summary_table counts each group (repro_ran_n, repro_code_error_n, repro_dependency_n, repro_time_n, repro_not_checkable_n), and the report’s first sentence gives them. The traffic light reflects the static readiness signals by default; a script in code_error that stopped with an error makes it red, as a script that crashes on its own analysis is a genuine reproduction failure, and a script in one of the other three groups keeps it from being green. Calls that need a screen, which the run does not have (dev.print(), dev.copy2pdf(), dev.copy2eps(), savePlot(), windows(), win.graph(), x11(), quartz(), View()), are replaced before the run by calls that need none, which modifications records as screen_call_replaced. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Perceiving materials like metal, wood or soil is essential for many everyday tasks, yet we still understand little about how materials are represented in the brain. Here we report the most comprehensive mapping of neural representations of materials and their properties to date. In an event-related fMRI design over multiple sessions, six participants viewed every image in the STUFF dataset-which includes 200 different material categories-14 times each, yielding precise estimates of cortical responses. We compared these responses with 36 'core dimensions' of material perception derived from >1.8 million perceptual similarity judgments on the same image set. This revealed 'cortical feature maps' of activity associated with each dimension. Most maps spanned large swaths of cortex, indicating a highly distributed and multiplexed representation. Multidimensional scaling revealed systematic relationships between the maps, with >95% of the variance between maps accounted for by just six axes. Despite this, for 35 of the 36 core dimensions, feature values could be decoded from brain activity patterns, and in pairwise comparisons, material categories could be decoded with 88.9% accuracy. Together our findings reveal a highly distributed multidimensional material representation that supports the read-out of both properties and categories of materials. question for the field is whether materials and their properties are clustered into specific regions of cortex, or whether the representation is instead highly multiplexed, with each region encoding many features of materials simultaneously in a multidimensional embedding.

Here, to answer this question, we sought to create the most comprehensive mapping of the cortical representation of material properties to date, both in terms of the categories and properties of the materials considered. While there are many possible dimensions of materials-indeed practically every visual feature could plausibly be relevant-here we focus on behaviourally relevant dimensions, specifically, dimensions that we recently demonstrated to be particularly important for similarity judgments and therefore a strong basis for organising and categorising materials 23 . Our goal was thus to understand how the most important dimensions of materials are represented across the cortex.

To do this, and to overcome challenges with selecting materials, we used the STUFF dataset 23 , which contains 600 images spanning 200 different nameable material categories-the broadest sampling of material types to date. In our previous study, we crowdsourced over 1.8 million perceptual similarity judgments, from which we empirically derived 36 'core dimensions' that observers used to make their comparisons. The resulting dimensions were intuitively understandable to other observers, and spanned relatively low-level visual characteristics like 'grainy' or 'yellow', up to high-level semantic aspects like the extent to which the material appeared to be a mineral or wood. We found that individual materials were typically represented with a subset of such dimensions, suggesting that the 36 'core dimensions' represent a superset of particularly important material characteristics. This hints that it might be feasible to decode materials and/or material properties from brain activity. Other studies have used similar data-driven analyses to reveal key psychological dimensions and in some cases cortical representation of objects, places and actions 24, 25 . Thus, out of a practically infinite number of possible visual properties, our approach offers a rigorous means to hone in on those that are most relevant for structuring our visual world, derived in a data-driven way from large-scale similarity judgments.

Thus, in some respects, materials are even more fundamental than objects for perception and action: the reason a hammer is useful for knocking in nails is not just because of its shape, but also because of its material properties (being heavy and hard). Yet, while numerous studies have investigated how objects, faces and places are visually perceived and represented in the brain [5] [6] [7] [8] , in comparison far less is known about the representation of materials and their properties 9, 10 . In particular, previous research on cortical representations of materials has primarily focussed on material categorization or characteristics as a whole (e.g., 'things' vs 'stuff') [11] [12] [13] [14] -rather than a fine-grained analysis of how materials are represented-or on highly limited ranges of properties, such as a gloss [15] [16] [17] , translucency 18, 19 and texture [20] [21] [22] . A major open between the representations of different properties? If the representations of materials are highly distributed across cortex ('everything, everywhere'), can we nonetheless decode material dimension values from cortical activity patterns?

We reasoned that answering these questions would allow us to test whether the cortical maps we measured capture the 'lion's share' of material-relevant variance in brain representations. To anticipate, our key findings are: 1) We find dimension-specific maps that for many dimensions are stable both within and between participants. 2) These are not scattered patterns, but broad, map-like representations, often spanning relatively large swaths of cortex. This suggests a highly distributed code. 3) Decoding analyses support this view by revealing that each region contains information about many dimensions, indicating a highly multiplexed, multidimensional representation of material properties. 4) The relationships between the feature maps are largely captured by a small number of axes, which form the basis for this multiplexed representation. 5) Despite this, we are still able to decode almost all individual dimensions with high accuracy. Our findings are thus reminiscent of the high-dimensional latent embeddings spaces found in artificial neural networks, from which many features can be read out. 1.

RESULTS

The representations of core dimensions of materials across the cortex

In previous work, we demonstrated that material appearance is best captured by a combination of 36 dimensions, spanning perceptual (e.g., grainy, blue) as well as conceptual (e.g., mineral, viscous) dimensions 23 . Findings on the neural representation suggested that material perception is multidimensional, and therefore might not be localized, but distributed across brain areas 26 . To test this, we first sought to measure how the 36 'core dimensions' were mapped out across cortex. We ranked all 600 images by their behaviourally defined values for each dimension, and then correlated the resulting value vectors with the activity elicited by each image in every voxel (averaged across participants and sessions).

This revealed systematic patterns of activity related to each material dimension across large swaths of cortex ('cortical feature maps'). Figure 2 shows maps for three example dimensions (see Figure S1 for the maps for all 36 dimensions). For example, images with a high value on Dimension 18 ("mesh") exhibit mesh-like, repetitive structures ( Figure 2a ). As might be expected, such spatial patterns evoked strong responses in early visual cortical areas (e.g., V1-V3 averaged beta value is larger than the mean beta in the rest ROIs for all participants, t(5)=5.74, p<.01) presumably due to their large contrasts and high spatial frequency content. In contrast, Dimension 27 ("sheet") , which is associated with sheet-like, plastic or thin materials, led to significant positive correlation in higher-level visual areas (e.g., V1-V3 averaged beta value is smaller than the mean beta in the rest of the ROIs for all participants, t(5)= -7.91, p<.001), particularly in parietal cortex, with marked negative association across early visual areas. Dimension 30 ("golden/shiny") was associated with golden, shiny or metallic appearances. Images with large values for these material dimensions elicited enhanced activity across early visual areas (e.g., V1-V3 averaged beta value is larger than the mean beta in the rest of the ROIs for all participants, t(5)= 7.88, p<.001), especially V1 and V2.

More broadly, we find similarly consistent activity patterns associated with most of the 36 feature maps (see Figure S1 ). The maps cover large and often overlapping regions of cortex. As a measure of how much of the cortex was involved in representing material properties ('coverage'), we calculated the percentage of cortical voxels that yielded significant beta values in each feature map for all participants (see Figure S2 ). This revealed that up to 55.65% cortex was significantly associated with a material dimension in one participant. The mean coverage across all 36 dimensions was 13.58%. Together, these results suggest a broad, overlapping and therefore multiplexed, multidimensional representation of material properties. Systematic relationships between cortical feature maps

Given the overlap between the cortical features maps, a key question is whether there is some overarching organising principle that relates the different maps to one another. For example, considering the maps in Figure 2a , the activity across all brain voxels for Dimensions 18 and 30 were significantly positively correlated ( Mean r = 0.39, t(5) = 8.14, p < .001 ), but negatively correlated with Dimension 27 ( Mean r = -0.40, t(5) = -6.59, p < .001 ). This was not due to correlations in the ordering of the stimuli associated with these dimensions, which were no more correlated than would be expected by chance (verified by bootstrap analysis with 1000 random draws).

To quantify the relationship between cortical responses associated with each dimension, we calculated the correlations of average whole-brain activity patterns (across sessions and participants) between all cortical feature maps. Note that one potential concern about this analysis is that the small but nonzero collinearity between dimensions could have resulted in structured covariance between beta parameters of different dimensions. To test the impact of this we additionally whitened the data matrix across dimensions (within each voxel). This yielded a highly similar pattern of results (see Figure S3 ); the correlation between the similarity matrices (original vs whitened) was 0.88 (p < .001).

Applying multidimensional scaling (MDS) to the resulting correlation matrix (see Figure S4 , last subplot) revealed a highly systematic organization of the cortical feature maps ( Figure 3 ) with the first six MDS axes accounting for 95% of the variance between maps and more than 70% of the variance accounted for by just the first two axes. In Figure 3 we plot all 36 cortical feature maps arranged according to their embedding in these first two MDS axes. It is notable that the first MDS axis appears to be related to the relative activation vs suppression of early visual areas (primarily in occipital lobe), while the second MDS axis appears primarily related to activation vs suppression of higher cortical areas (especially in temporal, parietal and frontal lobes). This is broadly consistent with previous observations with completely different stimulus sets 27.

In many cases, the relationships between cortical maps make intuitive sense. Even though all material perception dimensions are approximately independent in terms of behavioural similarity judgments, it is perhaps unsurprising that Dimensions 4 (fabric, soft) , 27 (sheet, plastic) and 29 (spongy) evoke somewhat similar brain activity, on left side of axis 1, and in contradistinction to Dimensions 1 (mineral, hard) , 3 (metallic) and 30 (golden) on the right end of the scale. Put another way, while participants can draw on many different and independent aspects of material appearance to subjectively judge similarity, the cortical representations of the images are somewhat structured by relationships between those features-such as various characteristics related to soft and deformable materials vs hard and rigid ones.

The relationships between cortical features maps are not wholly accounted for by basic, low-level image characteristics. As might be expected, MDS axis 1 correlates somewhat with image contrast (r = -0.54, p<.001), but most of the variance is not accounted for by this simple feature, suggesting that higher-level aspects of the interpretation of the images also play a role in driving cortical activity.

Many maps also contained negative ('blue') regions, that is, voxels whose responses decreased as an image's value on that dimension increased. This indicates that high-value images evoked weaker responses than the average image in the set. For example, the 'sheet' map is negative over early visual cortex, suggesting that sheet-like images drive early visual areas less than other STUFF images do. One possible explanation is that dimensions at one end of MDS axis 1 tend to be dominated by close-ups of bounded objects, whereas dimensions at the opposite end are more texture-like and thus contain more local contrast energy, to which early visual cortex is known to be sensitive. Cortical maps in the middle of the MDS space (e.g., bulbous, beige, yellow, blue, red, black) showed weaker positive and negative associations overall. One reason is that these tended to be dimensions for which there was greater variance across individuals, leading to less significant activation in the group mean ( Figure S1 ). Notably, many of them relate to colour aspects of the materials.

Representational capacity along the cortical processing hierarchy

It is interesting to ask to what extent individual brain areas have the capacity to capture and discriminate the material property dimensions we are investigating here. It seems plausible that early visual areas primarily represent low-level stimulus characteristics, which can be summarised with a relatively small number of features, like contrast, orientation, spatial frequency, etc, and therefore cannot distinguish the material dimensions very well. In contrast, later areas likely have a greatly expanded representational space to capture a greater variety of more complex and abstract stimulus characteristics, allowing them to tease the material dimensions apart. Put another way, we might expect the 'representational capacity' of earlier areas to be lesser than for higher areas (with respect to the material dimensions we are investigating here).

To evaluate this representational capacity hypothesis, we therefore also performed an analysis similar to the preceding one for each region of interest (ROI) individually. Specifically, we ran MDS on the average activity patterns (across participants and sessions) of each ROI. Interestingly, we found that early areas tend to organise the material dimensions in simple, low-dimensional ways. For example, V1 essentially organises the material dimensions along an approximately 1D family in the MDS space ( Figure 4a top ), presumably reflecting the fact that to V1 all images differ primarily in terms of only a few simple low-level image features like contrast (as well as orientation and spatial frequency). Indeed, we find that image contrast is a decent predictor of the embedding in the space of V1 responses: the first MDS axis correlates strongly with the average contrast of the top 20 images for each material dimension (r=-0.64, p<.001).

In contrast, for higher regions, like body area ( Figure 4a bottom ), the material dimensions are much more spread out and fill a larger proportion of the MDS space, and contrast cannot explain responses anymore (r=-0.13, p = 0.44). This suggests that higher areas use higher dimensional representations such that the behavioural dimensions are represented more distinctly. A simple way to characterise how much 'representational space' the features occupy is to calculate the mean pairwise distances between the embedding of different dimensions. We did this for each participant and then took the mean ( Figure 4b ). We find significant differences between early visual areas and both ventral and dorsal ROIs in terms of this measure of the separation of the materials dimensions from one another (t(5) = -13.6, p<.001; t(5) = -5.6, p<.01). This already hints that higher areas may enable decoding the dimensions (see Decoding material dimensions and materials from cortical activity patterns ).

As a sanity check, we tested whether relationships between representations in the ROIs reflect functional-anatomical relationships between brain areas. For this, we performed an MDS analysis on the group-averaged 36 × 36 material-dimension similarity matrices across the 15 ROIs (see Figure S4 ), which yields a highly systematic embedding ( Figure 4c ): Early visual areas (red: V1, V2, V3v, V3d), dorsal stream areas (green: V3B/KO, V3A, hMT+/V5) and ventral stream areas (blue: V4, FFA, PPA, LO, Object, Character) approximately clustered, with the whole-brain representation roughly centrally within the space of representations. ROIs within these three clusters (early, dorsal, ventral) had significantly more similar representations of the material dimensions than between clusters, based on mean pairwise distance in the embedding space [t(89)=-5.51, p<.001], replicating well-known functional-anatomical relationships from those between obtained representations.

Decoding material dimensions and materials from cortical activity patterns

Despite correlations between the cortical maps, the distributed activity patterns contained sufficient information to decode the 36 behavioural material dimensions. We trained a Support Vector Regression (SVR) to predict the value of each dimension from activation patterns across all ROIs and from whole-brain voxel patterns, using 200-fold leave-1-material-out cross-validation. We report decoding performance for the participant-averaged data; the same pattern was observed in individual participants (see Figure S5 ).

Figure 5a shows decoding accuracy for each dimension. Correlations between predicted and behaviourally defined dimension values were significant for 35 of the 36 dimensions after FDR correction, with correlations exceeding 0.70 for eight dimensions and exceeding 0.50 for 19 dimensions. Thus, despite substantial overlap between the cortical maps, activity patterns contained information that could be used to recover most behavioural material dimensions.

Decoding performance generally decreased for the later dimensions presumably because they were more sparsely represented (i.e., fewer images had high values). Consistent with this, Figure 5b shows a substantial negative correlation between dimension sparsity and whole-brain decoding performance (r = -0.65, p = 1.66 x10 -5 ). This relationship likely reflects the amount of information available for decoding: dimensions expressed strongly by fewer images provide fewer observations from which their cortical representation can be estimated. A similar pattern was observed in the number of material categories represented among the 200 images with the highest values for each dimension.

Colour-related dimensions were notable exceptions to this general relationship. Several fell below the trend-line relating sparsity to decoding performance, indicating lower decoding accuracy than expected given their sparsity ( Figure 5b ). These dimensions also showed relatively low consistency across repetitions, both within and between participants. This finding is consistent with some previous work reporting limited decoding performance for the color dimensions of object representation 24 . While traditional fMRI studies classify distinct colors [28] [29] [30] [31] [32] , our study utilizes SVR to decode high-value target color materials embedded within a diverse pool of irrelevant materials/colors. Consequently, the lower decoding performance for our color dimensions may reflect the complex, non-chromatic variance that makes isolating specific color features far more challenging.

We next asked whether cortical activity patterns also contained sufficient information to distinguish the 200 material categories. For each category, we first decoded its dimension profile, averaging across the three images belonging to that category. We then computed the cosine similarity between the decoded profile for one category and the corresponding behaviourally derived profiles of each of the other categories in a one-versus-one comparison. Across category pairs, the decoded profiles identified the corresponding material category with 88.9% accuracy, substantially above the 50% chance level (signed permutation test, p < 0.001).

Together, these results show that cortical activity patterns contain information about both the individual behaviorally relevant dimensions that organize material similarity and the material categories defined by their combination. Thus, the distributed cortical representation of materials is sufficiently structured to support readout of both material properties and material identity.

DISCUSSION

Here we conducted the most comprehensive cortical mapping of visual representations of materials and their properties to date. While previous studies have focussed on materials vs non-materials, or limited ranges of material categories or properties 11, 12, 15, 17, 33, 34 , here we sought to characterise how the most behaviourally important characteristics of materials are represented across the cortical surface within a single study. A major roadblock to achieving this so far has been the lack of principled ways to select which material categories and properties to focus on. If we only include some specific material categories, how do we know we are not missing important aspects of the representation? And out of the near-infinite plethora of possible visual properties that might be relevant, how can we identify those that are behaviourally important and evaluate them within the same experimental setting for comparison?

Our solution to the issue of which categories to include was 'greedy'-by covering practically all visually depictable material categories with a name in the English language (excluding food types, which often comprise multiple materials). To do this, we selected 200 material category terms from a list of all English words. Readers who are skeptical this is sufficient are encouraged to attempt identifying materials that (1) have a name, and (2) are not also just objects (e.g., 'banana'), which are not already included in the STUFF dataset.

To address the issue of selecting behaviourally relevant properties , we used a data-driven approach, based on a large dataset of 1.8 million perceptual similarity judgments derived from the STUFF dataset 23 . This previous work had identified 36 'core dimensions' of material appearance that could capture practically all the variance across our human similarity judgments. We do not interpret the number 36 as having any special significance; it was merely a minimal superset of dimensions that spanned the range of characteristics participants tended to focus on when asked to compare triplets of images from the dataset. We can have confidence that the resulting dimensions are semantically meaningful to observers, because participants were highly consistent when asked to provide names for each dimension 23 . Together this suggests that the 600 photographs in the STUFF dataset-plus the 36 'core dimensions' describing those images-indeed capture much of the behaviourally meaningful variance between materials.

With this data in hand, here we densely sampled cortical responses to the images in an event-related design in which six participants saw all 600 photographs fourteen times each, delivering extremely high signal-to-noise cortical activation patterns associated with each material dimension. This revealed broadly distributed, 'map-like' representations of each of the 36 behavioural dimensions that together spanned large swaths of cortex across both ventral and dorsal visual regions, and beyond.

The representations were generally less topographic than maps of basic stimulus characteristics in primary sensory cortex (e.g., retinotopy in V1-V4 35, 36 or tonotopy in primary auditory cortex (A1 37, 38 ). Yet, rather than being highly localised, or scattered chaotically across cortex, many of the material dimensions were represented in smooth, systematic patterns spanning multiple ROIs, suggesting an alternative way of conceptualising cortical representations of behaviourally-relevant features to traditional functional localisation.

We found that there was a substantial redundancy between maps, such that only six degrees of freedom were required to capture >95% of the variance between the 36 maps. Yet, despite this, the representations of different material properties were sufficiently distinct that we could decode them well from whole brain activity patterns. Indeed, a cross-validated decoding model could recover both properties and categories from cortical activity, suggesting that the cortical maps we report here are systematically related to human perceptual judgments of materials and their properties. Taken together, these findings indicate a rich, multidimensional cortical representation of materials and their properties.

A central question in visual neuroscience is how the brain balances the categorical classification of materials (e.g., wood, metal, fabric) with their continuous attributes/properties (e.g., glossiness, roughness, color). Some classes of visual stimuli have tightly localised associated cortical representations (e.g., faces in FFA 6, 39 , places in PPA 40, 41 ). In contrast, here we find that materials are represented broadly across cortex (i.e., there is no tightly circumscribed 'stuff area' 9 ). Yet, we are nonetheless well able to decode material properties from the activity patterns. This suggests properties and attributes might be just as useful as categories as an organising principle for understanding how materials are represented in the brain.

Although this is the most comprehensive mapping of materials to date, there are also some necessary shortcomings of our method, which could be improved on in future studies. For example, we only considered static photographs, whereas some material properties-especially mechanical characteristics, like viscosity or compliance-are especially indicated by motion cues 26, 42, 43 . Assembling a comprehensive dataset of movie clips spanning the same range of materials is challenging, yet doing so would likely enable better decoding of such properties from brain activity, and would likely elicit stronger responses from many cortical areas.

The use of photographs also limits the sensory signals driving the cortical responses to the visual modality, whereas in the real world touch 44 , sound 45, 46 and potentially other modalities also contribute to material perception. Yet it is also clear that vision is sufficient for an extremely rich phenomenology of materials, enabling categorisation 47, 48 , judgments of many characteristics [49] [50] [51] [52] , highly specific similarity judgments 23, 53 and predictions about how a material would be likely to feel to the touch 26, 54, 55 . Indeed, we and others have found that visually presented materials evoke activation in somatosensory areas [54] [55] [56] . It would be extremely interesting to compare cortical responses across senses, or indeed through verbal stimuli, which also evoke similar semantic representations of material characteristics 45, 53.

Another important limitation of using the STUFF dataset and the Sparse Positive Similarity Embedding (SPoSE) algorithm is that the resulting 36 dimensions are ranked by the prevalence of high values across the images. Thus, Dimension 1 (Mineral) has high values across many images in the dataset. This occurred because there are so many names for different types of mineral, so we have many images with mineral characteristics. In contrast only a handful of materials in the dataset were turquoise, which is why it ranks last among the 36 dimensions. This likely reflects the prevalence of turquoise substances in our environment. Yet, a critical consequence of this is that it impacts the signal-to-noise ratio (SNR) of the cortical responses-early dimensions are related to many images, leading to robust estimates of activation patterns and accurate decoding. In contrast, later dimensions are carried by only a few images, leading to less reliable cortical maps, and poorer decoding performance. Thus decoding performance should not be interpreted as a measure of the fundamental quality or extent of the representation of each material characteristic, but rather primarily reflects the number of related images (and hence SNR) in the STUFF image set.

Finally, this study focused primarily on the visual cortex, leaving the potential contributions of higher-level areas like the prefrontal cortex largely unexplored. While we noted intriguing activation patterns within these regions for specific dimensions and individual participants ( Figure S1 ), these observations remain preliminary. Investigating these high-level networks in the future may contribute to understanding the top-down dynamics of material processing-specifically, how cognitive modulations such as expectations 57 , selective attention and aesthetic preference 58 shape the neural mechanisms of material representation.

CONCLUSIONS

We find that the visually-inferred properties of materials are represented in systematically organised overlapping maps spanning large swaths of cortex. Early visual areas (e.g., V1-V3) primarily capture very basic aspects of material appearance, responding especially to local repeating structures like edges and lines. In contrast, higher regions (e.g, LO, FFA) were involved in a wider range of properties, also including semantic and multi-sensory aspects ( Figure S6 ). Despite the multiplexing of information, the representations were sufficiently rich to enable decoding both properties and categories of materials. Together the findings suggest materials are encoded in the brain in a distributed, multidimensional representation that untangles a material's identity from its physical characteristics.

METHODS

Participants

Six participants with normal or corrected-to-normal vision participated in the experiment (three women, aged between 26 and 38 years and screened for MRI safety). One of the participants was the author. All the participants were informed of the purpose and procedures of the study and provided written informed consent before participating . All participants completed 9-14 fMRI sessions over several months (see Design and Procedure ), in which each of the 600 images was presented to each participant 14 times. Each participant completed an additional localizer session (see ROI definition ). The study was approved by the local ethics committee of the Department of Psychology and Sports Sciences of the Justus Liebig University Giessen (LEK-FB06; application number: 2021-0032), and the non-author participants received monetary compensation.

ROI definition

Fourteen regions of interest (ROIs) were defined for each participant. V1, V2, V3v, V3d, V3A and V4 were defined from a standard retinotopic mapping scan. V3B/KO (kinetic occipital region), the human motion complex (hMT+/V5), and the lateral occipital complex (LOC) were defined by separate functional localizers (cf. 34, 54, 59 ). Five additional ROIs, including the fusiform face area (FFA), parahippocampal place area (PPA), extrastriate body area, visual word form area, and object-selective area, were defined by the fLoc localizer 60.

Those ROIs were selected to comprehensively investigate the neural mechanisms underlying material perception. Early retinotopic regions have been shown to encode low-level image statistics (such as contrast, spatial frequency, and color) that already enable decoding of material properties like roughness and texture 11, 12, 14 . Higher-order ventral areas, in contrast, represent perceptual material categories and visuotactile qualities (e.g., roughness, hardness, warmth) rather than raw image statistics [11] [12] [13] [14] 61 . In particular, the parahippocampal gyrus, collateral sulcus, and parahippocampal place area (PPA) have been found to support both material categorization and the estimation of surface properties 9, 13, 14, 62 . The fusiform gyrus and nearby regions (e.g., FFA and Collateral Sulcus, CoS), play a central role in material categorization and in transforming image-based into perceptual representations 11, 14, 21, 33 . Higher-order dorsal areas are critical for processing dynamic material motion and deformations and gloss cues 26, 59.

MRI data acquisition

A 3-Tesla Siemens Prisma scanner with a 64-channel phase-array head coil was used to obtain all MRI images. All of the data collection took place at the Bender Institute of Neuroimaging (BION) at Justus Liebig University Giessen.

Functional whole-brain scans were acquired using an echo-planar imaging (EPI) sequence. For the experimental runs, the acquisition parameters were as follows: 50 axial slices, repetition time (TR) = 1,500 ms, echo time (TE) = 30 ms, voxel size = 2.4 × 2.4 (in-plane) x 2.8 (thickness) mm³, flip angle = 71°, and matrix size = 80 × 80. Slices were acquired in an interleaved order. For the functional localizer runs, a different EPI sequence was used, with the following parameters: 60 axial slices, TR = 2,000 ms, TE = 30 ms, voxel size = 2.5 x 2.5 x 2.5 mm³, flip angle = 80°, matrix size = 96 x 96. Slices were also acquired in an interleaved order.

High-resolution T1-weighted anatomical images were acquired during the localizer session to reconstruct individual participants' cortical surfaces. Acquisition parameters were as follows: 176 sagittal slices, TR = 1,580 ms, TE = 2.3 ms, flip angle = 8°, and isotropic voxel size = 0.9 mm³. To improve anatomical-functional coregistration, gradient-echo (GRE) field maps were acquired during each experimental session to correct for EPI-related geometric distortions. The acquisition parameters were as follows: 40 axial slices, TR = 424 ms, TE1 = 4.92 ms, TE2 = 7.38 ms, voxel size = 3.1 × 3.1 × 3.0 mm³, and flip angle = 60°. Apparatus and Stimuli Stimulus presentation was controlled using MATLAB (MathWorks, Natick, MA, USA) and Psychtoolbox 63 . The stimuli were presented on a 32-inch monitor (BOLDscreen 32, Cambridge Research Systems Ltd.) located in the scanner room, with a refresh rate of 120 Hz. Participants viewed the stimuli through a front-surface mirror mounted on the head coil at a viewing distance of 140 cm. The stimuli subtended a visual angle of 13° × 13°. An eye-tracking camera (ViewPoint EyeTracker, MRC Systems GmbH) was used to record video images of participants' left eyes during recording.

Design and Procedure

An event-related fMRI design was used to investigate brain responses during the visual processing of 600 material images spanning 200 material categories from the STUFF dataset 23 . Each scanning session lasted approximately 1-1.5h, during which participants completed five to nine experimental runs. Each experimental run lasted 420s (280 volumes x 1,500 ms TR), including initial dummy scans to minimize transient magnetization effects. In each run, 120 of the 600 images were presented in randomized order, such that the entire image set was presented once across five runs. Each stimulus was presented for 2 s, followed by a 1-s interstimulus interval (ISI), resulting in a trial duration of 3 s.

Participants performed a binary likability judgment task, indicating whether they liked or disliked the depicted material by pressing one of two response buttons within the 3-s trial window. They showed a low proportion of missed responses (mean like rate = 39.08%, mean dislike rate = 59.26%, mean miss rate = 1.67%). Likeability ratings across the 600 images showed high consistency within participants (mean split-half reliability: r = .87), with relatively lower agreement between participants (mean pairwise corre lation: r = .20).

Ten fixation events (blank trials lasting 3 s each) were randomly interspersed throughout each experimental run. Additionally, five fixation events were presented at the beginning and end of each run to establish the fMRI signal baseline, resulting in a total of 20 fixation events per run. An illustration of the experimental procedure is shown in Figure 1.

Data analysis

We processed the MRI data using the pipeline described in our previous work 34, 54, 59 . Using BrainVoyager QX (version 21.4; Brain Innovation, Maastricht, The Netherlands), we segmented gray and white matter from each participant's anatomical scan and reconstructed, inflated, cut, and unfolded the left and right cortical surfaces. We preprocessed all functional runs with slice scan-time correction, 3D head-motion correction, high-pass filtering, and linear trend removal, and corrected geometric distortions using Anatabacus 64.

To identify neural response patterns associated with the 36 material dimensions, we performed a whole-brain, voxelwise general linear model (GLM) analysis. For each dimension, behaviorally derived embedding values across the 600 image conditions were zero-centered (summing to zero) and used as contrast weights. Applying these contrast vectors to the estimated GLM beta coefficients yielded whole-brain beta estimates for each participant, dimension, and session. This procedure was repeated independently across all 36 dimensions. Then the resulting beta maps were averaged across the 14 sessions within each participant and then averaged across all six participants to generate group-level activation maps. Representative t-maps highlighting significant voxels are shown in Figures 2 and 3, while complete maps for all participants and dimensions are provided in Figure S1. Mean beta values across ROIs and all 36 dimensions are displayed in the accompanying bar plots beneath the maps. Support vector regression (SVR) was used to decode the 36 material dimensions from multivoxel activity patterns. Voxel time series were first shifted by 4.5 s (3 TRs) to account for hemodynamic delay and z-score normalized within each run to remove baseline differences across runs and sessions. For each of the 600 stimulus conditions, activation patterns were obtained by averaging the signal across two consecutive time points (2 TRs = 3 s) within each run, and subsequently averaging these patterns across all 14 sessions. For each participant, separate SVR models were trained to predict the behaviorally derived embedding values of each dimension from multivoxel activation patterns within each ROI as well as across the whole brain for each participant (Figure S5) and the group (Figure 5a). Decoding performance was evaluated using a 200-fold leave-one-material-out cross-validation. The decoding analyses were implemented using The Decoding Toolbox 65.
