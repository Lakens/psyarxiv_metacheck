How Ethics Approval Check works

This module searches for statements of ethics approval, IRB approval, institutional review board approval, and related terms.

Patterns are designed to capture:

When a statement is expected

The module sorts each paper by where its data came from (the internal .data_source(); the signs and how the rule was tested are described in R/data-source.R): - own: the authors collected data from people or animals, for this paper, in an earlier study of their own, or (a protocol) will collect them; - existing_records: records about individual people that the authors obtained for this study, such as hospital records or a cohort; - existing_unclear: existing data about people from a source the module could not identify; - open_resource: an open resource any researcher can use, such as UK Biobank or NHANES; - none: no data about people or animals (a review, simulation, commentary, theory, tutorial, coding of published papers, or figures about groups); - uncertain: the signs were missing or pointed both ways; - no_text: the paper has no text.

A statement is expected for own, existing_records and existing_unclear. A paper without a statement in these classes, or in uncertain, is flagged. The module reads the text, and the results of power, stat_p_exact, stat_check, repo_check, data_check and prereg_check when they ran before it (run it after them); without stat_p_exact, it finds the p-values in the text.

On 199 PsyArXiv and medRxiv preprints labelled after the rule was fixed, the module decided right whether a statement is needed for 86.9% (the earlier live-data search: 83.4%). Its main errors: other people’s studies described in the words of a new study, records and specimens described only as counts, and open resources the paper does not call open.

How Power Analysis Check works

This module uses regular expressions to identify sentences that contain a statistical power analysis. If specified by the user, it also uses a large language model (LLM) to extract information reported in power analyses, including the statistical test, sample size, alpha level, desired level of power, and magnitude and type of effect size.

The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. Without the use of an LLM, the module uses regular expressions to classify the power analysis as a-priori, sensitivity or post-hoc. How StatCheck works

Check consistency of p-values and test statistics

The Statcheck module runs Statcheck. Statcheck searches for regular expressions that match a predefined pattern, and identifies APA reported statistical tests. More information on the package can be found at https://github.com/cran/statcheck. The module only returns Statcheck results for t-tests and F-tests, as these are the only tests which have been validated, see https://osf.io/preprints/psyarxiv/tcxaj_v1/.

Statcheck was developed by Michèle Nuijten and Sascha Epskamp.

Statcheck considers p = 0.000 an error, as you should report p < 0.001. Furthermore, p < 0.03 is an error if the p-value was 0.031, and one should simply report exact p-values (p = 0.031). When the sentence of a test says it is one-sided (“one-tailed”, “one-sided” or “directional”), a p-value that fits a one-sided test counts as consistent (statcheck’s OneTailedTxt setting; #695). When the paper says anywhere that its tests are one-sided, a p-value that fits a one-sided test in either direction counts as consistent too: half the two-sided p, or 1 minus that half for an effect against the predicted direction. Equivalence tests (TOST) are left out, as their p-values do not test the difference. A statistic written with “<” or “>” is read as a bound, and in a sentence about equal variances an F-test’s two-sided p (twice the one-tailed p) counts as consistent. For more information, see StatCheck.

This module only checks statistical results reported in the running text of the manuscript. It cannot (yet) process statistics reported only in tables.

This module was developed by Daniel Lakens and Lisa DeBruine

Read more in the metacheck manual.

Therefore 0% of true instances were missed, and 43% of detections were false positives. See https://osf.io/preprints/psyarxiv/tcxaj_v1/ for more details of the validation.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

This module was developed by Lisa DeBruine and Daniel Lakens

Read more in the metacheck manual.

Version 0.4.4.3 reported 419 p-values as imprecise, 388 of them correctly (93%), and missed 50 (89% found). How Codebook Check works

This module checks whether the data columns in a repository are documented in a codebook or README. It locates codebook/readme files, extracts the variable definitions they contain, matches those definitions against the data columns extracted by data_check, and reports documentation coverage: how many data columns are documented, and which documented variables are never used.

The Codebook Check module consumes the columns and file classification produced by data_check (and, transitively, repo_check). Files classified as codebook or readme are parsed with parse_codebook(), which reads structured tables (CSV/TSV/Excel with a variable-name column and a label column), embedded labels in haven files (SPSS/Stata/SAS), and plain text from rich-text formats (docx/pdf/rtf/odt). Embedded haven labels from data files are also harvested directly.

The module defaults to rules-only when llm_use(FALSE). When llm_use(TRUE), three optional LLM tiers run: parsing unstructured codebook text that the rules could not handle, fuzzy-matching still-unlabelled columns to still-unmatched codebook variables, and merging conflicting label definitions into a single canonical label.

How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

A link to a file-sharing service (Google Drive, Dropbox, OneDrive, Box, WeTransfer, MEGA, iCloud Drive, Baidu Netdisk, SURFdrive; see [file_share_links()]) gets a warning and makes the light yellow: such services are not repositories, as files can be changed or deleted at any time, get no DOI, and the link stops working when the account is closed. The report advises a stable repository such as Zenodo instead. Their files are not read, and summary_table$file_share_n counts the links.

Deposits in archives for sequence and expression data (GEO, the INSDC archives BioProject, SRA, ENA and DDBJ, and ArrayExpress; see [seq_archive_links()]), mostly named by accession number, are read for whose deposit they are. The authors’ own are listed with what they hold ([seq_archive_size()]) and are not downloaded or checked as data and code; summary_table$archive_own_n counts them.

R packages on CRAN ([cran_links()], [cran_info()]) are the paper’s own when a paper author is a package author and the paper presents the package; the paper’s own are listed with their version and not checked (summary_table$cran_own_n). A Handle link (hdl.handle.net/...) that leads to a repository read here is checked as a link to that repository ([handle_links()]).

Listing a repository’s files never requires an API key, but some hosts answer faster or more completely with one: OSF allows 100 requests/hour unauthenticated versus 10,000/day with a token (see [osf_pat()]), and Dryad enforces a strict per-IP daily quota on repeated listing (see cache below). Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Since this module only lists files and never downloads their contents itself, that limitation applies to data_check and code_check (which do download content), not here – see their own documentation.

When a linked OSF page is a registration, its registered_from project (the one it was registered from, which the manuscript itself may never link directly) is also checked: if that project is public its files are listed under its own URL, and if it is closed or otherwise inaccessible the report flags it explicitly, since some registrations only describe their content rather than mirroring it.

Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). On a round of labelled links the rules had not been written from, the three groups were right for 98% of links in the main text (93 of 95) and 90% in reference lists (74 of 82); the labels were made by Claude agents from each link’s evidence, and disputed ones checked against the deposits. Telling this paper’s own deposit from the authors’ earlier one is less certain.

Only the deposits that are this paper’s own are checked. A deposit linked in the text that holds other people’s work (others_data, others_code) or the authors’ earlier work (own_earlier_data, own_earlier_code) is listed in the report, with the reason, but its files are left out of table and kept in table_not_checked: they count toward nothing here (files that do not belong in a repository, naming, READMEs, studies, the traffic light), and code_check, data_check and reproducibility_check, which read table, do not check them either. reproducibility_check still puts the files of theirs that the paper’s code names in the folder the code runs in, as a re-analysis needs the data it re-analyses. When every linked deposit is set aside, the traffic light is “na”. A deposit that is the paper’s own is counted as such when its README, title or description names the paper (its title or DOI).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. Abstract

Computational reproducibility checks are essential to scientific credibility, yet few published papers are ever independently verified, largely because manual checking is labor-intensive and time-consuming. We tested whether an agentic large language model (LLM) could perform computational reproducibility checks at scale. We benchmarked computational reproducibility checks performed by an LLM analyst (Claude Opus running in the Claude Code harness) against results from expert-led reproducibility audits in the social and behavioral sciences and found that LLM accuracy was comparable to that of human experts. Agentic LLMs can now perform highquality reproducibility checks relatively cheaply, quickly, and easily, putting large-scale audits within reach for journals, granting agencies, organizations, and individual researchers.

Introduction

Computational reproducibility is the ability to obtain similar or identical statistical results using a research team's original data. Along with replicability and transparency, reproducibility forms the foundation of scientific credibility by allowing researchers to evaluate whether empirical claims are verifiable. Errors at any point in the research process (such as data curation, coding, or manuscript editing) can lead to reproduction failures, and these failures appear to be surprisingly common (Artner et al., 2021; Chang & Li, 2017; Fišar et al., 2024; Hardwicke et al., 2018; Miske et al., 2026; Naudet et al., 2018; Stodden et al., 2018). Despite this, published papers are very rarely checked or reproduced. This is largely because reproducibility checks are labor-intensive and time-consuming; it can take a skilled analyst many hours to reproduce and check the statistical results of a single paper even when the original analysis code is available.

For instance, one reproducibility audit of recent papers published in a single journal involved 733 volunteers, who collectively reported spending over 6,500 hours (more than three years of full-time work) to reproduce and check the primary empirical results from 459 papers (Fišar et al., 2024). The median reproduction attempt took four hours, and even this figure understates the time a full reproduction requires because it includes attempts that ended early when the data were unavailable.

We investigated whether large-scale computational reproducibility checks could be performed by a large language model (LLM) with access to local files and tools (i.e., an "agentic AI"). In many ways, reproducibility checks are a natural candidate for automation. The steps are well-defined: the analyst needs to locate the paper's data (and code, if it exists), reproduce the statistical analyses reported in the paper, and compare its results to those reported in the paper.

But there are also many parts of this process that require judgment and flexibility. Data are not always posted to a public repository. Descriptions of analyses might be incomplete, data files might be poorly documented, or key variables might not be present and need to be computed.

Code is often unavailable (Krähmer et al., 2026) and even when it can be obtained, it may contain errors, depend on outdated or deprecated third-party libraries, or require proprietary software. All these problems might be difficult for LLMs to solve. Indeed, a recent randomized controlled trial found that analyst teams performing reproducibility checks did not benefit from AI assistance, and that "AI-led" teams (where LLMs operated with minimal oversight) performed much worse than humans did (Brodeur et al., 2026). Similarly, agentic LLMs based on older models (GPT-4o and GPT-4o-mini) have not performed well on reproducibility benchmark tasks (Hu et al., 2025; Siegel et al., 2026).

On the other hand, other recent work has found that when embedded in a custom software workflow, LLMs can reproduce specific statistical results from papers in political science (Xu & Yang, 2026). It is unclear, though, whether a modern agentic LLM outside a custom workflow would be able to perform real-world reproducibility checks for papers in different fields, or how its accuracy compares to that of human experts. We examine this question in two test sets of results from papers in economics, political science, psychology, business, and sociology.

Test Set 1: SCORE project audit

We first compared the performance of an LLM analyst against a recent large-scale reproducibility audit conducted by the SCORE project (Alipourfard et al., 2021) and reported in Miske et al. (2026). This audit, which was conducted by over 100 expert human analysts, tested the reproducibility of 551 statistical claims from 143 papers across the social and behavioral sciences. To build our test set, we started with the set of papers for which the SCORE project recorded that 1) the paper reported an outcome that could be reproduced (sample size, coefficient, test statistic, effect size, or p-value); 2) at least one reproduction was attempted; and 3) data were publicly available. This yielded n = 92 papers; we then eliminated papers that did not use the journal-published version of record (e.g., preprints) because we found that they were frequently updated (and thus the LLM and human analysts might be reproducing different versions of the paper). This yielded 75 papers with 357 claims targeted for reproduction. Three of those papers, totaling 19 claims, were not attemptable by the LLM analyst because the authors' data could not be obtained from any of the standard repositories (OSF, Harvard Dataverse, the AEA replication archive, ICPSR, journal supplements, or author websites). 1 These papers and claims were excluded from analyses; this left 72 papers with a combined total of 338 empirical claims.

Procedure and Results

Our LLM analyst was Claude Opus 4.7 (Anthropic) running in the Claude Code harness configured with file system, code-execution, and web-fetch/search tools. 2 The analyst had access to R, Stata, and Python interpreters, as well as the standard Unix command-line tools. It was also able to install R packages as needed. The LLM analyst was provided with a detailed plan file (available on the project OSF page at https://osf.io/gcuqa/overview?view_only=c029842a28344a60bc68b53887d457ba) that instructed it to follow the SCORE protocol for reproduction. This was the same protocol followed by the human SCORE project analysts and reported in Miske et al. (2026).

Procedure and Results

We applied the LLM analyst described abovefoot_3 to the same 12 reproduction targets used by Brodeur et al. (2026).

Reproduction targets varied by paper but were always a table column, a set of model results, or a figure. Data for one paper were unavailable; for the remaining 11 targets the LLM analyst performed all reproduction checks including generating and verifying figures. Results from the checks (i.e. whether the results reproduced) matched those from the Brodeur et al. human-only teams, except for one paper for which the reproduction package had been updated (and a correction issued) between the Brodeur et al. reproductions and the LLM analyst run. Brodeur et al. also tested how well humans performed at two other tasks: spotting errors in the data or analysis code (each of the papers was chosen in part because it was known to contain coding errors and/or data irregularities) and proposing robustness checks. These tasks are less relevant to our research question, but we asked the LLM analyst to attempt them as well and found performance comparable to that of human analysts. Results for these tasks, along with details of the papers, reproduction targets, and results, are reported in the Supplemental Material. The entire set of checks (for all targets) took approximately 11 minutes (using 11 agents running in parallel). By comparison, the average human-only team in Brodeur et al. required 82 minutes to reproduce a single result or table of results from a single paper; the fastest humanonly team required 21 minutes. Our findings suggest that current agentic LLMs are substantially faster and more accurate than the AI systems evaluated by Brodeur et al., and that their performance is at least comparable to that of human experts. Discussion

LLM capabilities continue to improve rapidly, and our results suggest that even models widely available in 2026 may be accurate and capable enough to support widespread adoption of their use for computational reproduction of scientific results. In our first test set, the LLM analyst produced reproducibility checks consistent with expert human analysts 87% of the time. When the two disagreed, follow-up examination found an error in the LLM's work in 6/45 cases (13%) vs. and error in the SCORE project's work in 25 (56%). In our second test set, the LLM analyst produced results that matched those of human-only teams. The speed at which such reproducibility checks can be carried out is also noteworthy. The reproducibility audit in our first test set took expert analysts hundreds of person-hours to complete, whereas our LLM analyst completed the same work in less than 48 hours, running mostly unattended on the first author's laptop.

Second, our benchmarking data came from the social and behavioral sciences. In the case of the SCORE project (Test Set 1) this was a stratified random sample of papers from 62 journals in business, education, psychology, economics, political science, and sociology (see Miske et al., 2026; Table 1). In the case of Test Set 2, papers were selected (not sampled) from journals in economics, political science, and psychology. Based on the consistency across test sets, we believe the current results would likely generalize to other papers in the social sciences, but more work is needed to assess whether the high accuracy rates we observe here also extend to papers in the life and physical sciences.

Third, while LLM accuracy was high, it was not perfect. Occasionally, the LLM analysts would misinterpret their instructions, take shortcuts, or mis-apply scoring criteria. Of course, humans make errors as well-in the cases we checked, the SCORE project's human analysts made twice as many errors as the LLM analysts did (even when setting aside data pipeline errors). Furthermore, some of the LLM errors we observed were easily fixed by minor tweaks to the analyst instructions and software tools (see Footnote 4). Nonetheless, researchers should be aware that LLMs can make non-deterministic mistakes and take steps to reduce their impact. For example, a second independent agent could check outputs for possible errors, multiple runs could be done over the same data (with disagreements flagged for human review), or human analysts could audit a random selection of results.

Finally, we used proprietary models from Anthropic (Claude 4.7/4.8) rather than openweight alternatives. We did this because we suspected that open-weight models in 2026 are not yet capable enough to perform well at the kind of complex and long-running tasks required for some reproducibility checks. Indeed, Brodeur et al. (2026) found that GPT-4/4o (OpenAI's flagship models in 2024) performed quite poorly at reproducibility checks (see also Hu et al., 2025; Siegel et al., 2026). Researchers have argued convincingly that for research tasks like natural language processing, proprietary models impair transparency and replicability (Barrie et al., 2025). Additionally, proprietary models generally cost money to use (though open-weight models also require either buying or renting hardware to run them). We think that the downsides of proprietary models are justified in this case (although this will likely change as open-weight models improve). For reproducibility checks, the model's decision-making is transparent (in that it can be reconstructed from the analysis outputs and task logs), and using a proprietary model is relatively affordable. All analyses were performed using one researcher's 200 USD/month subscription; had they been done on a usage-based plan, one complete run of both test sets would have cost under 300 USD.

Conclusion

Our results suggest that agentic LLMs offer a promising solution to making scientific research more reproducible. Like human analysts, LLMs can make mistakes, and we do not think that human analysts can or should be replaced. But the fact that LLM analysts can now do highquality reproducibility checks easily and cheaply puts large-scale checks within reach for many individuals and organizations. This includes scientific journals that wish to check submissions or accepted papers before publication, meta-scientists doing large-scale reproducibility audits, and individual researchers interested in verifying their own work.

S1. Sample construction (Test Set 1)

The starting pool was Miske et al.'s reproducibility-claims database (624 unique claims across 177 papers with at least one recorded reproduction attempt). We first excluded claims that Miske et al. did not include in their quantitative assessment because none of the eligible statistical outcomes (sample size, coefficient, test statistic, effect size, or p-value) was available (repro_outcome_overall == "none"). We then applied two filters (variable names and values are from Miske's data) to obtain the working set.

1. data_available == "Yes" and type == "J" (paper level): only journal-published articles whose data were recorded as publicly available. The type filter removes, among others, a supplementary sample of COVID-related preprints.

2. repro_version_of_record == TRUE (claim level): selecting the canonical reproductionattempt row Miske et al. used in computing their headline rates. This is necessary because some claims have multiple reproduction attempts. These filters yielded 357 claims across 75 papers. Three of those papers (Baker & Greene, 2011 [SCORE code: 9lBL]; Hertel et al., 2018 [SCORE code: YabW]; Horowitz, 2018 [SCORE code: exBp]), totaling 19 claims, were not attemptable by the LLM analyst because data could not be obtained from any of the standard repositories (OSF, Harvard Dataverse, the AEA replication archive, ICPSR, journal supplements, or author websites). By inspecting the original human analyst reports, we discovered that the data had actually been shared with the SCORE project via email for these three papers. These papers and claims are excluded from the analyses in the main text; the analytic sample is therefore 338 attempted claims across 72 papers.

The claim file's orig_* fields (e.g., orig_stat_value, orig_effect_size_value_repro) contain the SCORE project's claim-extraction values -the original papers' statistics as coded by SCORE's extraction pipeline. These values were produced independently of the human reproduction attempts, and they served as the reproduction targets for the human analysts and the LLM analyst alike. (The "_repro" suffix distinguishes the reproducibility study's effect-size fields from the replication arm's converted effect sizes; it does not indicate a value produced during a reproduction attempt.) For a small number of claims, the extracted values are not printed verbatim in the paper (for example, a test statistic computed by the extraction team from a printed contingency table).

S2. The LLM analyst

The LLM analyst was Claude Opus 4.7 (Anthropic), operating with file-system, codeexecution, and web-fetch tools. The analyst had access to Python, Stata, R, and the usual UNIX tools. The analyst was provided with a detailed reproduction plan, which is available on the project OSF page (https://osf.io/gcuqa/overview?view_only=c029842a28344a60bc68b53887d457ba). For each paper the analyst dispatched a sub-agent that read the published PDF, located the authors' archived data and code, attempted to reproduce each claim, and wrote a structured per-paper report. The analyst was given the paper PDFs, which we downloaded in advance, and a list of claims to verify. For each claim, the list contained the SCORE project's extracted claim text and statistics (see S1) and three fields from SCORE's process-reproducibility data: whether data were available, whether code was available, and where SCORE had located the data (for example, "Publisher website, Author website"). The Miske et al. (2026) materials (analystpackage R code, raw analyst submissions, downstream-cleaned outcomes) were not available to the LLM analyst during reproduction. After our first run, we noticed an error in the reproduction plan scoring guide that caused a small number of p-values to be mis-classified. We corrected this error and asked the analyst to rescore any affected outcomes (it did not re-run any verifications at this step).

S3. Procedure

For each paper, the agent worked through four steps. First, it verified that each claim's extracted statistical values matched those printed in the published papers. Second, it located the archived data and code via OSF, Harvard Dataverse, the AEA replication archive, ICPSR, journal supplements, or author websites. (If it could not obtain the data after about 45 minutes of searching, it was instructed to mark the paper as not attemptable. For 22 papers, the data were available but could not be downloaded automatically (for example, because the repository required an account or blocked automated access); we downloaded these files manually and ran the analyst again on those papers with the files supplied.) Third, it attempted reproduction via the lightest applicable type: Push Button (author code, author data, no modification), Extended Push Button (path, package, or syntax fixes only), or Source Data Reproduction (rebuild from public data when no code was posted). Finally, it recorded reproduced values, the bounds computed from the paper's printed values, and a verdict for each claim.

S4. Coding rubric

We applied the SCORE Criterion Guide bands verbatim. A specific claim could consist of several sub-outcomes-for example, a test statistic, sample size, and p-value could be suboutcomes for a single claim. For each claim all applicable sub-outcomes were tested. A sub-outcome reproduction was coded as "precise" when the reproduced value, rounded to the paper's reported number of digits, equaled the paper's value; "approximate" when the reproduced value fell within ±15% of the original (within ±0.05 for exact p-values); and "not" otherwise. P-value thresholds (e.g., "p < .01") were handled by the Criterion Guide's one-sided rule: any reproduced p-value strictly less than the threshold counted as precise. The overall claim-level verdict was "precise" if every reported sub-outcome was "precise," "not" if any was "not," and "approximate" otherwise. As in the SCORE project, claims for which a reproduction was begun but the available data or code proved insufficient to complete it ("not attemptable") were counted as not reproduced.

S6. Disagreement adjudication

One of two coders (Y.I. and J.K., a research assistant) adjudicated every claim where the LLM's verdict disagreed with the canonical SCORE verdict. For each disagreement, the adjudicator consulted the published paper, the SCORE analyst's preregistration and transparency-trail document on OSF, and the LLM analyst's run logs and report. If necessary the coders also attempted to reproduce the result themselves from the authors' data and code (if available). Each disagreement was coded on 1) whether the LLM had made an error (for example, running the wrong statistical test), 2) whether the SCORE project had made an error (for example, a human analyst entering an incorrect value, or programming error in the SCORE data-processing pipeline), 3) whether both verdicts were defensible (which could happen if the paper authors updated their data or code between when the SCORE project ran their analyses and when we ran ours, or if the human/LLM analysts had made different but defensible judgment calls), or 4) whether both had made different errors.

Coder verdicts for each claim, along with the coder's explanation of the disagreement, are listed in the file adjudicated_disagreements.csv, which is available at the manuscript's OSF project page (https://osf.io/gcuqa/overview?view_only=c029842a28344a60bc68b53887d457ba).

For the LLM, we identified six errors. Three of these were the result of skipping computationally intensive processes (using the author's saved JAGS models instead of re-fitting and two cases of skipping very long permutation analyses to compute p-values). One was the result of not using statistics extracted from a figure. The remaining two were the result of re-implementing analyses originally in SAS/SPSS in other software and getting slightly different results. Of the 26 claims involving a SCORE error, 14 were due to bugs in the code that evaluated analyst reports, compared them to results extracted from the paper, and computed verdicts. Twelve were due to analyst errors (e.g., entering values incorrectly, mis-reading output, not being able to compute the DV correctly).

S7. Sensitivity to inclusion of details from pilot testing

We used four of the audited papers (G4mp, L22B, qg47, and Pxp7) for pilot testing. The reproduction plan provided to the LLM analyst inadvertently contained worked examples that referenced materials from these papers. These were an example directory name, a variable name from one paper's released data, a filter clause from another paper's code, and a rounding illustration using one claim's reported values. We removed these details from the reproduction plan and re-ran the reproductions in a clean environment for these four papers (using Opus 5, the latest Opus model available at the time). All results from this second run matched the original results, except that on this run the model was able to resolve a figure-read issue that the previous model could not (see Footnote 4 in the main text).

S8. Sandboxed re-runs

Each paper was reproduced by a separate freshly started agent (Claude Opus 4.7, run non-interactively through Claude Code 2.1.325). The agent received a short task prompt and a read-only input folder with the published paper, the list of claims to check, the reproduction plan, and the data and code posted by the paper's authors. The plan was identical to the one used in the first run, changed only where the sandbox required it (for example, the step in which the agent locates the data was removed, because data were supplied) and to incorporate two fixes for errors in the first-run plan: correcting scoring criteria (see section S2) and removing examples referencing pilot data (see section S7).

Every agent ran under a macOS Seatbelt profile (sandbox-exec) that applied to the agent and to every process it started, including Stata, R and Python. Under this profile the agent could read system software, a shared read-only library of preinstalled packages, and its input folder.

All other user files on the machine were unreadable. The agent started with no memory or settings from any other session. Launching other applications, inter-application messaging, and access to the keychain and clipboard were blocked.
