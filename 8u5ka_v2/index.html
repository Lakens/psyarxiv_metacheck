How Power Analysis Check works

This module uses regular expressions to identify sentences that contain a statistical power analysis. If specified by the user, it also uses a large language model (LLM) to extract information reported in power analyses, including the statistical test, sample size, alpha level, desired level of power, and magnitude and type of effect size.

The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. Without the use of an LLM, the module uses regular expressions to classify the power analysis as a-priori, sensitivity or post-hoc. With the use of an LLM, it checks if the power analysis is reported with all required information.

The regular expressions can miss power analyses, or fail to classify them correctly. The type of power analysis is often difficult to classify, which can easily be solved by explicitly specifying the type of power analysis as ‘a-priori’, ‘sensitivity’, or ‘post-hoc’. Note that ‘post-hoc’ or ‘observed’ power is rarely useful. The LLM can fail to identify information in the paper, and will not have access to information in paragraphs in the paper other than those that contain the word ‘power’. This package was validated by the Metacheck team on articles in Psychological Science.

This module was developed by Lisa DeBruine, Daniel Lakens and Cristian Mesquida

Read more in the metacheck manual.

Overall, among all instances flagged as power statements, 90.6% were correct (positive predictive value).

How Preregistration Check works

Retrieve information from preregistrations in a standardised way, and make them easier to check.

The Preregistration Check module identifies preregistrations on the OSF and AsPredicted based on links in the manuscript, retrieves the preregistration text, and organizes the information into a template. The module retrieves text from the OSF with its API, and from AsPredicted with ResearchBox’s API when a ResearchBox key is set (see rbox_token()), or else from the preregistration’s web page. The information in the preregistration is returned. An AsPredicted link that could not be read is named in the report, with the reason.

The module can’t extract information from non-structured preregistration templates (i.e., where the preregistration is uploaded in a single text field) and it can’t retrieve information in preregistrations that are stored as text documents on the OSF.

If you want to extend the package to be able to download information from other preregistration sites, reach out to the Metacheck development team.

How StatCheck works

Check consistency of p-values and test statistics

The Statcheck module runs Statcheck. Statcheck searches for regular expressions that match a predefined pattern, and identifies APA reported statistical tests. More information on the package can be found at https://github.com/cran/statcheck. The module only returns Statcheck results for t-tests and F-tests, as these are the only tests which have been validated, see https://osf.io/preprints/psyarxiv/tcxaj_v1/.

Statcheck was developed by Michèle Nuijten and Sascha Epskamp.

Statcheck considers p = 0.000 an error, as you should report p < 0.001. Furthermore, p < 0.03 is an error if the p-value was 0.031, and one should simply report exact p-values (p = 0.031). When the sentence of a test says it is one-sided (“one-tailed”, “one-sided” or “directional”), a p-value that fits a one-sided test counts as consistent (statcheck’s OneTailedTxt setting; #695). When the paper says anywhere that its tests are one-sided, a p-value that fits a one-sided test in either direction counts as consistent too: half the two-sided p, or 1 minus that half for an effect against the predicted direction. Equivalence tests (TOST) are left out, as their p-values do not test the difference. A statistic written with “<” or “>” is read as a bound, and in a sentence about equal variances an F-test’s two-sided p (twice the one-tailed p) counts as consistent. For more information, see StatCheck.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

A link to a file-sharing service (Google Drive, Dropbox, OneDrive, Box, WeTransfer, MEGA, iCloud Drive, Baidu Netdisk, SURFdrive; see [file_share_links()]) gets a warning and makes the light yellow: such services are not repositories, as files can be changed or deleted at any time, get no DOI, and the link stops working when the account is closed. The report advises a stable repository such as Zenodo instead. Their files are not read, and summary_table$file_share_n counts the links.

Deposits in archives for sequence and expression data (GEO, the INSDC archives BioProject, SRA, ENA and DDBJ, and ArrayExpress; see [seq_archive_links()]), mostly named by accession number, are read for whose deposit they are. The authors’ own are listed with what they hold ([seq_archive_size()]) and are not downloaded or checked as data and code; summary_table$archive_own_n counts them.

R packages on CRAN ([cran_links()], [cran_info()]) are the paper’s own when a paper author is a package author and the paper presents the package; the paper’s own are listed with their version and not checked (summary_table$cran_own_n). A Handle link (hdl.handle.net/...) that leads to a repository read here is checked as a link to that repository ([handle_links()]).

Listing a repository’s files never requires an API key, but some hosts answer faster or more completely with one: OSF allows 100 requests/hour unauthenticated versus 10,000/day with a token (see [osf_pat()]), and Dryad enforces a strict per-IP daily quota on repeated listing (see cache below). Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Since this module only lists files and never downloads their contents itself, that limitation applies to data_check and code_check (which do download content), not here – see their own documentation.

When a linked OSF page is a registration, its registered_from project (the one it was registered from, which the manuscript itself may never link directly) is also checked: if that project is public its files are listed under its own URL, and if it is closed or otherwise inaccessible the report flags it explicitly, since some registrations only describe their content rather than mirroring it.

Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). On a round of labelled links the rules had not been written from, the three groups were right for 98% of links in the main text (93 of 95) and 90% in reference lists (74 of 82); the labels were made by Claude agents from each link’s evidence, and disputed ones checked against the deposits. Telling this paper’s own deposit from the authors’ earlier one is less certain.

Only the deposits that are this paper’s own are checked. A deposit linked in the text that holds other people’s work (others_data, others_code) or the authors’ earlier work (own_earlier_data, own_earlier_code) is listed in the report, with the reason, but its files are left out of table and kept in table_not_checked: they count toward nothing here (files that do not belong in a repository, naming, READMEs, studies, the traffic light), and code_check, data_check and reproducibility_check, which read table, do not check them either. reproducibility_check still puts the files of theirs that the paper’s code names in the folder the code runs in, as a re-analysis needs the data it re-analyses. When every linked deposit is set aside, the traffic light is “na”. A deposit that is the paper’s own is counted as such when its README, title or description names the paper (its title or DOI).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability).

Provenance, kept so that a TRACE Research Object (TRO) declaration of the run can be written later from a stored result (metacheck #404; the helpers are in R/provenance.R). Only when code was run (execute = TRUE): * run_results$started_at, run_results$ended_at: when each run of a script started and ended (ISO 8601, UTC, milliseconds); NA for a script that was not started. A script run again in a later pass has the times of its last run. A TRO uses them for each trov:TransparentResearchPerformance. * run_results$exit_status: the exit status of the process that ran the script (0 = ended normally); NA when the process did not report one (a time limit, or Docker failing to start the container). * artifacts: one row per file, with stage (deposit: as downloaded from the repository, hashed from the downloaded file; before_run: the run folder just before the first script ran, after metacheck’s own changes, such as rewritten paths and unpacked archives; after_run: only the files the scripts made (status new), changed (changed) or removed (removed), as an unchanged file is the one listed before the run), path (relative to the run folder, as valid UTF-8, a byte of another encoding written as <xx>), size (bytes), sha256, mime_type (by extension, NA when unknown), source (the file’s address in the repository, for deposit). The package libraries metacheck installs in the run folder are left out, as are metacheck’s own files there (a script’s runner, and the statistical output it writes in statistical_output/). Files metacheck itself copied or made between passes (see modifications, output_copied, file_placed) show in after_run too. A TRO uses the rows as trov:ResearchArtifacts and each stage as a trov:ArtifactArrangement. * modifications$sha256_before, modifications$sha256_after: the hash of the changed script as downloaded and as it ran; NA when the script is not at the same path in both (a script made from an R Markdown file). * environment: the system that ran the code (trov:TransparentResearchSystem in a TRO): metacheck_version, started_at, ended_at, host (R version, platform, operating system), sandbox, network_isolated (TRUE only when every Docker run had --network none; the process sandbox does not stop the network), internet, timeout_per_script, total_timeout, python_local (the Python run outside Docker and its version), and docker: runs (for each kind of run, r_run, r_install, python_run, python_install, the image and the docker run arguments, such as --network none, --read-only, --cap-drop ALL, no-new-privileges, the process limit and the memory and processor limits) and images (for each image, its ID and digests from docker image inspect, its creation time and the R and Python versions its environment declares).

run_results$checked says what the run of each script shows about the code, in five groups, so that a script that does not reproduce is kept apart from one the check could not test: ran (it ran to the end); code_error (it did not reproduce: it stopped with an error of the code or the deposit, could not be read, or needs a file the deposit does not hold); dependency (a package or program was not available: a package that could not be installed or was not loaded, a program outside R and Python, a system library, or R crashing in a package’s compiled code); time (it did not finish within the time limit for one script, or was not started because the time for all scripts had run out); and not_checkable (it could not be checked automatically: it needs a person, the internet, a key or another setting of the authors’ computer, one platform such as Google Colab, Windows or OpenSAFELY, more memory than the run allows, a file that was not downloaded, a screen, or a program that runs it, or it is a file of a package of the code that Python runs only as a module of that package). It is NA for files run inside another script, files that are not an analysis, files not read, and a Docker failure. summary_table counts each group (repro_ran_n, repro_code_error_n, repro_dependency_n, repro_time_n, repro_not_checkable_n), and the report’s first sentence gives them. The traffic light reflects the static readiness signals by default; a script in code_error that stopped with an error makes it red, as a script that crashes on its own analysis is a genuine reproduction failure, and a script in one of the other three groups keeps it from being green. Full text

Abstract

There are many different data analytical procedures applicable to data obtained via single-case experimental designs, with mean differences, regression-based procedures, and nonoverlap indices being among the most frequently used ones. The possibilities are reduced when the data are ordinal and/or variable and cannot be meaningfully summarized by straight lines. For such scenarios, nonoverlap indices become prominent. The current text is a continuation of previous discussions related to the quantification of trend in the context of using nonoverlap indices. Focusing on the Tau indices by Parker and colleagues and by Tarlow, we underline potential drawbacks that have not been discussed previously, while also suggesting alternatives. Specifically, we point at situations in which underestimation and overestimation of trend are possible, as well as discussing the quantification problems arising in case trend levels off by reaching an upper or lower bound. The aim of the review of existing options and of the tentatively proposed alternatives is to ignite further discussion regarding how to deal with trend without assuming that a straight line (or any specific nonlinear model) is a good representation of the data. A new graphical representation is suggested to accompany the newly proposed quantification of monotonic trend.

Single-case experimental designs allow obtaining evidence on whether an intervention is effective, on the basis of multiple measurements of the target behavior in different conditions. This evidence is more solid (i.e., internally and externally valid), the more that an effect is replicated within a participant and across participants (Morley, 2018; Tate & Perdices, 2019). In that sense, one of the main requirements from a SCED is to include several demonstrations of an intervention effect (What Works Clearinghouse, 2022). Additionally, Levin and Kratochwill (2026) stress the presence of baseline trend and outliers as some of the most relevant operational issues that can affect the respectability of SCED research, in addition to the importance of randomization and replication. The current text, with its emphasis on monotonic trend, is directly related to both trend and outliers. SCED data analysis includes multiple options that have already been reviewed, discussed, and formally compared across several manuscripts (e.g., Busse et al., 2015; Chen et al., 2015; Dowdy et al., 2021; Gage & Lewis, 2013; Maggin et al., 2019; Manolov & Rochat, 2024; Parker & Brossart, 2003; Parker & Hagan-Burke, 2007; Pustejovsky & Ferron, 2017; Solomon et al., 2015). The current text focuses on situations in which the data are ordinal or variable and exhibit trend. In a recent paper on Type I error rates it was specifically mentioned that controlling false alarm rates is more complicated when data are "messier" (characterized by few measures, trends, and variability; Wolfe & Ferron, 2026). Accordingly, a set of data analytical options appropriate for such data also dealt with. The aim is to caution applied researchers about potential drawbacks of some data analytical options and to tentatively suggest ways of dealing with them. In what follows, we first define the essential terms. Subsequently, we refer to the quantifications of effect that are applicable, with their potential limitations, illustrated with data from previous reviews of nonoverlap indices. We also suggest alternatives and comment on their features.

Preliminary Notes

Definitions of Key Terms

Overlap

Overlap is conceptually defined as "proportion of data values that are the same across adjacent conditions" (Ledford et al., 2019; p. 52) or "the extent to which data in adjacent phases are within the same range of values" (Maggin et al., 2018, p. 188).

Thus, there aparently is some relation between nonoverlap and level 1 . Specifically, when the distance in level increases, the overlap can be expected to be smaller.

Moreover, a complete separation (i.e., an even larger distance in level) would entail no overlap.

Ordinal Data

The term "ordinal" refers to the measurement scale of the dependent variable, considering how information is gathered. Specifically, ordinal data only allow for saying whether two values are equal or not (like in a nominal scale) and, if not, which value is larger. They do not justify quantifications in terms of distance due to the impossibility to assume constant distances or intervals between pairs of possible values (i.e., the data cannot be assumed to be measured in an interval scale). Ordinal data can arise, for instance, from rating scales representing subjective states (e.g., satisfaction, fatigue). Among SCED data analytical alternatives, nonoverlap indices (Manolov & Tanious, 2025; Parker, Vannest, & Davis, 2011; Rakap, 2015; Yucesoy-Ozkan et al., 2020) are especially suitable for ordinal data, as they quantify dominance, that is, the 1 Level is defined as relative value or magnitude (Lane & Gast, 2014), mean or average (Maggin et al., 2018), or as amount of behavior (Wolfe et al., 2019).

extent to which the measurements from one condition are better (higher or lower, according to the aim of the intervention) to the measurements from the other condition, without quantifying how much better (i.e., distance). In contrast, quantifications based on means such as regression models (Allison & Gorman, 1993; Swaminathan et al., 2014), log-response ratio (Pustejovsky, 2018), standardized mean difference (Shadish et al., 2014), a ratio of distances (Carlin & Costello, 2018), are not technically applicable to ordinal data.

Variable Data

The term "variable" is opposite to "stable". Variability can be defined as the "extent to which individual data points deviate from the overall trend of the data within the phase" (Maggin et al., 2018, p.188) or the "the spread or fluctuation of the data around the trend line" (Wolfe et al., 2019, p. 491). It may be subjective to define when data is stable or predictable vs. variable, although certain arbitrary criteria have been suggested, such as the stability envelope (Lane & Gast, 2014). In the current text, we use "variable" loosely to denote data that cannot reasonably be summarized or represented by a straight flat line (e.g., a mean or a median) or a straight trend line.

A Specific Way of Quantifying Nonoverlap

A nonoverlap index such as the Nonoverlap of All Pairs (NAP; Parker & Vannest, 2009) is especially useful for variable data, given that it does not represent the data by any single reference value (e.g., the best measurement as in the Percentage of nonoverlapping data; Scruggs et al., 1987) or straight line (e.g., the median in the Percentage of data points exceeding the median -PEM; Ma, 2006). Instead, each measurement from one phase is compared to a measurement from the other phase. Thus, variability is not lost by reducing the data to a single point or line, nor is it treated as error (for standardizing purposes). Moreover, NAP has been stressed recently as a potentially useful quantification, due to using all data and being well aligned with the idea of common language effect sizes that are likely to be more easily interpreted by a wider audience than statistical experts (Uanhoro & Rojo, 2026).

Trend

The term "trend" is conceptually defined as "progress over time" (Lane & Gast, 2014, p. 447) or "the direction and magnitude of change in outcome data within a phase" (Maggin et al., 2018, p. 188), thus, distinguishing between "direction (accelerating or decelerating), magnitude (steep or gradual), and relation to the hypothesized change (improving or deteriorating)" (Ledford et al., 2019, p. 51).

Such a progression entails that there is no stable or maintained level in a given condition, but rather a change is taking place in subsequent measurement occasions. A trend can take place in the baseline and represent a deterioration or a spontaneous improvement before an intervention is introduced. A trend can also take place in the intervention phase, indicating that the effect of the intervention is progressive rather than abrupt and maintained.

There are multiple ways to fit straight trend lines to SCED data (Manolov, 2018), as well as proposals for using nonlinear models (e.g., Sullivan et al., 2015; Swan & Pustejovsky, 2018; Verboon & Peters, 2020). Moreover, quantifications of monotonic trend that do not require any specific model have also been suggested (Parker, Vannest, Davis, & Sauber, 2011; Tarlow, 2017). The latter are especially relevant for the current text, given that monotonic trend can be quantified even for ordinal data and also because these proposals have been specifically implemented in the context of nonoverlap indices.

Monotonic Trend

Before referring to the existing proposals for combining nonoverlap and monotonic trend, it is important to define two terms. The first term is "monotonic trend"

and it refers to a progression in the data in which the direction does not change.

Specifically, if the measurements are increasing at earlier moments, they never decrease at later moments (i.e., they only increase or are maintained equal to adjacent previous measurements). Analogously, if the measurements are decreasing at earlier moments, they never increase at later moments (i.e., they only decrease or are maintained equal to adjacent previous measurements). This definition of trend is present in Tau-U (Parker, Vannest, David, & Sauber, 2011) and in the Baseline corrected Tau (BCT; Tarlow, 2017). However, the exact operational definition is not the same in both nonoverlap indices. In Tau-U, there is a comparison between each measurement and all preceding measurements from the same phase, quantifying the proportion of these comparisons in which the later measurement represents an improvement. Expressions are available in Pustejovsky (2016b Pustejovsky ( , 2016c)). In BCT, Kendall's correlation is computed between the measurements obtained in a phase and a variable representing the measurement occasions by integers (1, 2, etc.). Expressions are available in Aydin (2026).

Strictly Monotonic Trend

In relation to trend, a second term that needs to be defined is "strictly monotonic trend", which we recommend in the current text, as will be discussed later. A "strictly monotonic trend" is a progression in which the measurements in a given phase always change in the same direction without maintaining equal values. Specifically, if the measurements are increasing at earlier moments, they only increase at later moments (i.e., they do not decrease and do not remain the same as in the adjacent previous measurement). Analogously, if the measurements are decreasing at earlier moments, they only decrease at later moments (i.e., they do not increase and do not remain the same as in the adjacent previous measurement). Building on Previous Discussions and Proposals on Overlap and Trend

In the SCED context, there are multiple procedures dealing with trend (e.g., Allison & Gorman, 1993; Moeyaert et al., 2014; Parker et al., 2006; Swaminathan et al., 2014). One noteworthy discussion of trend is due to Parker, Vannest, Davis, and Sauber (2011) advocating against linear trends that continue unabated and against impossible projections, specifically recommending to avoid regression-based models such as the one by Allison and Gorman (1993). This discussion led to, at least, two different consequences. On the one hand, Parker, Vannest, Davis, and Sauber (2011) suggested the previously described quantification of monotonic trend to be included in the calculation of the nonoverlap index called Tau-U. On the other hand, a proposal was made for deciding how far away is it reasonable to project baseline trend and how to deal with impossible projections (Manolov et al., 2019).

Subsequently, the trend correction procedure implemented in Tau-U was studied and criticized by Tarlow ( 2017 has also been addressed with a modification in the common time series line chart (Manolov & Tanious, 2025). Finally, in relation to Tau-U, interpretative benchmarks and cut-off points for trend control have been proposed (Vannest & Ninci, 2015 , 2016), but without a clear basis such as field study or meta-analysis (Manolov et al., 2024).

Specifically focusing on Tarlow's (2017) study and discussion, it led to the proposal of the BCT. This index is different from Tau-U is both the quantification of monotonic trend and the way in which trend is controlled for (specifically, using the Theil-Sen method fitting a straight line; see Vannest et al., 2012). Regarding BCT, it has been stressed that the baseline trend test is not the same as the baseline trend controlled for (Manolov & Tanious, 2025). Also, the original evidence provided by Tarlow (2017) shows that this test is underpowered for short baselines (i.e., shorter than 10 measurements, considering the median of 7 measurements for initial baselines reported in the review by Pustejovsky et al., 2023, a mode of 6 reported by Smith, 2012, and almost half of the baselines having fewer than 5 measurements in the review by Shadish & Sullivan, 2011). Also focusing on BCT, a recent comment by Aydin (2026) criticizes two aspects: the two-tailed test for trend and the sensitivity to tied values. As a consequence, refinements of BCT were proposed to mitigate these limitations. Ferron and colleagues (2026) also stress some limitations of the BCT: specifically, they mention that the use of Kendall's tau-b and the presence of ties using the binary phase indicator (for distinguishing between baseline and intervention) lead to challenging interpretation of the quantification as overlap, apart from pointing at the problematic assumption of trend stability.

Regarding other nonoverlap indices, similar to NAP, PEM (Ma, 2006) does not quantify baseline trend, but a modified version (Percentage of data points exceeding median trend -PEM-T; Wolery et al., 2010) entails a comparison with the projected baseline trend line fitted using the split-middle or bisplit method. Nonetheless, a trisplit method has been suggested to be superior than bisplit (Manolov, 2023; Parker et al., 2014).

The current text follows the same line of identifying limitations in already existing proposals (specifically, Tau-U and BCT) and identifying potentially useful alternatives.

Similarly, Ferron's et al. (2026) review of SCED quantifications specifically focuses on identifying and making explicit their limitations. We follow a similar approach, concurring with Taleb's (2010) comment that it is usually easier to identify what is wrong than to know what is right and that it is crucial to prevent problems by dismantling myths and debunking false certainties. In this case, the aim is to address the potentially excessively simplified idea that more recent nonoverlap indices are necessarily good options just because they overcome some limitations of previously proposed indices (i.e., just because they are better in some aspects).

We consider that it is reasonable to look for an alternative for Tau-U due to its frequent use in published SCED research across different disciplines (e.g., Balikci & Gulboy, 2026; Brown et al., 2024 Brown et al., , 2026;; Moeyaert et al., 2025; Morin et al., 2024; Peltier et al., 2023; Zink et al., 2024) and also in meta-analysis among other nonoverlap indices (Jamshidi et al., 2023). For instance, according to a review by Brown et al. (2026), there is evidence for incorrect reporting and also for differences between authorreported values and recalculated values after digitizing the data) specifically for Tau-U.

Additionally, there are specific publications recommending it (Zimmerman et al., 2018) or aiming to highlight Tau-U's advantages (Lee & Cherney, 2018) and thus, we consider that researchers need a more complete perspective instead of focusing only on positive features. Moreover, an example from a recent publication (Lavefjord et al., 2026), includes several potentially problematic features: (a) using Tau combining control for baseline trend and quantification of intervention phase trend (called a "conservative version"), without any justification regarding why trend needs to be taken into account in any of the phases, on the basis of expectations or data patterns, as it is not clear from plots reported that trend lines are different from mean lines in many of the phases; (b) using Tau-U benchmarks (Vannest & Ninci, 2015 , 2016) lacking any empirical or theoretical basis; and (c) using p-values for Tau-U without any comment on the assumption of independent data. Currently, there is no evidence regarding the extent to which BCT is used, but the fact that it was proposed by Tarlow (2017) as an improvement of Tau-U and the work by Aydin (2026) prompted us to also focus on this nonoverlap index. Another reason for the need of further comments on these quantifications is that confusions between Tau-U and BCT are possible (see, for instance, Al Sharaa et al., 2025).

Problematic Impact of Earlier Measurements: An Example with an Alternating Pattern

As mentioned previously, Tau-U (Parker, Vannest, Sauber, & Davis, 2011) compares each measurement to all of the previous measurement from the same condition, regardless of how far away in time they are obtained. There are two consequences. First, an earlier measurement is involved in more comparisons than later measurements and, thus, can have greater effect on the quantification of trend. This may be especially problematic if researchers wait for an initially variable baseline to stabilize before intervening: the quantification of trend will be highly influenced by the values prior to stabilizing. Second, an outlier can distort the comparisons with all subsequent measurements, when quantifying monotonic trend.

In contrast, the definition of strictly monotonic trend in β A entails comparing only adjacent values. Therefore, all measurements, except for the first and the last in the phase, have influence on two within-phase comparisons only -when comparing to the previous and to the subsequent value. Regarding the justification of the focus on adjacent values, it is strongly related to how differencing is performed in ARIMA models (Harrop & Velicer, 1985) and also to the mean phase difference quantification (Manolov & Solanas, 2013). Actually, the idea to focus on adjacent values is also related to the naïve method for forecasting, according to which each value is predicted to be equal to the previous one (Chatfield, 2020). Similarly, when assessing intervention effectiveness in a reversal design (ABAB or ABABAB), only adjacent phases are being compared; not the first A with the last B.

Reaching an Asymptote: Dealing with Impossible Progressions

Regarding trend and the importance not to assume that it can continue unabated forever (Parker, Vannest, Davis, & Sauber, 2011), it may be necessary to consider the possibility of reaching an upper asymptote (when the aim is to increase the target behavior) or a lower asymptote (when the aim is to eliminate it). When referring to an asymptote, we specifically consider the case in which the minimal or maximal value of target behavior as measured is known and thus it is not possible to obtain a more extreme score.

As an example, consider again the data from Figure 3 and suppose the maximal possible value was 10, reached in the last three intervention phase measurement occasions. For such a pattern as the one observed during the intervention phase, the quantification of strictly monotonic trend could be underestimated (the value of β B = .33 ).

This quantification is potentially affected by the fact that the measurements cannot increase any more. Thus, a stopping rule may be justified. Specifically, when quantifying strictly monotonic trend, it would be reasonable to exclude the data (and the comparisons) after the upper bound is achieved and after it is verified via visual inspection that this asymptote is maintained in subsequent measurements. In this specific example, if we discard the last two intervention phase measurements, β B = .50 , correcting the underestimation. Baseline Trend Correction

Limitations of Tau-U

The way in which trend is controlled for in the context of Tau-U and BCT is not necessarily optimal. Regarding Tau-U, the original text by Parker, Vannest, Davis, and Sauber (2011) includes two different computational examples in relation to baseline trend control. Even if the version implemented in the websites (https://singlecaseresearch.org/ and https://jepusto.shinyapps.io/SCD-effect-sizes/) is used, there is evidence that baseline trend control is insufficient (Tarlow, 2017). An additional problem identified by Tarlow (2017) is the possibility of obtaining out-ofbound values. Finally, the arbitrary nature of the correction entails that standard errors (and thus confidence intervals) are not available for Tau-U (Pustejovsky, 2016b (Pustejovsky, , 2016c)). Additionally, potential issues in the quantification of monotonic trend (as illustrated here) necessarily have impact on trend correction.

Different Ways of Proceeding across SCED Data Analytical Techniques

Due to the previously presented limitations, we consider that mixing in the same index a quantification of trend and overlap may not be optimal. A similar distinction can be made between two regression-based options. The generalized least squares model by Swaminathan et al. (2014) considers jointly level and trend into a single quantification of the average difference (vertical distance) between the projected baseline trend line and the fitted intervention trend line. As an example of an interpretative challenge, such a quantification it can yield a zero when the change in slope and change in level are in different directions, potentially obscuring information.

In contrast, piecewise regression (Center et al., 1985; Moeyaert et al., 2014) which is the building block of multilevel models, separately quantifies of level and trend.

There is evidence that the estimation is more precise with separate quantifications rather than with a joint one (Manolov, 2023). As an interpretative challenge, taking into account the trends in the baseline and intervention phase, a comparison in level is only possible for a given moment in time (e.g., the first or the last intervention phase measurement occasion) not overall. Actually, such a comparison implicitly entails a projection of baseline trend. In contrast, the comparison between the estimates of slope in baseline and intervention phase entails no projection.

Our Recommendation

We here suggest not to account for trend, but rather to assess whether it is present and act accordingly quantifying it. Instead of suggesting a quantification of overlap for a given moment in time, we suggest using NAP when there is no trend. On the contrary, when there is trend, we recommend comparing the monotonic trends in the baseline and intervention phase (i.e., the values of β A and β B ), as would be done when comparing slopes in a piecewise regression model.

Similarly, we do not suggest extending baseline trend, although this would allow for a comparison between actual and projected data, as suggested by Kratochwill et al. (2013), and as feasible via PEM-T (Wolery et al., 2010) or the regression model by Swaminathan et al. (2014). We advocate for avoiding unreasonable projections, following previous cautions on that matter (Manolov et al., 2019; Parker, Vannest, Davis, & Sauber, 2011).

Additional Graphical Representation

As part of the proposal for defining strictly monotonic trend, a new graphical representation is suggested, illustrated in the right panels of Figures 1, 2, and 3. This graph would represent the differences between successive measures within each phase, consistent with the definition of monotonic trend. When the differences are in the direction of improvement, they are marked with green dots. Complementarily, when the differences entail deterioration, they are marked with red dots. Ties are marked in blue.

A predominance of green dots would reflect an overall trend of improvement.

According to where these green dots are located in time, it is possible to evaluate whether there is a strictly monotonic trend throughout the whole phase or the data pattern is somewhat more complex (e.g., a monotonic trend that has late onset or that fades away). If there are more green dots (proportionately to the number of measurements) in the intervention phase than in the baseline phase, this would be indicative of a stronger improving trend after the intervention.

Moreover, in case the lower or upper bound is reached, and the quantification of strictly monotonic trend ceases, the remaining data points are marked in grey (not in green, red, or blue).

Further Questions

As the aim of the current text is to ignite discussion, beyond the alternatives suggested, there are still many questions that need to be answered. We here specifically comment on two such questions next: the need for modeling and the place of inference in SCED data analysis.

Chance Fluctuations and Modelling

NAP and Tau use the measurements as obtained when performing calculations.

These measurements are not reduced by any summary measure (e.g., there is no comparison between a baseline mean and an intervention phase mean). The same is the case when quantifying monotonic trend (as operationally defined in Tau-U) and strictly monotonic trend (as operationally defined here). In that sense, all these calculations could be said to be sensitive to chance fluctuations. On the one hand, chance fluctuations can be relevant for the quantification of trend, as shown previously in the text (see the subsection entitled "Random fluctuations (or not)" within the "Issues and Suggested Alternatives" section). On the other hand, they can have an effect on baseline trend control. For instance, when deciding whether to control for baseline trend, Parker, Vannest, Davis, and Sauber's (2011) recommend assessing whether trend is pronounced or credible. Accordingly, Lee and Cherney (2018) illustrating Tau-U, chose a cut-off point for baseline trend control that corresponds to "trend that is evident upon visual inspection of the data" (p. 498). Such a way of proceeding leads to a subjective judgment which may be suboptimal or not necessarily rational (e.g., consider the results by Henderson et al., 2006, on participants giving more or less importance to deviations when assessing trend according to irrelevant factors, illustrating the Construal Level Theory). Moreover, it has been emphasized that with short series it can be difficult to determine whether there are trends: on the one hand, an existing trend may not be detected and, on the other hand, a small sample of observations may suggest that data appear to have trend (Wolfe & Ferron, 2026). In this context, we should consider also the human tendency to look for deterministic patterns even when there are not any (see Kahneman et al., 2021, and psychological traps such as the post-hoc causal narrative and the denial of statistical reality). Thus, the researchers' knowledge about the participant and the relevant variables surrounding the intervention and the target behavior can be crucial for distinguishing between pattern and random (unexplained) variability.

The alternative would be to try to represent the real underlying pattern via a model and thus reduce noise. For instance, regression-based models include such representations of the data via trend lines and the standardized mean difference does the same via mean lines. The descriptive measures require assuming or checking that these lines fit well the data, whereas any inferential information requires further assumptions about the results. Moreover, it is not always clear whether we can imagine that a model is correct only because it fits well the data. For instance, a quadratic model can fit well to exponential data but still be incorrect, just like a cubic model can fit well to logistic data but still be incorrect. Additionally, there may not be any solid rationale (from previous evidence or from the data gathered) for any given model.

We specifically contextualized the discussion of overlap and trend in scenarios in which data are not stable. We do not have an answer to the questions whether data variability is noise (unwanted chance fluctuation) or it is information worth keeping in its original form. We consider that this question cannot be answered in general, irrespective of the knowledge of the person, issue treated, and intervention. Therefore, we consider that a parsimonious option would be to work directly with the data (as in NAP, Tau-U, and the definitions of monotonic and strictly monotonic trend), rather than using models to account for or reduce chance fluctuations. Stated otherwise, a quantification in ordinal and monotonic terms is more general and open-ended that assuming the model is known and correctly identified. However, it is important to judge whether a single measure can be affecting unduly the quantifications (as in some of the examples from Table 1), following the idea that expert judgement is especially relevant in the idiographic approach (Imam, 2021).

In general, it is necessary to consider the costs and consequences of reducing noise, only if it is unwanted variability (Kahneman et al., 2021). For instance, the interpretation of the slope of a linear trend requires equal time intervals between measurement occasions, otherwise the increase or decrease quantified refer to non-time units (e.g., session number instead of calendar days), an issue already discussed for time-series linear charts (Bulla & Kubina, 2026). Another question worth answering would be whether reducing noise (e.g., using a linear model as in the Theil-Sen method instead of quantifying monotonic trend) may introduce bias.
