>       omega0 <- theta[(K+2):(2*K+1)]       # length K
>       
>       A_indistinguishable = psi * tcrossprod(Lambda) / sum(Lambda^2) # A_indistinguishable
>       Z_indistinguishable = (1-psi^2) * tcrossprod(Lambda)
> 
>       # 2) Compute the implied covariance.
>       S_implied <- dcf_ccov_Mblock(Lambda, psi, time_points) + 
>         diag(rep(omega0, times = time_points), time_points*K, time_points*K)
>       
>       if(return_cov) {return(S_implied)}
>       
>       if(any(eigen(S_implied)$values < 1e-6)) {warning("Non positive-definite implied covariance.")}
> 
>       # 3) Compute the discrepancy.
>       return(F_ML = log(det(S_implied)) + 
>                     sum(diag( solve(S_implied) %*% S )) - 
>                     log(det(S)) - 
>                     time_points*K) 
>     }
>     
>     # Maximum Likelihood statistic, with constraints:
>     # Error variances (perturbations in the Supplementary Material) and serial covariances positive.
>     # The CF is implicitly assumed to have unit variance.
>     # DCF is constrained stationary.
>     lower_bounds  <- c(-1, rep(-Inf, times = K), rep(0,   times = K))
>     upper_bounds  <- c( 1, rep( Inf, times = K), rep(Inf, times = K))
>     F_ML  = optim(
>       par = c(psi, Lambda, omega0 ), 
>       fn  = F_criterion,
>       S   = S,
>       K   = K, 
>       method = "L-BFGS-B", 
>       lower  = lower_bounds,
>       upper  = upper_bounds,
>       control = list(maxit = n.iter))
>     
>     # Return T statistic.
>     statistic = (N-1) * F_ML$value
> 
>     # Compute degrees of freedom.
>     DF    = time_points*K*(time_points*K + 1)/2 - (K + 1)
>     
>     # Compute RMSEA.
>     RMSEA = sqrt( max(0, statistic - DF) / (DF*(N-1)) )
>     
>     # Return implied covariance.
>     S_implied <- F_criterion(theta = F_ML$par, S = S, K = K, return_cov = T)
>     
>     # Warnings.
>     if(F_ML$value < 0) warning("Negative discrepancy observed.\nResults are not interpretable")
>     
>     # Return results
>     return(list(
>       "ML_optimizer_result"           = F_ML,
>       T_statistic                     = statistic,
>       RMSEA                           = RMSEA,
>       CF_ar_coef                      = F_ML$par[1],
>       Factor_loadings                 = F_ML$par[2:(K+1)],
>       within_time_point_errorvars     = F_ML$par[(K+2):(2*K+1)],
>       DF                              = DF,
>       "Implied_covariance"            = S_implied,
>       "VAR_original_covariance"       = S
>     ))
>     
>   }

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). On a round of labelled links the rules had not been written from, the three groups were right for 98% of links in the main text (93 of 95) and 90% in reference lists (74 of 82); the labels were made by Claude agents from each link’s evidence, and disputed ones checked against the deposits. Telling this paper’s own deposit from the authors’ earlier one is less certain.

Only the deposits that are this paper’s own are checked. A deposit linked in the text that holds other people’s work (others_data, others_code) or the authors’ earlier work (own_earlier_data, own_earlier_code) is listed in the report, with the reason, but its files are left out of table and kept in table_not_checked: they count toward nothing here (files that do not belong in a repository, naming, READMEs, studies, the traffic light), and code_check, data_check and reproducibility_check, which read table, do not check them either. reproducibility_check still puts the files of theirs that the paper’s code names in the folder the code runs in, as a re-analysis needs the data it re-analyses. When every linked deposit is set aside, the traffic light is “na”. A deposit that is the paper’s own is counted as such when its README, title or description names the paper (its title or DOI).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability).

Provenance, kept so that a TRACE Research Object (TRO) declaration of the run can be written later from a stored result (metacheck #404; the helpers are in R/provenance.R). Only when code was run (execute = TRUE): * run_results$started_at, run_results$ended_at: when each run of a script started and ended (ISO 8601, UTC, milliseconds); NA for a script that was not started. A script run again in a later pass has the times of its last run. A TRO uses them for each trov:TransparentResearchPerformance. * run_results$exit_status: the exit status of the process that ran the script (0 = ended normally); NA when the process did not report one (a time limit, or Docker failing to start the container). * artifacts: one row per file, with stage (deposit: as downloaded from the repository, hashed from the downloaded file; before_run: the run folder just before the first script ran, after metacheck’s own changes, such as rewritten paths and unpacked archives; after_run: only the files the scripts made (status new), changed (changed) or removed (removed), as an unchanged file is the one listed before the run), path (relative to the run folder, as valid UTF-8, a byte of another encoding written as <xx>), size (bytes), sha256, mime_type (by extension, NA when unknown), source (the file’s address in the repository, for deposit). The package libraries metacheck installs in the run folder are left out, as are metacheck’s own files there (a script’s runner, and the statistical output it writes in statistical_output/). Files metacheck itself copied or made between passes (see modifications, output_copied, file_placed) show in after_run too. A TRO uses the rows as trov:ResearchArtifacts and each stage as a trov:ArtifactArrangement. * modifications$sha256_before, modifications$sha256_after: the hash of the changed script as downloaded and as it ran; NA when the script is not at the same path in both (a script made from an R Markdown file). * environment: the system that ran the code (trov:TransparentResearchSystem in a TRO): metacheck_version, started_at, ended_at, host (R version, platform, operating system), sandbox, network_isolated (TRUE only when every Docker run had --network none; the process sandbox does not stop the network), internet, timeout_per_script, total_timeout, python_local (the Python run outside Docker and its version), and docker: runs (for each kind of run, r_run, r_install, python_run, python_install, the image and the docker run arguments, such as --network none, --read-only, --cap-drop ALL, no-new-privileges, the process limit and the memory and processor limits) and images (for each image, its ID and digests from docker image inspect, its creation time and the R and Python versions its environment declares).

run_results$checked says what the run of each script shows about the code, in five groups, so that a script that does not reproduce is kept apart from one the check could not test: ran (it ran to the end); code_error (it did not reproduce: it stopped with an error of the code or the deposit, could not be read, or needs a file the deposit does not hold); dependency (a package or program was not available: a package that could not be installed or was not loaded, a program outside R and Python, a system library, or R crashing in a package’s compiled code); time (it did not finish within the time limit for one script, or was not started because the time for all scripts had run out); and not_checkable (it could not be checked automatically: it needs a person, the internet, a key or another setting of the authors’ computer, one platform such as Google Colab, Windows or OpenSAFELY, more memory than the run allows, a file that was not downloaded, a screen, or a program that runs it, or it is a file of a package of the code that Python runs only as a module of that package). It is NA for files run inside another script, files that are not an analysis, files not read, and a Docker failure. summary_table counts each group (repro_ran_n, repro_code_error_n, repro_dependency_n, repro_time_n, repro_not_checkable_n), and the report’s first sentence gives them. The traffic light reflects the static readiness signals by default; a script in code_error that stopped with an error makes it red, as a script that crashes on its own analysis is a genuine reproduction failure, and a script in one of the other three groups keeps it from being green. Calls that need a screen, which the run does not have (dev.print(), dev.copy2pdf(), dev.copy2eps(), savePlot(), windows(), win.graph(), x11(), quartz(), View()), are replaced before the run by calls that need none, which modifications records as screen_call_replaced. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

1. Introduction

The high covariance amongst observed psychopathologies requires an explanation and has implications for improving mental health interventions (Krueger & Eaton, 2015). The traditional categorical approach, which groups symptoms into discrete disorders, does not provide a satisfactory explanation for this covariance, or "comorbidity" (e.g., Kotov et al., 2017; Lilienfeld & Treadway, 2016). Consequently, other conceptualizations of psychopathology have gained popularity (N. R. Eaton et al., 2023). In the field of psychometrics, the best-known approaches are the common factor (CF) models and the symptom network (SN) models (Borsboom, 2017; Caspi et al., 2014; Cramer et al., 2010).

In their simplest form, CF models explain the symptom co-occurrence with a shared unobserved cause for multiple symptoms, traditionally viewed as a defining trait of the disorder or liability to it (Hopwood et al., 2023). In contrast, SN models explain the co-occurrence with causal effects between symptoms themselves. In this way, the models have a distinct causal interpretation (Marsman et al., 2018). Stated as a counterargument to the CF models (Cramer et al., 2010), SN models dismiss the idea of an underlying shared cause and instead propose that psychopathology is n emergent feature arising from the causal effects between symptoms (Borsboom, 2017). That is, for the CF model the construct we are trying to capture is a common cause, while for the SN model the construct is the collection of symptoms and their mutual relationships (Rhemtulla et al., 2020).

While both of the psychometric approaches are widely used (Hopwood et al., 2023; Robinaugh et al., 2020), concerns remain about whether the theory development has become stagnant: It is often implicitly assumed that the other approach is false, without evidence to justify the made assumption (Fried, 2020). One reason for this is that, despite being distinct in their causal interpretation, CF and SN models cannot, in general, be statistically distinguished from each other in cross-sectional data (Epskamp, Kruis, et al., 2017; Molenaar et al., 2007; but see Van Bork et al., 2021). This hinders direct empirical comparisons: when multiple models fit the data equally well, it becomes inherently difficult to discern which one more accurately captures the underlying psychological processes. Especially, due to the arguable absence of well-defined interventions to evaluate theories in psychological research (Eronen, 2020) the importance of statistical comparisons, and so statistical distinguishability, is of interest.

Statistical distinguishability means the distribution of symptoms being different under substantively distinct models, which are in our case SN and CF models (Spirtes et al., 2000, pp. 59-72). That is, indistinguishable models predict equal distribution for the modelled variables. A weaker version can be defined as distinguishability in covariance. We will mainly use this weaker definition throughout the article, as covariance-based analysis is the most common approach in applied empirical studies of this field and suffices to show the main point, but we will also generalise to distributional distinguishability. From here on we use (in)distinguishability as shorthand for covariance distinguishability, if not otherwise specified.

Contributions and relation to the literature

To date, for the CF and SN models the discussion on distinguishability is limited to crosssectional results indicating indistinguishability in covariance (Molenaar et al., 2007; Van Bork et al., 2021) and cross-sectional item response theory models (Marsman et al., 2018). Stationary dynamic CF models, presented as an autoregressive model in an augmented vectorfoot_0 have been discussed in at least two occasions (Molenaar, 1985; Stock & Watson, 2005). Though, no direct analysis of distinguishability was done in either study. An adjacent topic in time series literature is singular autoregression models (Anderson et al., 2012; Deistler et al., 2010). 3 These models have reduced rank innovation covariance. As we will show below, reduced rank innovation covariance is a necessary but insufficient condition for indistinguishability between a longitudinal SN and a CF model. Moreover, a thorough analysis mindful of contemporaneous psychopathology research would account for i) the data being possibly ordinal and conflated with measurement error, ii) the plausibility of non-normal distributions in psychopathology (Reise et al., 2018; Talkkari & Rosenström, 2024), iii) that psychopathology develops continuously in time (for example, Kuiper & Ryan, 2018; Ryan & Hamaker, 2022) and iv) the psychopathology process being non-stationary (Bringmann, 2021; Schumacher et al., 2023; Siepe et al., 2024). To our knowledge, there is no study that would simultaneously consider these aspects.

Consequently, the main contributions of this article are as follows: We show formal proofs of indistinguishability conditions between SN models and CF models, without assuming stationarity or time-invariance and lending on a geometric intuition about the CF models presented in the psychometric literature (Thurstone, 1931 (Thurstone, , 1934)). While we focus on distinguishability in covariance of the discrete SN models (Epskamp, 2020), we generalize to distinguishability in distribution and to continuous time models. We also argue why the results generalise different kinds of measurement models. Second, we produce a simple method for evaluating distinguishability between the longitudinal SN and CF models. All of the results relate to both time series and panel modelling and so also to contemporaneous psychological methodological literature (Epskamp, 2020; Falkenström et al., 2022).

We begin by analytically showing conditions for indistinguishability in covariance between the longitudinal SN and CF models in a simplistic scenario, which suffices to demonstrate the main, generalisable, idea while capturing central aspects of SN and CF models. We then continue to generalize the results. Finally, we proceed to evaluate the consequences of the analytic results using numeric and empiric examples. Alongside these examples, we give R scripts for evaluating the distinguishability between the longitudinal SN and CF models.

We begin with a commonly applied longitudinal SN model which is the discrete time vector autoregressive model of first order (VAR(1); Epskamp, 2020; Robinaugh et al., 2020). For simplicity, a stationary version of VAR(1) is often used in applications (Bringmann et al., 2013 (Bringmann et al., , 2022;; Robinaugh et al., 2020). However, the time invariance assumption is not aligned with the full SN theory: A hypothesis in the SN approach is that the causal effects contained in 𝐀(𝑡) would change over time as the mental disorder develops (Borsboom, 2017; Schumacher et al., 2023; van de Leemput et al., 2014). Thus, we relax stationarity restrictions on 𝐀(𝑡) for our analysis.

Similarly, we allow time dependence of 𝐙(𝑡), as the innovation covariance might change over time as well (Bringmann et al., 2024). A longitudinal SN model can be extended to include a measurement model, which will be discussed in a separate section after presenting the CF model.

2.5 Measurement models and multilevel structures

In application, the symptom process 𝐗 𝑡 is not observed directly, and so there is a need to include a measurement model that maps the symptoms to the observations 𝐘 𝑡 . Both, the CF and the SN models can be extended to observations via a measurement model with additive and uncorrelated or correlated errors (Epskamp, 2020; McArdle, 2009; Rhemtulla et al., 2020; Schuurman et al., 2015; Schuurman & Hamaker, 2019; Vogelsmeier et al., 2019; Widaman et al., 2010). We clarify the meaning of correlated errors 𝛜 𝑡 of 𝐘 𝑡 and why we can focus our analysis on 𝐗 𝑡.

In many cases, a serially correlated residual structure is considered. For example, Molenaar (1985) discerns the 'aetiological process' from the orthogonal 'residual'. On one hand, it has been argued that correlated residuals are justified as there might be contextual or methodological reasons for associations unique to some indicator due to wording and response format specific to the indicator (Cole et al., 2007; Hoyle, 2023). On the other hand, it has been suggested that residuals to a CF could be a SN (Epskamp, Rhemtulla, et al., 2017). Others do not allow residual dependencies at all (Vogelsmeier et al., 2024; Widaman et al., 2010). To avoid ambiguity, we simply consider the residual to represent measurement artefact unrelated to the symptom process.

To obtain a like-for-like comparison, we analyse the cross-covariance of the symptom process 𝐗 𝑡 .

3.1 Summary

To summarize, longitudinal CF models can be transformed to SN models. For the reverse relationship, the main condition is that the SN model implies symptom process must lie in some space understood as the space defined by the factor loadings.

To see if a SN model is indistinguishable in distribution from a CF model, it suffices to show that it is indistinguishable in covariance from a CF model. When a Markov SN model is indistinguishable from some CF model, the same SN model is indistinguishable from a Markov CF model. The same applies for S-VAR(c) SN models; when such a model is indistinguishable from some CF model, there exists a distributionally indistinguishable CF model with an S-VAR(c) CF process. For CT-VAR models, the same main condition applies. CT models can be either discretized to VAR(1) models or transformed directly.

We make two final notes before the numerical and empirical examples. First, we note that under model indistinguishability the VAR(1) model, S-VAR(c) and CT-VAR are not identified. This is because there are excess dimensions in the model. In other words, there is multicollinearity due to all 𝐾 symptoms being parametrizable as linear transformations of 𝑞 < 𝐾 CFs. This can cause spurious results to occur when the model is near indistinguishable as we will show. Second, whilst multicollinearity is a consequence of indistinguishability, part of the substantive discussion is tied to how factor loadings change, or do not, over time (Fried et al., 2016; Widaman et al., 2010). Loadings that vary abruptly over time might not make sense from a substantive viewpoint, as they make the CF hard to interpret. Therefore, while we generalised the results to arbitrarily changing factor loadings, the time-invariant case might be the most interesting one. We return to our original focus on the time-invariant case in the next section.

That is, we made all of the fitted VAR(1) models identifiable, yet, nearly indistinguishable from a CF model, with which the data was simulated. All VAR(1) model coefficients ended up suggesting sometimes opposite directions of association (negative vs.

positive). Given that the etiological interpretation of a CF model is considerably distinct from these randomly identified coefficient matrices, this should be motivation enough for us to find a way to quantify distinguishability from a CF model in empirical applications.

To proceed, first, we show how cross-covariance matrices can be evaluated for a more thorough analysis of a stationary VAR(1) model. Second, the steps shown in the first part are applied in an empirical example. We conclude by giving quick-to-use functions to conduct the distinguishability analyses in applied research. The main points of the analysis are discussed here, while Supplementary Material 7 provides additional details about technical aspects especially. For the graphical illustrations of SN models we use the R -package 'qgraph' (Epskamp et al., 2012). Specifically, this particular way the SNs are visualized has been promoted as a strength of the SN approach (Bringmann, 2024).

4.1 Analysis of cross-covariance

We first show how distinguishability can be summarized using the eigenvalues (or singular values, discussed below) and eigenvectors of the cross-covariance matrices implied by a VAR(1) model (hereafter cross-covariance, in short). The first step resembles, but is distinct to, what is done in the scree plot method (Cattell, 1966). The intuition is that, if a (one) CF model is true, then we should see a "dominant" component in cross-covariance matrices, indicated by the first eigenvalue remaining large over time increments: 𝐊(𝑡, 𝑡), 𝐊(𝑡 + 1, 𝑡), 𝐊(𝑡 + 2, 𝑡) … 𝐊(𝑇, 𝑡), where 𝑇 is the last time point. The scree plot method is analogous to this, but it is based solely on the within time point covariance, 𝐊(𝑡, 𝑡) matrix. If the cross-covariance is perfectly explained by a CF (Markov, or other), there is only one component and so the first eigenvalue is the only nonzero eigenvalue, which can be ascertained from the IC 1 and IC 2. 7 That is, a one CF model implies rank one (cross-)covariance. If the first eigenvalue is not stably large, additional components may be required to explain the cross-covariance.

Suppose that we see a dominant component in the cross-covariance, and interpret it as a CF. We do not yet know anything about the factor loadings.

We need to analyze if the VAR(1) model produces a stable direction, which could be interpreted as the direction of the factor loadings.

Consequently, we then inspect if the first eigenvector of cross-covariance retains its direction over time increments. If it does, then the largest component has a stable direction over time. If there is no stable direction, the largest component can lose its meaning as representing a consistently interpretable CF.

More precisely, we do this by computing the congruency coefficientfoot_6 (Reise et al., 2000) between the first eigenvectors of subsequent cross-covariance matrices, (𝐊(𝑡 + 1, 𝑡), 𝐊(𝑡 + 2, 𝑡 + 1)), … , (𝐊(𝑇 -1, 𝑇 -2), 𝐊(𝑇, 𝑇 -1)) up to some 𝑇. Essentially, if the congruency coefficient is always exactly 1, the factor loadings would be perfectly time-invariant. If the congruency coefficient is not stably large, e.g., consistently larger than 0.90 (Hurley & Cattell, 1962; Reise et al., 2000; Somma et al., 2019), then the loadings are not time-invariant. We use the absolute value of the congruency, as the CF direction and the eigenvectors are unidentified up to sign. It is worth noting that we use the base R function eigen, which orders eigenvalues in terms of their modulus (absolute value) so that ties are solved by selecting the value with positive weight for the imaginary part first and for ties between real valued eigenvalues the positive eigenvalues come first.

How to select 𝑇 depends on the substantive context and data used. For example, analyses with daily measurements over a few weeks might consider it feasible to include 𝑇 up to the data horizon of few weeks. Alternatively, one might consider 𝑇 up to when all components are near zero so that little variation is left to analyse. 9 This might, however, require computing the crosscovariance well past what is a realistic time horizon for the estimated model. Although we focus here on seeing if there is a single dominant component, we show in Supplementary Material 7 that the choice of 𝑇 can be consequential especially for models where multiple relevant components exist.

In addition, while intuitive for professionals familiar with factor analysis, eigenvalues are more complex for analysis of cross-covariance. Cross-covariance matrices can have negative eigenvalues with imaginary parts. A simpler solution is to use singular values. Singular values, obtained from the singular value decomposition of the cross-covariance, are always non-negative and real valued. They have two important properties. First, for the within time point covariance 𝚺(𝑡), singular values equal eigenvalues. This means that the 'total variance', which is the sum of the eigenvalues of 𝚺(𝑡), is also the sum of the singular values. For cross-covariance matrices, the sum of the singular values is understood as maximal total cross-covariance under arbitrary rotation (Schönemann, 1966). Intuitively, the sum is maximal cross-covariance when we are naïve to factor loading direction(s). This defines meaning of the value 𝜎 𝑗 / ∑ 𝜎 𝑗 𝐾 𝑗=1 as the proportion of maximal total cross-covariance explained by the j-th singular value.

Second, Before showing examples, we summarise with a non-exhaustive list of different scenarios and possible interpretations is: i) If there is a dominant component, and it has a stable direction (both are true), then there is evidence that a CF, with time invariant factor loadings, is (informally put) contained in the VAR(1) model.

ii) If there is a dominant component, but it does not have a stable direction, then the interpretation of this component can be questionable, though in principle would not contradict there being a CF with time-varying factor loadings.

iii) If no dominant component is seen, then there is no support for a CF, at least if we require the CF to be the largest cause of the symptoms. This is independent of the stability of the (first) eigenvector(s).

iv) If a relatively large component is seen, with a stable direction, but also other nonnegligible components appear, the result is inconclusive. Argumentation can be continued using other observations or reasoning.

v) When there are multiple components that are comparable in size, the congruency for the largest direction is insufficient for a clear view about if a CF -like component exists. We give numeric examples and additional details how to analyse the congruencies in these scenarios in Supplementary Material 7.

4.3 Empirical application

To conduct a complete analysis of whether a (one) CF model could be rejected in empirical data, we used ecological momentary assessment (EMA) data freely available from the supplementary materials of Fried et al. (2022). The data included 79 subjects. For each subject, a two-week period was sampled. Each day, four assessments were taken. Three subjects were not included due to having less than 50 total assessments (distinctively fewer than all other subjects), and one subject was not included due to subsequent missing values over a week. All observed variables were truncated to four categories, instead of five, due to low cell counts in the last category. For a more detailed view of the data, we refer to Fried et al. (2022).

In two separate analyses, with two distinct data sets, a latent VAR(1) model was estimated.

While the models were estimated by including a measurement model, as well as time-of-day effects and multilevel structure (see below), the results themselves solely relate to the latent VAR(1). This VAR(1) model was analysed for indistinguishability using the methods constructed above. Hence, the results rely on the assumption that the latent VAR(1) model is estimated correctly.

We lay out how we estimated the model: The model was specified as a Stan (Carpenter et al., 2017) model and implemented in the cmdstanr package (Gabry et al., 2025). Markov Chain Monte Carlo estimation was run with 4 chains, 4000 iterations per chain. In both analyses discussed below, the chains converged well, and no signs of divergent paths were seen. The model has the following important assumptions and properties. First, the symptoms must behave as a process with the Markov property. Second, to reflect our prior belief, we set a weak prior distribution for the innovation and coefficient matrices, which is centred around a VAR(1) indistinguishable from a CF model.

Third, for the observed ordinal variables, a probit measurement model was used (e.g., Samejima, 2010; see measurement model section above).

Fourth, missingness in the data was handled by including unobserved responses in the data as parameters in the model. Fifth, multilevel structure was accounted for by allowing individuals to have their own subject-specific intercept terms. Sixth, no detrending was done. Seventh, we also included a time-of-day variable (morning, midday, noon, evening) as a covariate to model systematic daily changes in the symptoms. This variable was allowed to affect each symptom differently. A sensitivity analysis was conducted with prior parameterisation that does not favour a CF model. The full Stan model specifications can be found online (https://osf.io/hu7g9/files/osfstorage?view_only=184ae735527d4616ae96af5c0201e1c8 ) and the mathematical definitions in Supplementary Material 8. In the first analysis, we restricted the observed variables to a set, which would plausibly be from an "anxiety liability" CF (difficulties in relaxing, worry, nervousness; see Fried et al., 2022).

In Figure 4, the absolute values of eigenvalues and congruency coefficients are shown for the posterior mean VAR(1) model. The analysis suggests that a single component dominates the cross-covariance matrices over time-increments, and it has a stable direction. For all posterior draws, the first singular value explained a larger proportion than 0.90 over all latent VAR(1) implied cross-covariance. Similarly, for all posterior draws, all the congruency coefficients between subsequent first eigenvectors were larger than 0.90. Taken together, there is strong support for interpreting the estimated VAR(1) as a CF model.

We then repeated the analysis for a larger set of observed variables (difficulties in relaxing, worry, nervousness, and, in addition, tiredness, hunger, feeling alone, feeling angry; Fried et al., 2022). Since this set contains more variables, and arguably variables not relatable to anxiety liability alone, it is less likely to produce a VAR(1) model that would behave as a Markov CF model. Indeed, as seen in Figure 5, though the first component is distinctively large, two more non-zero components appear through the cross-covariance matrices over time increments.

For all the posterior draws, the first singular value never explained more than 0.90 over all latent VAR(1) implied cross-covariance. However, for all the posterior draws, the congruency coefficients between subsequent first eigenvectors were larger than 0.90. Also note that feelings of hunger and tiredness were largely explained by time of day, hence the lower innovation covariance. Especially since the analysis was done with the prior belief that the VAR(1) would be indistinguishable, which was explicitly stated with prior distributions for the parameters, we conclude that a single CF is not sufficient to explain the cross-covariance implied by this model.

Yet it would be an overstatement to completely reject a CF being involved, especially since the first component is distinctively large and has a stable direction. Sensitivity analyses with another prior parameterisation not favouring the CF model led to the same conclusion for both the first and the second analysis. The sensitivity analyses, and plots with time increments up to 50, are found in Supplementary Material 8, sensitivity analyses -section.

4.4 Conclusion of numerical and empirical examples

Using the cross-covariances implied by an estimated stationary VAR(1) SN model, we can assess its properties via decomposing the cross-covariance. This is similar to a scree plot but generalized to cross-covariance (not just within time point covariance) and is based on an estimated model, while the scree plot uses empirical covariance. Since we are using model implied cross-covariance(s), we have the possibility to use an explicit measurement model for the ordinal items, to account for multilevel structures and other variables alongside other possibilities. The downside of this is that this approach relies on a correctly specified model and an identifiable estimation scheme.

We used a heuristic reference of 0.90 for the first singular value divided by the sum of all singular values, and 0.90 for congruency. However, historically cut-off values suggested (and simultaneously criticized) by methodologists have caused problems in progression of research (Hayduk et al., 2007; Hu & Bentler, 1999; Lakens, 2021; McNeish & Wolf, 2023; Xia & Yang, 2019). Thus, we do not recommend any specific cut-off here. Similar remarks can be made about null hypothesis testing (Hayduk et al., 2007), but see Cragg & Donald (1997) or Robin & Smith (2000) for relevant statistical testing. Instead, our focus is on better understanding of the models that we fit to data and in model comparison.

We conclude this section by providing the functions used to compute the analyses for crosscovariance matrices, as done above. The function var_ccov_decompose (https://osf.io/hu7g9/files/dra4g?view_only=184ae735527d4616ae96af5c0201e1c8 ) takes as its arguments a stationary coefficient and an innovation matrix. The analysis should not take more than a few seconds. 13 The results and related visualizations include eigenvalues (ignoring imaginary parts thereof), singular values of the cross-covariance matrices and the congruency coefficients of the eigenvectors of the cross-covariance matrices.

5. Discussion

A strength of psychometric models in psychopathology research is that we can formally analyze their theoretical predictions to guide empirical research, theory development, and, eventually, improve mental health interventions (Bringmann et al., 2022; Krueger & Eaton, 2015; Ryan & Hamaker, 2022). Building upon formal analysis, we made two separate contributions to this field of research. First, we mathematically, numerically, and empirically showed that longitudinal CF models with the Markov property can be related to a SN model that is indistinguishable in distribution. Further, we demonstrated how to use this fact in practice. As longitudinal and time series data and analyses are becoming more prevalent (Bringmann, 2024; Robinaugh et al., 13 The analysis ran for 270 ms on a single core of Intel(R) Core(TM) Ultra 7 165H, 1400 Mhz.

2020), the results carry particular significance: They underscore the importance of carefully evaluating the (in)distinguishability between the fitted SN and CF models.

Since a large class of longitudinal CF models can be presented as SN models, there is not always a need to perform completely separate analyses for comparisons. Given the overlap, it suffices to derive the implied cross-covariance from one model, such as a VAR(1) (or continuous time VAR) model, and analyze to what extent this cross-covariance is incompatible with a CF model.

This can shorten analysis, especially when the research aim is not focused on theoretical comparison.

The methods provided above offer a quick solution to check this assumption, as they only require the user to input a stationary VAR(1) model. This adds to known possibilities (Schumacher et al., 2024) on how to improve applied SN analysis. If a CF model seems plausible, more rigorous testing and model comparisons can be done. Nuanced approaches, with case-by-case consideration of substantive theory, are likely needed when no clear distinction is seen.

We mention some further applied models and data structures for which our analytic results are applicable: First, the analytic results generalize to latent VAR(1) SN models in addition to observed ones. That is, our results and tools are applicable also in the possible future of SN analyses where measurement models for SNs are included (Bringmann et al., 2022; Epskamp, Rhemtulla, et al., 2017; Schumacher et al., 2024). Second, though the analytic results were shown from a 𝑁 = 1 perspective, they generalize to multilevel models with multiple subjects (as was done in the 4.3 Empirical application -section). The same linear algebra and statistics apply for the coefficient and innovation covariance matrices, independent of the level of analysis -as long as there is a VAR(1) ingrained in a model 14 that one is willing to interpret, then using methods given here is feasible. For a CT-VAR model, discretization can be a pragmatic choice for stationary models, as shown in Supplementary Material 6. Finally, even if studying distinguishability would not be of interest, analysis of cross-covariance matrices can still show how the symptoms behave over time in a SN. E.g., informally put, we could analyze to what extent the SN is oriented around a certain direction(s) (component(s)). Methods given here can be useful for this purpose as well.

6. Limitations and future directions

The models presented here could be extended in various directions, and reanalyzed if necessary.

For example, assumptions driven by theory, or a specific hypothesis about what kind of changes over time are expected for a SN, such as critical transitions (van de Leemput et al., 2014) or a trait-like time independent CF (Cole, 2012; Hoffart & Johnson, 2020), will likely improve distinguishability.

All the details that require consideration in empirical applications cannot be discussed in this paper, or any single paper (Bastiaansen et al., 2020; Bulteel et al., 2016; Durlauf & Phillips, 1988; Epskamp et al., 2018; Hamaker et al., 2018; Ryan et al., 2025). The applicability of the results and methods shown here depend on having a correctly defined and estimable model. If the symptom process is not correctly estimated, there is no solid basis for analysing further how distinct theoretical models can be distinguished based on it.

While the analytic results are applicable to time-varying models, the numeric-estimation functions given here are not generalized for time-varying models. Thus, future extensions of the numeric algorithms might be needed, as time-varying modeling becomes more common in applied SN modeling (Schumacher et al., 2024). Second, the methods given here are meant to give a minimal check for disputing a CF model. Using them does not mean that more rigorous analyses would not be ultimately needed as research progresses. Third, analysis of eigenvalues and singular values and -vectors of cross-covariance matrices does not have a fixed theorydriven "cut-off" against which one would base decisions. Due to the non-invertibility of low rank implied crosscovariances, a singularity is encountered in the discrepancy function required for computing RMSEA accurately. Thus, simulation-based methods were tested, but they were not stable enough for reliable use. These experimental methods are given in the open science framework project, alongside the methods suggested for use.

7. Conclusions

Estimated SN models that seemingly have a complex structure can be indistinguishable from a common factor model. Though this is a problem, it simultaneously leads to easily applicable methods for quantifying between-theory differences, which in turn aid theory development in the long run. We suggest using the methods provided here as a minimal check before coefficients of stationary longitudinal SN models are interpreted, and also when interested in comparing CF and SN theories.

Comments on model definition and estimation

Above, we provide an example of how to estimate a possible SN (as a VAR(1)), which can further be inspected for distinguishability from a Markov CF. It additionally provides a new prior parameterization, motivated by the indistinguishability conditions (and Supplementary Material 3). It favours a Markov CF model, but as seen in the 7-symptom scenario, it can deviate from one. It is presented here to demonstrate possibilities in Bayesian estimation that naturally follow from the analytical results. That is, if one has the prior belief that a CF is the true cause, a new opportunity presents itself.

Second, we note that there is no general estimation scheme for longitudinal SNs. This is likely partly because the modelling needs to be customized in a case-by-case manner: It depends on the observed variables, on whether the time increments are equidistant or not, how the multilevel structure should be modelled, non-convergence, high computational demand, long estimation times, and so forth. Bayesian Markov Chain Monte Carlo procedure with RStan is suitable for this purpose, due to its flexibility.

Third, we have defined the multilevel structure for intercepts 𝒄 + 𝒂 𝑖 . We did not define a multilevel structure for the 𝐀 or 𝐋 matrix. This is because of quickly increasing model parameters, not supported by limited data. In future empirical applications, these issues might need to be addressed.
