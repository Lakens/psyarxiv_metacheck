If specified by the user, it also uses a large language model (LLM) to extract information reported in power analyses, including the statistical test, sample size, alpha level, desired level of power, and magnitude and type of effect size.

The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. Without the use of an LLM, the module uses regular expressions to classify the power analysis as a-priori, sensitivity or post-hoc. With the use of an LLM, it checks if the power analysis is reported with all required information.

The regular expressions can miss power analyses, or fail to classify them correctly. The type of power analysis is often difficult to classify, which can easily be solved by explicitly specifying the type of power analysis as ‘a-priori’, ‘sensitivity’, or ‘post-hoc’. Note that ‘post-hoc’ or ‘observed’ power is rarely useful. The LLM can fail to identify information in the paper, and will not have access to information in paragraphs in the paper other than those that contain the word ‘power’. This package was validated by the Metacheck team on articles in Psychological Science.

How StatCheck works

Check consistency of p-values and test statistics

The Statcheck module runs Statcheck. Statcheck searches for regular expressions that match a predefined pattern, and identifies APA reported statistical tests. More information on the package can be found at https://github.com/cran/statcheck. The module only returns Statcheck results for t-tests and F-tests, as these are the only tests which have been validated, see https://osf.io/preprints/psyarxiv/tcxaj_v1/.

Statcheck was developed by Michèle Nuijten and Sascha Epskamp.

Statcheck considers p = 0.000 an error, as you should report p < 0.001. Furthermore, p < 0.03 is an error if the p-value was 0.031, and one should simply report exact p-values (p = 0.031). Statcheck might miss one-sided tests, and falsely assume the p-value is incorrect. For more information, see StatCheck.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.) or reported as exactly zero (e.g., p = .000).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

This module was developed by Lisa DeBruine and Daniel Lakens

Read more in the metacheck manual.

Version 0.4.4.3 reported 419 p-values as imprecise, 388 of them correctly (93%), and missed 50 (89% found). How Non-Significant P Value Check works

This module checks for imprecisely reported p values. If p > .05 is detected, it warns for misinterpretations.

The nonsignificant p-value check searches for regular expressions that match a predefined pattern. The module identifies all p-values in a manuscript and selects those that are not reported to be smaller than or equal to 0.05. It returns all sentences containing non-significant p-values.

In the future, the Metacheck team aims to incorporate a machine learning classifier to only return sentences likely to contain misinterpretations. If you want to help to improve the module, reach out to the Metacheck development team.

A p-value next to words that state a threshold is kept, because such sentences often report a result against that level (“not significant at the conventional threshold (p = .054)”).

How Codebook Check works

This module checks whether the data columns in a repository are documented in a codebook or README. It locates codebook/readme files, extracts the variable definitions they contain, matches those definitions against the data columns extracted by data_check, and reports documentation coverage: how many data columns are documented, and which documented variables are never used.

The Codebook Check module consumes the columns and file classification produced by data_check (and, transitively, repo_check). Files classified as codebook or readme are parsed with parse_codebook(), which reads structured tables (CSV/TSV/Excel with a variable-name column and a label column), embedded labels in haven files (SPSS/Stata/SAS), and plain text from rich-text formats (docx/pdf/rtf/odt). Embedded haven labels from data files are also harvested directly.

Each data column is then matched against the parsed variable definitions with match_column_labels(), using normalised-name matching with experiment-group scoping, haven-label priority, and rule-based label-equivalence merging.

Beyond the variable label, the module harvests the DDI-style per-variable properties a source supplies: the value labels / code list (the 1=“Strongly disagree”…5=“Strongly agree” mapping — from SPSS/Stata value labels and from a codebook “values”/“coding” column), the missing-value scheme (which codes denote missingness, from haven declared missings and labels that read as “refused”/“n/a”), and question text and columns when present. These are carried onto the matched data columns and exported into the Psych-DS variableMeasured (as a schema.org code list plus namespaced metacheck: fields).

The module defaults to rules-only when llm_use(FALSE). When llm_use(TRUE), three optional LLM tiers run: parsing unstructured codebook text that the rules could not handle, fuzzy-matching still-unlabelled columns to still-unmatched codebook variables, and merging conflicting label definitions into a single canonical label.

How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

Listing a repository’s files never requires an API key, but some hosts answer faster or more completely with one: OSF allows 100 requests/hour unauthenticated versus 10,000/day with a token (see [osf_pat()]), and Dryad enforces a strict per-IP daily quota on repeated listing (see cache below). Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Since this module only lists files and never downloads their contents itself, that limitation applies to data_check and code_check (which do download content), not here – see their own documentation.

When a linked OSF page is a registration, its registered_from project (the one it was registered from, which the manuscript itself may never link directly) is also checked: if that project is public its files are listed under its own URL, and if it is closed or otherwise inaccessible the report flags it explicitly, since some registrations only describe their content rather than mirroring it.

Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). On a round of labelled links the rules had not been written from, the three groups were right for 98% of links in the main text (93 of 95) and 90% in reference lists (74 of 82); the labels were made by Claude agents from each link’s evidence, and disputed ones checked against the deposits. Telling this paper’s own deposit from the authors’ earlier one is less certain.

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

How Replication Check works

This module checks references and warns for citations of original studies for which replication or reproduction studies exist in the FLoRA database.

The Replication Check module compares the reference list against studies in the FLoRA (FORRT Library of Replication Attempts) database based on the DOI. If a study in the database is found, a reminder is provided that a replication or reproduction of the original study exists, and should be cited. No reminder is given when the paper already cites that replication or reproduction (matched by its DOI).

The module requires that the reference has a DOI: the DOI in the paper’s reference list, or one looked up with add_bib_match() before the module runs (see ref_table()). References without a DOI are not checked.

It is possible the original study was cited for other reasons than the empirical claim tested, or that the replication/reproduction in the FLoRA database is for only one of the studies in the paper, and not the study the authors discuss.

The database can be manually updated with the FLoRA_update() function. For more information, see https://forrt.org/FLoRA/.

Introduction and Theoretical Background

The Nomological Network

The nomological network of a measurement instrument describes the pattern of relationships between scores of this instrument and scores of other measurement tools. It can be formalized as a vector of bivariate correlations between the test score for the construct under scrutiny and scores of external variables. The variables shaping the empirical nomological network, in turn, can be measured with diverse data sources, such as selfreported, behavioral, physiological, or other-reported information (Campbell & Fiske, 1959; Cronbach & Meehl, 1955). Constructing a nomological network for a newly devised or reevaluated measure has been the standard procedure for the investigation of evidence in favor of or against construct validity because the nomological network reflects an indicator of what the measurement instrument under scrutiny actually assesses. If the test score of the measurement instrument manifests a set of theoretically expected associations with the external variables within the nomological network, it is usually inferred that the target measure assesses what it purports to (American Educational Research Association et al., 2014; Cronbach & Meehl, 1955).

Similarity Between Nomological Networks as an Index of Construct Redundancy

Mere investigations of isolated bivariate relations with external variables, however, are associated with the risk to establish a landscape of redundant or insufficiently validated measures when researchers frequently pay little attention to overlaps with already existing constructs and measures (Hanfstingl et al., 2025; Lawson & Robins, 2021). More specifically, ostensibly alternative measures for a construct under scrutiny often fail to tap into the same concept, or measures purported to tap into a new construct in fact repackage existing concepts. Considering whether psychometrical scales actually assess what they purport to, systematic investigations of such jingle fallacies (i.e., measures/constructs intended to tap into the same concept in fact measure different constructs [Thorndike, 1904]) and jangle fallacies (i.e., measures/constructs with different measurement intentions in fact assess the same concepts [Kelley, 1927]) have commenced only recently (Hanfstingl et al., 2025).

In these analyses, comparisons between empirical sets of correlations (hereafter correlation profiles) take a central role beyond the analyses of mere intercorrelations. That is, high (low) correlations between potentially jingled/jangled scores do not necessarily cause identical (different) correlation profiles involving external variables (Lawson & Robins, 2021). Instead, the degree to which two scores are correlated only determines the range of differences between the correlations of these scores with other variables (Yule, 1922). For instance, Gonzalez et al. (2021) demonstrated that, given an almost perfect correlation (r12 = .998) between two variables (say, two extraversion scales) and a correlation between the first variable with an external variable (say, frequency of experiencing positive mood) of rY, X1 = .30, the second variable can yield correlations with the external variable within a range between .24 and .36. If, however, the two variables (again, two extraversion scales) were correlated at a more realistic yet still high level, such as r12 = .70, and the first was correlated with the external variable at rY, X1 = .30, possible correlations between the second variable and the external variable would range from -.47 to .89. Finding a set of similar relations of the two variables with a reasonable set of external variables, despite the hypothetical range of possible correlations, would pose an indicator of redundancy (Campbell & Fiske, 1959; Cronbach & Meehl, 1955; Gonzalez et al., 2021). Instead of inspecting the mere correlation between two measures, it is recommended to compare the profiles of correlations with external variables.

Therein, the coefficients within the correlation profiles of measures for the same construct should be similar, whereas the coefficients in the correlation profiles of measures for disparate constructs should not (Blötner, 2025; Lawson & Robins, 2021; Thielmann & Hilbig, 2019).

Evaluating the Similarity between Correlation Profiles

To address the question of whether two or more correlation profiles are (almost) identical, existing methodological guidelines recommend correlation difference tests for dependent correlations (Blötner, 2025; Gonzalez et al., 2021; Thielmann & Hilbig, 2019).

According to the concomitant logic, two scores reflect the same construct if they exhibit, by and large, equivalent correlations with a reasonable set of external variables. This approach is related to several problems, however, that limit its utility to gauge the equivalence vis-à-vis distinctiveness of correlation profiles. First, the statistical power to detect an existing correlation difference depends on a plethora of aspects, such as the sample size, the minimum difference between the correlations above which one assumes a substantial difference, the intercorrelation of the compared scores, and the desired α-level (see Blötner, 2025, for a pertinent recommendation for power analyses in the context of examinations of assumed jingle and jangle fallacies). In this regard, Blötner (2025) illustrated that methodologically sound examinations of jingle and jangle fallacies require sample sizes that are frequently not achieved in published research. Second, but relatedly, it is barely possible to propose a rule of thumb for a critical ratio of significant versus non-significant correlation differences above which construct redundancy is assumed to hold and below which construct uniqueness is assumed. More specifically, it stands to reason that it is hardly possible to compare two conceptually unrelated endeavors to examine particular jangle fallacies (Blötner, 2025).

Alternative guidelines (e.g., Blötner, 2025; Lawson & Robins, 2021; Thielmann & Hilbig, 2019), thus, recommend combined approaches that supplement examinations of correlation differences with a descriptive overall index of the similarity between two correlation profiles.

Determinants of Profile Similarity

Generally speaking, any kind of profile can be described through three parameterselevation, scatter, and shape (Cronbach & Gleser, 1953). Elevation and scatter denote the central tendency and the dispersion of the coefficients within a profile, respectively, such as the mean and the variance across the elements. Shape reflects the pattern of peaks and valleys of the trajectory of the elements of a profile across the utilized correlates, but it is usually not quantified through a comprehensive index. An index that quantifies the similarity between correlation profiles should acknowledge the three aforementioned characteristics. At first glance, the most straightforward way to quantify the similarity between two vectors of correlation coefficients with a single index would be computing the bivariate correlation between them (e.g., Pearson's product-moment correlation r or Spearman's rank correlation ρ). These indices, however, quantify the (dis)similarity of the rank order, not the elementwise correspondence between the elements of the vectors themselves. For instance, consider the correlation profiles X = [.05, .19, .57, .34] and X' = [.35, .49, .87, .64]. Each element of X' reflects an element from X to which a constant of .30 was added. Since the rank order remains identical if a constant is added, bivariate correlations between X and X' would indicate perfect similarity (e.g., r = 1.00)-despite an obvious lack of element-wise correspondence. Accordingly, bivariate correlation coefficients are maximally sensitive to shape (dis)similarity but insensitive to scatter and/or elevation (dis)similarity (Furr, 2010), rendering them unsuitable to acknowledge shape, scatter, and elevation simultaneously.

Consistent with earlier research on the agreement between the correlation profiles of different measures (e.g., Blötner, 2025; Gonzalez et al., 2021; Thielmann & Hilbig, 2019), the similarity between correlation profiles (or profile similarity) is herein understood as the overall degree of element-wise correspondence between correlation profiles. In turn, correlation profiles are deemed different if-by and large-considerable element-wise discrepancies occur. Accordingly, to justify conclusions about the redundancy of correlation profiles due to their overall similarity (Blötner, 2025; Gonzalez et al., 2021; Thielmann & Hilbig, 2019), (almost equal) magnitudes of elevation and scatter as well as (almost equal) visual shapes are required (Cronbach & Gleser, 1953).

The Double-Entry Intraclass Correlation and Its Limitations

An index recommended in the aforementioned guidelines is the Double-Entry Intraclass Correlation (ICCDE; McCrae, 2008). For its computation, the vector of the k elements of the first profile (e.g., A = [a1, a2, a3, …, ak]) is appended to the vector of the k elements of the second profile (B = [b1, b2, b3, …, bk]) and vice versa. The ICCDE reflects the bivariate correlation between the double-entered vectors AB = [a1, a2, a3, …, ak, b1, b2, b3, …, bk] and BA = [b1, b2, b3, …, bk, a1, a2, a3, …, ak], rAB, BA (McCrae, 2008). An ICCDE of +1 is usually interpreted as perfect agreement, an ICCDE of -1 as perfect inverse agreement, and an ICCDE of 0 as absence of systematic correspondence. Whether inverse agreement should be viewed as a form of similarity or dissimilarity depends on the substantive research question.

Earlier studies recommended general cutoffs, such as |ICCDE| ≥ .60 (Lawson & Robins, 2021) or .80 (Thielmann & Hilbig, 2019), whereas many published studies applied a cutoff as high as |ICCDE| > .90 as an indicator of construct redundancy (e.g., Baerg MacDonald & Schermer, 2025; Blötner & Mokros, 2023; Hart et al., 2023; Hyatt et al., 2020; Miller et al., 2017; Mund et al., 2023; Samuel et al., 2012; Somma et al., 2021; Vize et al., 2021; see Blötner, 2025, for an overview). Because the ICCDE is mathematically related to the correlation between profiles, its is often heavily influenced by shape similarity (Furr, 2010).

Consequently, when within-profile variance becomes small, variation in shape may exert a disproportionately large influence on the resulting ICCDE. Thus, variance restrictions have a strong impact on the magnitude of the ICCDE and concomitant evaluations of construct overlaps in the sense of jingle and jangle fallacies. Moreover, the stronger the levels of scatter of the compared profiles differ, the higher the ICCDE. Whether such behavior is desirable depends on one's definition of profile similarity. Last, Furr (2010) demonstrated that the magnitude of the ICCDE is largely driven by the bivariate correlation between the profiles under scrutiny. Due to the mathematical interdependence, the ICCDE is sensitive to essentially the same determinants as the bivariate correlation coefficient r.

The aforementioned limitations have important implications for the fidelity of the ICCDE, as represented through the breadth of the corresponding confidence intervals, even in large samples: For instance, Blötner (2025) proposed a bootstrapping approach to estimating confidence intervals around empirically observed ICCDEs. In a simulated dataset consisting of four normally distributed random variables (n = 1,000), an ICCDE as large as -.662 was observed for the profile similarity between two particular variables. The 95% confidence interval around this ICCDE, however, ranged from -.999 to .398. Therefore, the off-diagonal elements of the correlation matrices produced across the iterations from the bootstrapping procedure can be expected to be narrowly dispersed around r = 0, which also suggests low levels of scatter in the analyzed vectors of correlations. As a result, random variations of shape (dis)similarity occurred across the iterations, while scatter and elevation were almost constant across iterations, further suggesting that the element-wise comparisons between the correlation profiles elicited only small numerical differences. The findings suggest that, particularly under low-scatter conditions, ICCDE values may be dominated by shape similarity despite also being mathematically influenced by elevation and scatter.

Since each element of a correlation profile contributes to the nomological network of a measure (Campbell & Fiske, 1959; Cronbach & Meehl, 1955), dissimilarities in the patterns of correlations observed for to-be-compared measures concerning scatter, elevation, and shape also pose indicators of differential construct validity. Differential patterns of correlations with external variables, in turn, underscore the absence of a jangle fallacy or the existence of a jingle fallacy (Blötner, 2025; Gonzalez et al., 2021; Lawson & Robins, 2021). To reliably make such conclusions, researchers require a principled framework for evaluating overall agreement between profiles.

Objectives

The present study does not seek to provide a definitive demonstration that the ICCDE is generally unsuitable as an index of profile similarity. Rather, the goal is to specifically examine how the ICCDE behaves when applied to correlation profiles, a context in which the coefficients are bounded, mathematically constrained, and often exhibit relatively low levels of within-profile variability. In this vein, Furr (2010) demonstrated analytically that the ICCDE reflects a combination of shape, elevation, and scatter similarity and illustrated how these characteristics affect the coefficient, but he applied these considerations to profiles of test scores that can theoretically take on all possible values between -∞ and +∞. The present manuscript does not argue that correlation profiles require an entirely new theory of profile similarity. Rather, the practical importance of the problem differs because correlation profiles frequently exhibit substantially lower within-profile variance than test profiles consisting of personality, ability, or clinical characteristics. Thus, correlation profiles constitute a domain in which previously identified weaknesses of the ICCDE may be particularly likely to occur.

The present study therefore should not be viewed as a replacement for these earlier critiques, but rather as an extension of them to the specific context of nomological network comparisons. More specifically, the contribution of the present study is threefold.

First, it investigates situations in which shape, scatter, and elevation similarities vary simultaneously rather than in isolation. Second, it examines the behavior of the ICCDE under constraints imposed by correlation coefficients and the rule by Yule (1922) (see Equation 1) that determines the possible range of coefficients to be observed in the manipulated profile (denoted as rY, X2), given the correlation between the variables for which the correlation profiles were tested (i.e., not the correlation between the profiles; denoted as r12) and the magnitude of the coefficients in the reference profile (denoted as rY, X1). That is, unlike the unbounded metric of test scores from psychological measures, the metric of correlation profiles imposes a certain amount of variance restriction when applied to the ICCDE.

Third, this research evaluates the sensitivity of the index under conditions of both substantial and very low levels of within-profile variability. Thus, the emphasis of the present work is not the discovery of a previously unknown limitation, but a systematic illustration of how known limitations manifest when the object of interest is a profile of correlations.

Method

Sample of Simulated Examples

Substantial Levels of Scatter Within Profiles

To systematically examine the effects of (dis)similar shapes, scatters, and elevations on the direction and magnitude of the ICCDE, eight simulation conditions were created. Each of these conditions entails a combination of equal/different shapes, equal/different scatters, and equal/different elevations. For each condition, 10,000 iterations were carried out in which a reference profile was created by randomly drawing 30 numbers from a uniform distribution with a minimum of -.70 and a maximum of .70 (reflecting the correlation coefficients). This range was selected because it was deemed representative of plausible correlation coefficients usually observed in construct validation studies. Furthermore, this range warrants substantial levels of scatter within the simulated correlation profiles. The number of elements was chosen because it was deemed realistic for an extensive construct validation study. A number of 10,000 iterations was chosen to obtain stable estimates of the coefficient distributions across simulations that comply with the formula by Yule (1922).

To introduce dissimilarities concerning shape, and/or scatter, and/or elevation, different mechanisms of data manipulation were applied to the reference profile to derive the corresponding profile to which the reference profile is compared. More specifically, random resampling of the order of the elements of the reference profile was used to obtain shape dissimilarity. Centering of the elements of the reference profile, along with multiplication with .50 and adding the mean of the reference profile, was utilized to generate scatter dissimilarity. More specifically, the standard deviation of the elements of the manipulated profile was half the standard deviation of the reference profile. In this regard, Furr (2010) proposed a ratio of the scatters of the compared profiles as high as 2 as substantial. Last, elevation dissimilarity was obtained by adding .30 to each element of the reference profile. In this regard, the guideline for effect sizes in personality research by Gignac and Szodorai (2016) treated correlations as high as .30 as a large effect size. To obtain two or more aspects of dissimilarity, the aforementioned mechanisms of data manipulation were combined.

Low Scatter

Furthermore, the impact of the scatters of the correlation profiles on the magnitude of the indices of profile similarity (Furr, 2010; Hilbig et al., 2021) was evaluated in detail. Akin to the mode of the aforementioned simulations with substantial levels of scatter, a reference profile was created by drawing 30 random numbers from a uniform distribution, but the range of the uniform distribution was restricted to numbers between -.05 and .05. To afford the eight simulation conditions, the same mechanisms of data manipulations were applied as in the analyses of correlation profiles with substantial levels of scatter. Across both sets of simulations, a test loop was implemented to ensure that the profiles in all iterations of both sets of simulations complied with the formula by Yule (1922).

In the simulations, the correlation between the variables was set to r12 = .50. This level of intercorrelation roughly corresponds to the correlations between measures for which jangle fallacies have been tested recently (e.g., Baerg MacDonald & Schermer, 2025; Blötner & Mokros, 2023; Hart et al., 2023; Hyatt et al., 2020; Lawson & Robins, 2021; Miller et al., 2017; Mund et al., 2023; Samuel et al., 2012; Somma et al., 2021). Moreover, it enables a sufficiently broad range of correlations in the manipulated profiles as per the formula by Yule (1922). The RMarkdown file in the Open Science Framework supplement describes the procedures employed to manipulate shape, elevation, and scatter (dis)similarities in both analyses (https://osf.io/9pjkd/overview?view_only=9a42e9981fbf411794a37b756db5bf75). Furthermore, the file provides information about the simulation results as well as the acceptance rates of the test to determine whether the manipulated profiles comply with the formula by Yule (1922).

Analytical Strategy

The corresponding pairs of simulated correlation profiles per iteration and condition were subjected to analyses of profile similarity using the bivariate correlation coefficient r and the ICCDE. The 95% confidence intervals across the 10,000 iterations per condition and coefficient were computed to determine the breadth of the distributions of coefficients. The analyses were conducted with the R package iccde (Blötner & Grosz, 2026). The bivariate correlation coefficient r was computed to specifically demonstrate its shortcomings when shape (dis)similarity exists.

Another interesting finding refers to the heterogeneity of the detected coefficients across iterations in the conditions with shape dissimilarity. More specifically, the magnitude of the ICCDE varied considerably more strongly across iterations in the conditions with different shapes than in the conditions with equal shape (see the 95% confidence intervals in Table 1). Note in this regard the complexities concomitant with the creation of correlation profiles for the conditions targeting different shapes. That is, the correlation profiles that differed from the reference profile in terms of shape did not comply with the formula by Yule (1922) in many iterations, necessitating a large number of new draws. The corresponding acceptance rates ranged from 0.3 to 13%, while the acceptance rates for the conditions with equal shape ranged from 59 to 100% (see the supplemental RMarkdown file for the concrete acceptance rates and the required numbers of draws to provide pairs of correlation profiles that complied with the formula by Yule, 1922).

Low Scatter

Across the eight conditions with low levels of scatter within the reference profile, conclusions derived from the ICCDEs ranged from virtually perfectly antagonistic profiles (ICCDE = -.98) to high yet imperfect agreement, ICCDE = .80. Note in this regard that the range of simulated correlation coefficients in the reference profile was very narrow by design (-.05 ≤ rs ≤ .05), suggesting only low levels of within-profile variability and high levels of factual element-wise similarity in all four conditions with equal scatter. Furthermore, in the conditions with equal levels of elevation, the element-wise differences between the compared profiles are, by design, very small, while substantial element-wise differences existed in the conditions with different levels of elevation, obtained by shifting each coefficient by Δr = .30.

Under the conceptualization of profile similarity adopted herein, one might expect an index of profile similarity based on the conceptualization adopted in the present article to indicate almost perfect similarity (≈ 1.00) if the levels of elevations were similar and to indicate far from perfect agreement if the absolute levels of elevation differed (<< 1.00). The ICCDE did, however, elicit the reversed pattern such that it was high if levels of elevation differed and low if levels of elevation agreed. Interestingly, the confidence interval of the ICCDE was comparatively broad if shape dissimilarity was combined with elevation similarity, regardless of whether the scatters were similar or different. Unlike in the simulation of correlation profiles with substantial levels of scatter, the simulation of correlation profiles with low levels of scatter obtained acceptance rates of 100% in all conditions. That is, all iterations produced pairs of correlation profiles that complied with the formula by Yule (1922).

Discussion

Many studies that sought to evaluate the similarity between correlation profiles observed for specific psychological measures or constructs relied on the ICCDE as a measure of profile similarity (e.g., Baerg MacDonald & Schermer, 2025; Blötner & Mokros, 2023; Hart et al., 2023; Hyatt et al., 2020; Lawson & Robins, 2021; Miller et al., 2017; Mund et al., 2023; Samuel et al., 2012; Somma et al., 2021). That said, substantial concerns have been raised about the ICCDE (Furr, 2010; Hilbig et al., 2021). More specifically, the ICCDE is highly sensitive to shape similarity (despite elevation dissimilarities) and scatter dissimilarity (Furr, 2010). Differences in shape similarity or scatter similarity alone are not necessarily indicative of jingle or jangle fallacies. More specifically, element-wise discrepancies between correlation profiles can occur even when the shapes of the correlation trajectories align (see Figure 1, panel A), and (un)equal levels of scatter within the compared profiles are not indicative of (dis)similar patterns of the involved correlation coefficients.

Accordingly, a high absolute ICCDE can occur even when the scores subjected to analyses of jingle or jangle fallacies actually reveal substantial differences in their correlation patterns. Hilbig et al. (2021) built on the criticism expressed by Furr (2010) in that they found that the ICCDE is particularly influenced by low variance within the correlation profiles. Of note, the ICCDE was originally devised to quantify the similarity between individuals (e.g., the Big Five profiles of romantic partners; McCrae, 2008), while its applicability for investigations of the similarity between correlation profiles has not yet been examined systematically.

The present study examined how the ICCDE behaves under different conditions by applying it to simulated pairs of correlation profiles that varied in shape, scatter, and elevation similarity. Moreover, the role of the magnitude of the scatter within the profiles was examined. As such, this work provides initial evidence about the interactions between shape, scatter, and elevation (dis)similarity.

Evaluation of the Findings

Importantly, the simulations do not establish a universal criterion against which the performance of the ICCDE can be objectively judged. Consequently, the results should not be interpreted as proving that the ICCDE is "wrong" or generally invalid. Instead, the simulations document how the index responds under a range of theoretically meaningful conditions.

Consistent with Furr (2010), the findings indicate that changes in shape similarity are associated with pronounced changes in the ICCDE, whereas the effects of elevation and scatter similarity appear less prominent in several conditions. Whether this property is desirable depends largely on one's conceptualization of profile similarity. Researchers primarily interested in rank-order correspondence may regard strong sensitivity to shape as advantageous. Researchers interested in element-wise agreement of correlation magnitudes, however, may find such behavior problematic.

The most noteworthy findings emerged in conditions characterized by very low within-profile variability. Under these circumstances, profiles with only small element-wise discrepancies occasionally produced highly discrepant ICCDE values. Although this observation is consistent with concerns previously raised by Hilbig et al. (2021), the present results should be interpreted as illustrative rather than definitive.

Two examples from published studies refer to the nomological networks of fixed and growth mindsets (i.e., the belief that cognitive abilities can or cannot be altered over the life course; see Lee et al., 2024) and those of psychopathy and sadism (Kowalski et al., 2024, Study 4): Upon re-analysis of the findings from the study by Lee et al. (2024), low levels of scatter for the correlations of test scores of the aforementioned constructs with external variables emerged (SDs = 0.11 and 0.13). The corresponding correlation coefficients (and thus, levels of elevation), however, were almost identical in absolute magnitude (Ms = -0.01 and 0.01), but the corresponding ICCDE for the set of correlation coefficients was only -.75.

Under the conceptualization of profile similarity adopted here, this magnitude may appear surprisingly small, considering that the coefficients subjected to analysis were almost mirrorsymmetric. In the fourth study by Kowalski et al. (2024), in turn, the levels of elevation (Ms = 0.13 and 0.18) and the visual trajectories of the correlations across criteria were highly similar, but the levels of scatter differed (SDs = 0.13 and 0.21), accounting for an ICCDE of .79 (see the Open Science Framework supplement for re-analyses of both studies).

Given that the studies by Lee et al. (2024) and Kowalski et al. (2024, Study 4) reflect only two examples, additional work will be needed to determine the frequency with which the conditions employed in the present research arise in applied nomological network research and how they have recently affected substantive conclusions. If low-scatter correlation profiles are not uncommon in analyses of nomological networks, understanding how profile similarity indices behave under such conditions is of direct practical relevance rather than merely theoretical interest.

Accordingly, the principal conclusion of the present study is not that researchers should abandon the ICCDE altogether, but rather that interpretations of the coefficient should be accompanied by consideration of the underlying profile characteristics, particularly shape, scatter, and elevation. One implication of the present findings is that no single coefficient can fully characterize all aspects of resemblance between correlation profiles. Following the distinction made by Cronbach and Gleser (1953) between shape, scatter, and elevation, researchers may benefit from treating profile similarity as a multidimensional construct rather than reducing it to a single omnibus value (Furr, 2010). Under such an approach, shape similarity informs the extent to which two measures exhibit comparable patterns of stronger and weaker relations with external variables. Elevation similarity informs whether the overall magnitudes of the correlations are comparable. Scatter similarity reflects the extent to which the strength of differentiation among correlates is comparable across measures.

The relative importance of these components depends on the substantive research question. In some contexts, similar shape may be sufficient evidence for theoretical overlap.

In other contexts, discrepancies in elevation or scatter may be theoretically meaningful and inconsistent with claims of redundancy. Consequently, researchers should explicitly justify which aspects of similarity are most relevant to their conclusions rather than relying exclusively on a single summary coefficient.

Conclusion

The present study provides a systematic examination of the behavior of the ICCDE when applied to correlation profiles. Accordingly, the contribution of the present study is not the identification of a previously unknown limitation of the ICCDE, but the demonstration of how previously recognized characteristics of the coefficient may manifest in an important and commonly encountered application domain. The findings do not suggest that the coefficient is universally invalid, nor do they overturn previous theoretical analyses. Rather, they indicate that conclusions based on the ICCDE may depend substantially on shape similarity and on the amount of variation contained within the profiles under investigation. Accordingly, researchers should exercise caution when interpreting the ICCDE as a standalone indicator of similarity between nomological networks. At minimum, the coefficient should be supplemented with information about shape, scatter, and elevation, alongside graphical inspection of the profiles themselves. The icc.de function from the iccde package (Blötner & Grosz, 2026) automatically provides these sources of information. Future research should focus not only on evaluating alternative omnibus indices, but also on developing principled frameworks for integrating multiple dimensions of profile similarity into substantive conclusions. That said, the present conclusions pertain specifically to the use of ICCDE for comparing correlation profiles and should not be interpreted as a general rejection of the coefficient across all profile similarity applications.

Limitations and Future Directions

The present research was not without limitations. First, the present simulations do not exhaust the universe of possible combinations of shape, scatter, and elevation (dis)similarity.

The representativity of the achieved intensities of shape (achieved through random reordering), scatter (i.e., a ratio of the standard deviations of SDreference/SDmanipulated = 2), and elevation dissimilarities (i.e., adding .30 for each element) is debatable, even though they were derived from empirical studies (Furr, 2010; Gignac & Szodorai, 2016). The specific manipulations were selected because they represent plausible scenarios, but alternative parameterizations may produce different results.

Second, the study did not incorporate a formal external criterion of profile similarity.

Consequently, the analyses document how the ICCDE behaves under specified conditions but cannot determine whether the observed values are objectively correct or incorrect. Future work should develop and justify explicit criteria against which competing indices of profile similarity can be evaluated.

Third, unlike elevation and scatter, shape similarity was generated through random permutation, yielding a distribution rather than a fixed level of shape similarity. Consequently, direct quantitative comparisons between the effects of shape, scatter, and elevation should be interpreted cautiously. Random reordering does, however, go along with a high chance that at least one element of the reordered correlation profile no longer falls within the corresponding boundaries of mathematically plausible values to be observed for the same-ranked element of the reference profile, as defined by the equation by Yule (1922). Consistent with this consideration, 77,527 to 3,287,409 iterations of data creation were required to obtain the targeted number of 10,000 iterations that complied with the formula by Yule (1922; see the RMarkdown file in the Open Science Framework supplement under https://osf.io/9pjkd/overview?view_only=9a42e9981fbf411794a37b756db5bf75). Accordingly, the correlation profiles produced in the four concluded that trait agreeableness and the core of aversive personality features reflect virtually perfect opposites, rendering the latter redundant.Interestingly, the ICCDE was originally developed as an index of the similarity between person profiles (e.g., the similarity between two individual Big Five profiles;McCrae, 2008).

Its eligibility as an index of the similarity between correlation profiles, however, has not yet been evaluated systematically, but only anecdotally on the basis of pre-specified profiles. For instance, Hilbig et al. (2021) demonstrated that, despite clear element-wise differences, the ICCDE posits the vectors X1 = [.03, .01, .02] and X2 = [.51, .52, .53] as mutual opposites, ICCDE = -1.00. In turn, Hilbig et al. showed that, despite clear element-wise correspondence between the elements of the vectors Y1 = [.29, .31, .30] and Y2 = [.30, .30, .29], the corresponding ICCDE indicates almost perfect distinctiveness, ICCDE = -.06. These exemplary cases point to cases in which the ICCDE may indicate substantial similarity despite pronounced element-wise discrepancies (see the profiles X1 and X2) and oversees existing similarity (see vectors Y1 and Y2).
