We left out 20 files that software creates by itself, not the authors: editor settings (11), Jupyter checkpoints (8), R history (1). They hold nothing a reader can use, but they clutter the repository, and software can mistake them for real files (for example a ._ copy of a .csv for data).

Remove these: Operating system files: macOS adds a __MACOSX folder and a ._ copy of every file it puts in a zip, and .DS_Store files to folders; Windows adds Thumbs.db and desktop.ini. On a Mac, create zips from the command line with zip -r -X, or remove them afterwards with zip -d archive.zip "__MACOSX/*" "*.DS_Store". RStudio session files (.Rproj.user/) hold open tabs and unsaved edits; R history (.Rhistory) lists the commands typed in a session and can hold file paths and passwords; Jupyter checkpoints (.ipynb_checkpoints/) are automatic copies of notebooks; compiled Python files (__pycache__/, .pyc) are recreated when the code runs; open-document lock files (~$...docx, .~lock...#) are left while a document is open; editor backups (file~, .bak, .swp) and temporary files (.tmp, .temp) are copies a program made by itself.

Keep only on purpose: version control folders (.git, .svn, .hg) hold the project’s history, which can include earlier versions of files and data that was later removed; editor settings (.idea, .vscode) can hold paths on your own computer. A .gitignore based on GitHub’s templates (https://github.com/github/gitignore) keeps them out of a repository.

How Power Analysis Check works

This module uses regular expressions to identify sentences that contain a statistical power analysis. If specified by the user, it also uses a large language model (LLM) to extract information reported in power analyses, including the statistical test, sample size, alpha level, desired level of power, and magnitude and type of effect size.

The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. Without the use of an LLM, the module uses regular expressions to classify the power analysis as a-priori, sensitivity or post-hoc. With the use of an LLM, it checks if the power analysis is reported with all required information.

The regular expressions can miss power analyses, or fail to classify them correctly. The type of power analysis is often difficult to classify, which can easily be solved by explicitly specifying the type of power analysis as ‘a-priori’, ‘sensitivity’, or ‘post-hoc’. Note that ‘post-hoc’ or ‘observed’ power is rarely useful. The LLM can fail to identify information in the paper, and will not have access to information in paragraphs in the paper other than those that contain the word ‘power’. This package was validated by the Metacheck team on articles in Psychological Science.

How Marginal Significance works

How StatCheck works

Check consistency of p-values and test statistics

The Statcheck module runs Statcheck. Statcheck searches for regular expressions that match a predefined pattern, and identifies APA reported statistical tests. More information on the package can be found at https://github.com/cran/statcheck. The module only returns Statcheck results for t-tests and F-tests, as these are the only tests which have been validated, see https://osf.io/preprints/psyarxiv/tcxaj_v1/.

Statcheck was developed by Michèle Nuijten and Sascha Epskamp.

Statcheck considers p = 0.000 an error, as you should report p < 0.001. Furthermore, p < 0.03 is an error if the p-value was 0.031, and one should simply report exact p-values (p = 0.031). Statcheck might miss one-sided tests, and falsely assume the p-value is incorrect. For more information, see StatCheck.

This module only checks statistical results reported in the running text of the manuscript. It cannot (yet) process statistics reported only in tables.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.) or reported as exactly zero (e.g., p = .000).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold” or “legend”). Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Codebook Check works

This module checks whether the data columns in a repository are documented in a codebook or README. It locates codebook/readme files, extracts the variable definitions they contain, matches those definitions against the data columns extracted by data_check, and reports documentation coverage: how many data columns are documented, and which documented variables are never used.

The Codebook Check module consumes the columns and file classification produced by data_check (and, transitively, repo_check). Files classified as codebook or readme are parsed with parse_codebook(), which reads structured tables (CSV/TSV/Excel with a variable-name column and a label column), embedded labels in haven files (SPSS/Stata/SAS), and plain text from rich-text formats (docx/pdf/rtf/odt). Embedded haven labels from data files are also harvested directly.

Each data column is then matched against the parsed variable definitions with match_column_labels(), using normalised-name matching with experiment-group scoping, haven-label priority, and rule-based label-equivalence merging.

Beyond the variable label, the module harvests the DDI-style per-variable properties a source supplies: the value labels / code list (the 1=“Strongly disagree”…5=“Strongly agree” mapping — from SPSS/Stata value labels and from a codebook “values”/“coding” column), the missing-value scheme (which codes denote missingness, from haven declared missings and labels that read as “refused”/“n/a”), and question text and columns when present. These are carried onto the matched data columns and exported into the Psych-DS variableMeasured (as a schema.org code list plus namespaced metacheck: fields).

The module defaults to rules-only when llm_use(FALSE). When llm_use(TRUE), three optional LLM tiers run: parsing unstructured codebook text that the rules could not handle, fuzzy-matching still-unlabelled columns to still-unmatched codebook variables, and merging conflicting label definitions into a single canonical label.

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Brain-computer interfaces (BCIs) may provide a communication option for people with severe motor impairment, when conventional assistive access becomes unreliable. To date, several potential improvements of BCI-related hardware and software components have been investigated, for instance, classification algorithms for brain signals such as electroencephalography (EEG). These efforts focused on laboratory work with healthy participants. However, this is not representative for real-life conditions of potential motorimpaired end-users with diseases such as amyotrophic lateral sclerosis (ALS). Our study compares state-of-the-art classification approaches on a real-life dataset of an end-user with ALS in the locked-in state (LIS) and a tactile P300-based BCI, obtained during long-term home-use. We applied classifiers, including Shrinkage Linear Discriminant Analysis (ShrinkLDA) and Riemannian Geometry Classifiers (RGC). We tested effects of different calibration scenarios (i.e., amount of training data, time between calibration) and spatial filtering (xDawn). These variations were compared to the results of a Stepwise Linear Discriminant Analysis (SWLDA), the classifier used during the original online recordings and reimplemented here as the reference. We defined an accuracy of >70% as sufficient performance (based on prior work). SWLDA could be outperformed, but without spatial filtering with xDawn, no classification algorithm allowed for sufficient independent home-use, with accuracies ranging between 33% to 66%; SWLDA: 59%. The addition of spatial filtering via xDawn notably improved classification results for most classifiers, with the best performance (73%) achieved by classifiers using Riemannian Geometry. For some tangent space support vector machine (SVM) approaches, xDawn decreased performance. No tested classifier achieved consistent accuracy of >70% known as a minimum threshold for meaningful communication via assistive technology. This is the first study comparing classifiers on a large set of tactile P300-based BCI data obtained from an end-user in the LIS in his own home. Of the state-of-the-art classifiers, only four tested classifiers were able to reach slightly beyond an average accuracy of >70%. No classifier performed consistently above this threshold. Future work can build on our findings by investigating how disease characteristics, hardware and software optimization, and environmental factors influence BCI signal classification under real-life conditions for potential end-users with severe motor impairment including the LIS.

1 Introduction

The locked-in state (LIS) can be defined as the state of a conscious mind in a paralyzed body.

Although terminology varies across publications, we adopt "state" as a broader designation encompassing different underlying conditions, while using "syndrome" for the traditional clinical presentation associated with brainstem injury. The term "locked-in syndrome" was introduced by Plum and Posner in 1966 (Posner et al., 2019). Whereas in classic LIS only vertical movement of the eyes and eyelids remain, in complete or total LIS (CLIS) no voluntary muscle movement is possible (Bauer et al., 1979). (C)LIS is not caused by a singular disease, but may have several causes, most commonly vascular complications, traumatic brain injuries or demyelinating disease such as multiple sclerosis, and neurodegenerative motor neuron disease such as amyotrophic lateral sclerosis (ALS) (Patterson and Grabois, 1986; Lulé et al., 2009; Schnetzer et al., 2023). In the LIS, patients retain the potential ability to use an eye-tracker for communication, but this ability is challenged during the transition to complete LIS. The potential independence from muscular activity renders braincomputer interfaces (BCIs) one of the last communication options in CLIS (Kübler et al., 2001a).

In the past, various BCIs for communication have been proposed, active (e.g., based on motorimagery, slow cortical potentials (Kübler et al., 1999; Neuper et al., 2006; Saeedi et al., 2017)) as well as reactive (i.e., based on event-related potentials (ERPs) (Farwell and Donchin, 1988; Nijboer et al., 2008) or visual evoked potentials (VEPs) (Wang et al., 2008; Bin et al., 2009 Bin et al., , 2011;; Spüler et al., 2012)). The P300-based BCI remains one of the most frequently used candidates (Allison et al., 2020). It utilizes a positive ERP response associated with attending to a task-relevant salient target stimulus in an oddball paradigm, where it is usually presented in a randomized order and less frequently with additional task-irrelevant and more frequently presented non-target stimuli (Wascher et al., 2020). The highest information transfer rates (ITR) are typically achieved in visual paradigms (Kaufmann and Kübler, 2014; Allison et al., 2020; Pan et al., 2022). However, the progressive loss of control over ocular muscles and eyelids is considered detrimental for visual paradigms (Brunner et al., 2010), making them less feasible for potential end-users (Pires et al., 2022). Hence, gazeindependent paradigms such as auditory or tactile P300-based BCIs have been investigated (Kübler et al., 2009; Riccio et al., 2012; Herweg et al., 2016; Eidel and Kübler, 2020; Ziebell et al., 2020; Huang et al., 2021; Séguin et al., 2024). While patients are the main target group for the proposed devices, they have rarely been included in studies (Kübler, 2020; Peters et al., 2022; Rezvani et al., 2024).

To target this issue, a growing body of work on user-centered design has been conducted to consider the needs and opinions of potential end-users at every step of BCI development (Vaughan et al., 2006; Sellers et al., 2010; Schreuder et al., 2013; Kübler et al., 2014; Choi et al., 2017; Bettencourt et al., 2024). For instance, long-term independent home-use studies have evaluated and optimized several BCI applications, including the visual P300-based Brain Painting software (Botrel et al., 2015; Holz et al., 2015a Holz et al., , 2015b)), audiovisual P300-based communication paradigms for a patient in a CLIS and a tactile P300-based BCI (Ziebell et al., 2024). Predominantly, these studies have focused on collecting and implementing objective and subjective measures on the usability criteria effectiveness (e.g., online accuracy), efficiency (e.g., ITR), and satisfaction (e.g., rating scales). Complementary to this focus on the comprehensive assessment of usability measures, it has been suggested to optimize BCIs based on signal characteristics (Han et al., 2022). Signal-based optimizations could for example include improving the signal quality through training (Eidel and Kübler, 2022), identifying user states beneficial for BCI performance using electrophysiological features, for instance via Lempel-Ziv complexity (Settgast and Kübler, 2024), or testing alternative signal classification algorithms (Huang et al., 2021).

In particular with regard to signal classification algorithms, a plethora of BCI-related studies were published in recent years -however, this work has so far been mostly directed at optimizing signal classifiers for data of healthy participants in laboratory conditions (Lotte et al., 2007 (Lotte et al., , 2018;; Peters et al., 2022; Rezvani et al., 2024). Notably, classifiers such as Linear Discriminant Analysis with a shrinkage parameter (ShrinkLDA) and Riemannian Geometry Classifiers (RGCs) have demonstrated promising performance (Blankertz et al., 2011; Lotte, 2015; Congedo et al., 2017; Yger et al., 2017; Lotte et al., 2018), reaching higher accuracies than more traditional approaches such as Stepwise Linear Discriminant Analysis (SWLDA) while minimizing computational demands. Further strength lies in their capability to deal with little training data. As an additional example, spatial filtering, for instance via xDawn has been identified as a tool with substantial potential (Rivet et al., 2009 (Rivet et al., , 2011)).

As a next step in line with the hitherto reviewed literature, a major current challenge remains in testing the reliability of such promising classifier methods on end-user data, since diseases as well as circumstances of home use may influence data distribution in terms of lower signal to noise ratio and higher variance (Bettencourt et al., 2024).

The aim of this study was to test a selection of state-of-the-art signal classification algorithms on a previously collected large dataset that was long-term recorded from an end-user in the LIS at his own home. In related work, where additional details can be found, this dataset has been analyzed with a focus on the long-term persistence of the P300 (Ziebell et al., 2024). More specifically, we were interested in whether promising algorithms such as ShrinkLDA, MDM, FGMDM, tangent-space logistic regression and SVMs, and combinations with spatial filtering via xDawn may improve the performance baseline established with SWLDA.

2 Methods

2.1 Participant

The end-user of the BCI (WT) is a male electrical engineer, who was 58 years at the time when the relevant data collection for this paper began. He was diagnosed with ALS ten years prior (October 2010) and has been in the LIS since 2015 (Revised Amyotrophic Lateral Sclerosis Functional Rating Scale; ALSFRS-R=0, (Cedarbaum et al., 1999)). He receives invasive mechanical ventilation by tracheostomy and nourishment via a percutaneous endoscopic gastrostomy. WT was able to communicate via eyeblinks, eye-movements, and pressure detection on his leg throughout the entire study. Usually, he relies on eye tracking in combination with assistive software, such as Dasher (http://www.inference.org.uk/dasher/) and GRID 3 (https://thinksmartbox.com/product/grid-3/), to operate his computer, which was his preferred communication device. WT reported this way of communication as increasingly exhausting, as eye movement became difficult. In February 2021, i.e., four months after the start of the relevant data collection for this paper, the patient was further diagnosed with sensory neuropathy in his legs, which led to an adaptation of the experimental setup.

WT has been interested in BCI testing since 2016 and had his first tests with a tactile P300-based BCI in 2018 (Ziebell et al., 2024). The protocol was conducted in accordance with the ethical guidelines of the Declaration of Helsinki and approved by the Ethics Committee of the Psychological Institute of the University of Würzburg (approval number: GZEK 2013-1/GZEK 2021-53).

2.2 Data Origin

The data collection was guided by the user-centered design approach (Kübler et al., 2014) and is one of the rare instances of a long-term use of a BCI in a patient's own home. It was part of a cooperation between the Nuremberg Institute of Technology Georg Simon Ohm and the University of Würzburg, for developing devices to assist people with severe motor impairment. This particular project aimed at improving the tactile P300-based BCI paradigm to achieve gaze-independent control of communication software presented on a computer.

In the current study, we focused on data that was collected in 39 sessions, starting November 13 th , 2020 and ending May 31 st 2021. The first two months included three sessions per week, the remaining months included typically one session per week. Initially, the hardware was set up by staff of the University of Würzburg at the home of the patient. Until session 13 (December 14 th , 2020), the caregivers were introduced to the experimental setup so that they could prepare the setup independently. This was a considerable advantage during the COVID-19 pandemic. In addition, the sessions were supervised and controlled remotely by the authors via the remote service software AnyDesk (https://www.anydesk.com/).

2.3 Experimental Setup

Tactile Multi-Class Oddball-Paradigm

The paradigm used here has been established in prior work (Kaufmann et al., 2014; Herweg et al., 2016; Eidel and Kübler, 2020, 2022; Ziebell et al., 2024). In our analysis, we focused on a tactile P300-based BCI paradigm with six classes. In this paradigm, six vibrotactile stimulators (T1, T2, T3, T4, T5, T6) were placed on shoulders (T1/2), elbows or wrist joints (T3/4) and ankles, knee pits or thighs (T5/6) (see Figure1A) to elicit P300 responses. After the patient was diagnosed with sensory neuropathy in the legs, the placement was adapted and the lower limb positions were moved on the torso, T5 on the chest and T6 on the neck (see Figure1B).

To assess BCI performance we used a copy-spelling task as pioneered by prior work and described there in more detail (Kübler et al., 2001b). In brief, during each response selection trial, the patient was visually instructed to focus on one specific target tactor, which he should select accurately (or in terms of the copy-spelling task, copy accurately) by using the BCI. During a stimulation sequence, tactors vibrated for 220 ms in a randomly counterbalanced order, with an interstimulus interval of 400 ms. One trial consisted of ten (calibration) or eight (copy) activations of each of the six tactors. One run comprised six trials, each tactor being the target once, resulting in 60 target and 300 nontarget epochs per calibration run. Each training session started with three calibration runs and was followed by three copy runs. After that, the patient could freely choose to continue testing the BCI for an undetermined number of more runs. To allow for a standardized comparability, those additional freely chosen runs were excluded from analysis.

In the copy runs, the patient was instructed to focus on a specific tactor and received feedback on the classification result. This classification was based on a SWLDA, which was calibrated based on the data from the calibration runs.

The BCI cycle was controlled by BCI2000 (Schalk et al., 2004), connected wirelessly to an Arduino (Adafruit HUZZAH32 ESP32 Feather) which controlled the tactors. The soft-and hardware for the Arduino was specifically developed for this use case.

PREPRINT EEG Signal Acquisition

EEG signal was recorded with twelve Ag/AgCl g.Ladybird active electrodes (g.tec Engineering GmbH, Graz, Austria). The electrodes were positioned according to the 10-10 system, first in positions of SetA (Fz, FC1, FC2, C3, Cz, C4, P3, Pz, P4, O1, Oz, and O2) and were later moved to focus around Cz (SetB: Fz, FC1, FC2, C1, C3, Cz, C2, C4, CP1, CPz, CP2, Pz; after session 11 on December12 th 2020) as signal strength of the P300 was higher in locations closer to Cz. Reference and ground were placed on the right earlobe and AFz. All data was recorded using BCI2000 (Schalk et al., 2004) with a sampling rate of 512 Hz, a bandpass-filter from 0.1 to 60 Hz, and a notch-filter from 48 to 52 Hz.

EEG Processing

As in previous studies (Herweg et al., 2016; Eidel and Kübler, 2020; Eidel et al., 2021; Ziebell et al., 2024), the focus in the physiological analysis was on the electrode positions Fz, Cz and Pz. The data was filtered with a band pass (0.1 -40 Hz) and baseline corrected (subtracting the mean of the 100 ms pre-stimulus). Epochs, which contained a peak-to-peak amplitude of 100 µV or higher were excluded. Visual inspection of the data suggested an increased latency, hence, the critical time window for evaluating the P300 was shifted to 350 -600 ms. Although a positive deflection was maintained longer than 600 ms the window was chosen in this manner because best discriminability (predicted by R²) was expected in said window and further elongation would have also increased the overlap with subsequent stimuli.

Signal Classification

A SWLDA, provided by BCI2000 (Schalk et al., 2004) represented the current classifier of the device, therefore, a Python SWLDA implementation was considered as a reference for all other tested algorithms. All classifiers were implemented in Python 3.7.13, using the machine-learning library scikit learn 1.0.2, the framework for MEG and EEG analysis MNE 0.23.0 and the toolbox for signal classification with Riemannian Geometry pyRiemann 0.2.7. For the implementation of the SWLDA, code from a git repository of Stocks was adapted (https://github.com/taliastocks/Py3GUI). The regular LDA and the ShrinkLDA were applied using the predefined function of the scikit-learn framework. The regularization parameter was determined by the Ledoit-Wolf optimization algorithm (Ledoit and Wolf, 2004). For the RGCs, the covariance matrices and respective classification results were calculated using the functions provided by the pyRiemann-toolbox. Five covariance-based classification approaches were implemented: minimum distance to mean (MDM), MDM preceded by Fisher geodesic discriminant analysis (FGMDM), tangent-space classification using logistic regression (TS_LG), a linear-kernel support-vector machine (TS_SVM_lin), or a radial-basisfunction-kernel support-vector machine (TS_SVM_rbf). The FGDA is an adaptation of Fisher's Linear Discriminant Analysis to tangent space (Barachant et al., 2010). RGCs rely on spatial covariance matrices for classification. Logistic regression (TS_LG) used an L1 penalty and the liblinear solver. To assure the covariance matrices were symmetric positive-definite, they were regularized, again with the parameter determined by the criterion of Ledoit and Wolf (Ledoit and Wolf, 2004). Due to the use of spatial covariance matrices, the computational complexity of the RGCs was not influenced by temporal resolution. MDM, FGMDM and the three tangent-space classifiers were evaluated using covariance representations derived from both the original sampling rate and data resampled to 20 Hz. Approaches using resampled data are marked with the suffix "_res", and approaches using spatial filtering are marked with "_xDawn"

To increase the signal-to-noise ratio we introduced spatial filtering with the xDawn algorithm (Rivet et al., 2009). Nonetheless, it increases the computational demands, calibration time and induces the dual optimization problem, i.e., the independent tuning of the filter and classifier. To address the issue of increased computational demands and calibration time the filter decomposed the signal into two components per class, yielding a reduction of 2/3 of the former signal in both classification approaches. LDA, ShrinkLDA and SWLDA were each evaluated with and without xDawn; MDM, FGMDM, TS_LG, TS_SVM_lin and TS_SVM_rbf were each evaluated with and without xDawn and temporal resampling, yielding 26 classifiers.

To sustain comparability with BCI2000, epochs were down sampled to 20 Hz in all implementations, except mentioned otherwise. Accordingly, the time window of the epoch remained 0 -800 ms after stimulus onset. All python scripts used for the data classifications are available online (https://github.com/iamraP/P300ClassifierComparison.git).

Classifiers were trained using the calibration runs specified for each of the four conditions below.

The accuracy of each training session was evaluated independently on the three copy runs. To further increase the relevance for the use case, it was attempted to approximate an online classification process. Therefore, target-class probabilities were estimated for each tactor and for individual epoch and averaged across its eight stimulus repetitions within each selection. The tactor with the highest cumulative probability was selected as the overall classification result of the respective trial.

For the calibration itself, four conditions were tested:

Sessionwise Calibration -3 Runs (Sess3): For each session, the classifiers were retrained using the three calibration runs of the same day (180 target trials) to account for possible changes in between sessions, which corresponded to the paradigm applied during data acquisition.

Sessionwise Calibration -1 Run (Sess1): For each session, the classifiers were retrained only using the first calibration run of that day (60 target trials) to still account for possible changes between sessions, but also to test classification performance with limited training data.

Transferred Classifier -One Session (Trans1):

To assess classifier transferability and performance stability across sessions, we applied the existing classifier from the first available session (180 target trials) to all sessions with the same setup. This was done separately for the two electrode configurations: For electrode SetA, classifiers were trained on the calibration data of the first day and evaluated on copy runs from that day and subsequent sessions using SetA. The same was done for SetB. Here, the classifiers were calibrated on the data of the first session after the switch.

Transferred Classifier -Three Sessions (Trans3):

To account for some expected variance in the data between sessions, the classifiers were trained on the first three sessions (540 target trials) with the corresponding electrode setup.

For an individual session comprising 18 six-choice selections, at least seven correct selections (38.9% accuracy) exceeded chance in an unadjusted one-sided exact binomial test at α = 0.05, assuming independent selections with chance probability 1/6 (Billinger et al., 2013). Three Sess1 SWLDA fits failed to produce a classifier. These sessions were assigned with zero accuracy in the summaries and inferential analyses, retaining all 39 sessions for each approach.

PREPRINT Data Analysis

All statistical analyses were conducted with the programming language R. Classifiers were compared against each other within each calibration condition. To accommodate non-normally distributed accuracies and the evaluation of all classifier approaches on the same 39 sessions, we used nonparametric Friedman tests with session as the blocking factor, followed by two-sided paired Wilcoxon signed-rank tests. If alpha correction was necessary, we applied the Bonferroni method. As a criterion for successful performance, we defined an accuracy beyond 70%, since accuracies beyond 70% have traditionally been described as sufficient to operate relevant communication software (Kübler et al., 2001b). Friedman test results and complete pairwise comparisons are provided in Supplementary Tables 2 3 4 5, including Bonferroni-adjusted p-values, Wilcoxon W statistics, and effect-size magnitudes r.

3 Results

Basic findings

In previous work we showed that the patient consistently presented a P300 ERP pattern (Ziebell et al., 2024). For the data in the current analysis, the P300 mean amplitudes in the window of interest, averaged over all sessions, were 2.1 µV at Cz (SD: 1.55 µV), 1.7 µV at Pz (SD: 1.59 µV) and 1.56 µV at Fz (SD: 2.88 µV). For the Fz electrode the shape deviated from the commonly observed P300, around 400ms after stimulus onset the voltage increased in an almost linear manner. For a depiction of the ERP patterns at Fz, Cz, and Pz, see Figure 2. For a more detailed electrophysiological analysis we refer to related work (Ziebell et al., 2024).

Figure 3 presents the session-wise mean amplitudes in the time window of interest (350 -600 ms) at Cz and the corresponding online accuracies. There was a clear difference between target and nontarget conditions in almost every session. Nonetheless, there were high fluctuations in signal strength (P300 average of all electrodes: M: 2.0 µV, SD: 2.1 µV), as well as in the classification accuracies (Online SWLDA M: 60% SD: 16%).

Comparison of signal classification algorithms

The offline analysis compared 26 classifier configurations across the same 39 sessions under four calibration conditions, using eight stimulus repetitions per tactor within each six-choice selection. These configurations combined eight classification approaches with or without xDawn spatial filtering and, where applicable, temporal resampling. Mean accuracies and standard deviations are reported in Supplementary Table 1. Classifier performance differed significantly within every calibration condition (Friedman tests, all p < .001). All pairwise p-values reported below are Bonferroni-adjusted across the 325 classifier pairs within the corresponding condition; complete test results are provided in Supplementary Tables 2 3 4 5.

Sessionwise Classification

With three calibration runs per session (Sess3), SWLDA achieved a mean accuracy of 59% (SD: 20%). Four configurations significantly outperformed this reference, all incorporating xDawn. Tangent-space logistic regression with xDawn achieved the highest mean accuracy (73%, SD: 16%), followed by FGMDM with xDawn (72%, SD: 17%). Both exceeded SWLDA by approximately 14 percentage points (pp), with p < .001 for both comparisons and effect-size magnitudes of r = .81 and r = .76, respectively. The resampled variant of tangent-space logistic regression with xDawn also outperformed SWLDA (71%; p = .010), as did shrinkage LDA with xDawn (69%; p = .005). Figure 4 shows the distributions for all configurations, and Supplementary Table 2 provides the pairwise comparisons.

With one calibration run per session (Sess1), mean accuracy was lower than in Sess3 for 23 of the 26 configurations, with an average decrease of 10 pp across configurations. SWLDA achieved 44% accuracy (SD: 22%), including the three failed fits scored as zero. FGMDM and tangent-space logistic regression with xDawn each achieved 62% accuracy (SD: 20% and 19%, respectively), exceeding SWLDA by approximately 18 pp (both p < .001). Three additional configurations, all with xDawn, significantly outperformed the reference: resampled tangent-space logistic regression (62%), linear-kernel tangent-space support-vector classification (61%), and resampled FGMDM (59%; all p ≤ .016). No configuration achieved a mean accuracy above 70% in this condition (Figure 5; Supplementary Tables 1 and 3).

Transferred Classification

The transfer conditions used calibration data from one or three source sessions for each electrode configuration. Their summaries include evaluations of the calibration-source sessions as well as subsequent sessions.

With calibration based on three runs from one session (Trans1), mean accuracy was lower than in Sess3 for all 26 configurations, with an average decrease of 10 pp across configurations. SWLDA achieved 50% accuracy (SD: 17%). FGMDM with xDawn had the highest mean accuracy (66%, SD: 19%), exceeding SWLDA by 16 pp (p = .002; r = .72). Tangent-space logistic regression with xDawn, both with and without resampling, also outperformed the reference. Both variants achieved 64% accuracy (SD: 18%), corresponding to gains of approximately 14 pp (both p ≤ .004). No configuration achieved a mean accuracy above 70% (Figure 6; Supplementary Tables 1 and 4).

With calibration based on nine runs from three sessions (Trans3), mean accuracy was higher than in Trans1 for 24 of the 26 configurations. The average increase across configurations was 9 pp; the exceptions were resampled minimum-distance-to-mean classification and linear-kernel tangent-space support-vector classification with xDawn. SWLDA achieved 60% accuracy (SD: 17%).

Five configurations significantly outperformed SWLDA in Trans3. FGMDM with xDawn achieved the highest mean accuracy (73%, SD: 15%), exceeding the reference by 13 pp (p = .004; r = .71). Tangent-space logistic regression with xDawn achieved 72% with and without resampling, while resampled FGMDM with xDawn achieved 71%; all three also significantly outperformed SWLDA (all p ≤ .010). Resampled tangent-space logistic regression without xDawn provided a further significant improvement (70%, SD: 16%; p = .049). Figure 7 shows the accuracy distributions, and Supplementary Table 5 provides the complete comparisons.

Effects of xDawn spatial filtering

Matched comparisons isolated the effect of adding xDawn to each classifier configuration. Across the four calibration conditions, xDawn increased mean accuracy in 9-12 of the 13 matched pairs, although the statistical evidence for these improvements varied by classifier and condition.

Both the original and resampled minimum-distance-to-mean classifiers improved significantly with xDawn in every calibration condition (all p ≤ .030). FGMDM and tangent-space logistic regression without temporal resampling showed significant improvements under Sess3, Sess1, and Trans1, but PREPRINT not under Trans3. For SWLDA mean accuracy increased with xDawn in all four conditions, but none of the matched comparisons was significant after correction (Supplementary Tables 2 3 4 5).

Spatial filtering reduced accuracy for some tangent-space support-vector configurations. In Trans3, the linear-kernel variant decreased from 66% without xDawn to 40% with xDawn (p < .001), and its resampled counterpart decreased from 56% to 39% (p = .001). The resampled linear-kernel variant also showed significant reductions under Sess3 and Trans1 (Supplementary Tables 2, 4, and 5). Thus, the effect of xDawn depended on the classifier configuration and calibration condition.

Variability across sessions

Three configurations in Sess3 and four in Trans3 achieved mean accuracies above the study's 70% criterion; all of these configurations used xDawn. However, no configuration exceeded 70% in every evaluated session under any calibration condition (Figures 4 5 6 7). Classifier rankings also varied between sessions, with no single configuration consistently achieving the highest accuracy. Under Sess1, 10 of the 26 configurations achieved or tied for the highest accuracy in at least one session and the lowest accuracy in at least one other session (Figure 8). Improvements in mean accuracy therefore coexisted with substantial variation in performance across recording days.

4 Discussion

Here we provide the first comparison of state-of-the-art signal classification algorithms on long-term home-use data from an ALS end-user in the LIS who used a tactile P300-based BCI (author WT). In related work, we provided first analyses of these data with a focus on the ability of WT to persistently produce a P300-like ERP pattern based on ideas from the user-centered design (Ziebell et al., 2024). In the spirit of expanding this earlier user-centered work by focusing on optimizing signal classification (Han et al., 2022) and based on the stability of WT's P300 ERP component, we evaluated selected algorithms such as ShrinkLDA, RGCs, tangent-space logistic regression and SVMs, as well as a traditional SWLDA (which also has been used in prior work with WT) in combination with spatial filtering via xDawn. As seen in previous studies target and non-target were best separable at central electrodes, where a typical P300 pattern was observed (predicted by R² ) (Ziebell et al., 2024).

Notably, even though in WT a P300 could be persistently elicited, we found a high variance of amplitude and online accuracy, which is why it was of special interest to us whether alternative signal classification algorithms could have optimized WT's BCI performance in hindsight and for potential future work. As a measure of performance, we aimed for accuracies >70% which have traditionally been described as a minimum for meaningful communication via assistive technology (Kübler et al., 2001b).

We could show that some of the newer classifiers could improve the results achieved by the SWLDA. The strongest candidates were FGMDM_xDawn and the xDawn-based tangent-space logistic-regression approaches; FGMDM_res_xDawn was also competitive, particularly in Trans3. Online information transfer rates (ITRs) ranged from 0.11 bits/min to 3.69 bits/min, the maximum session accuracy was 100%, corresponding to a theoretical ITR of 5.21 bits/min under the existing six-choice, eight-repetition paradigm.

Whereas the ShrinkLDA_xDawn has minimal computational costs, in comparison, the FGMDM_xDawn and FGMDM_res_xDawn are among the more computational demanding of the tested classifiers because they use two kinds of filters. Nonetheless, both should be feasible online, as the calibration and classification of an entire training day remained well under a minute on a conventional laptop.

As expected from earlier work (Lotte and Guan, 2009; Delgado et al., 2020), the classification accuracy decreased for almost all classifiers when fewer calibration data were included (we tested three runs with 180 target trials versus one run with 60 target trials). The exceptions were MDM_res whose mean accuracy remained approximately stable and whereas TS_SVM_lin_xDawn and TS_SVM_lin_res_xDawn even improved. For instance, SWLDA accuracy decreased by 25% (relative). Likely the distribution of the data, sampled in a single run, is not representative for the specific day it was collected on, as attention, noise or electrode contact quality may vary. Most classification results improved further with spatial filtering via xDawn, which increases the signal-tonoise ratio and hence facilitates the estimation of the true distribution of the data. This is particularly relevant for real-life end-user settings, where occurrence of confounding noise is of higher likelihood than in laboratory settings that allow for stricter noise control (Bettencourt et al., 2024).

Among classifiers without xDawn, FGMDM showed the smallest decrease from Sess3 to Trans1 (3.3pp), whereas several classifiers improved from Sess3 to Trans3. FGMDM_xDawn achieved the highest mean accuracy in both transfer conditions: 66% in Trans1 and 73% in Trans3. In Trans3 the 70%-threshold was also exceeded by TS_LG_res_xDawn (72%), TS_LG_xDawn (72%) and FGMDM_res_xDawn (71%). The lower Trans1 accuracies relative to Sess3 may reflect limited generalization of models and filters fitted to one calibration session. Training on a limited set of sessions may restrict generalization to other sessions. Averaged across the 13 matched classifier pairs, xDawn increased mean accuracy in each condition, although individual SVM approaches sometimes performed worse, with significant decreases for TS_SVM_lin_res in Sess3, Trans1 and Trans3, and for TS_SVM_lin in Trans3. A possible account for poorer SVM performance is that fixed filtering and SVM settings were less suitable together or that useful information was lost. Future work should investigate them by jointly varying the number of xDawn components and SVM hyperparameters within validation restricted to the training data, while keeping evaluation data held out.

FGMDM, which performed lower than SWLDA in both session-wise calibration approaches, was significantly enhanced by the preceding xDawn in three conditions. FGMDM_xDawn achieved higher mean accuracy than both SWLDA and SWLDA_xDawn in all calibration conditions. For SWLDA, xDawn increased mean accuracy in every calibration condition, but none of these matched comparisons was significant after the within-condition Bonferroni correction. This may be due to the fact that the regularization of the covariance as well as the stepwise feature selection already counteracts the background noise of the acquired signal. The Riemannian approaches without xDawn showed heterogeneous performance, with the lowest accuracies for MDM_res and considerably higher Trans3 accuracies for FGMDM and tangent-space logistic regression. While in other studies these approaches could hold up or even outperform other state-of-the-art classifiers (Barachant and Congedo, 2014; Delgado et al., 2020), the MDM underperformed in this dataset. This might be explained by the partially malfunctioning electrode and further supports the combination of classifiers with spatial filters. While MDM only maps the data to the manifold, it does not perform a feature selection and is therefore imperiled to distortion by such issues (i.e., bad channels).

Overall, we observed a high variance of the classification accuracy. Although several classifier approaches achieved mean accuracies above 70%, no variant exceeded this threshold in every evaluated session under any of the four calibration conditions. Thus, none consistently met the PREPRINT study's performance criterion across all recording days, indicating that the improvements in average accuracy did not establish reliable day-to-day performance. Interestingly, performance rankings were inconsistent, and no single classifier always outperformed the others. This means the variations in data distribution had different effects on the different approaches. This indicates that there might not be the "one" classifier that always yields the best possible classification result. More likely, depending on factors, which can vary from session to session and patient to patient, different classifiers will perform best.

The observed day-to-day variability may reflect several physiological, technical and environmental influences. Potential contributors include changes in psychological factors such as attention, fatigue or mental workload (Han et al., 2022). Differences in the subjective perception of the tactile stimulus might factor in as well (Eidel and Kübler, 2022). Electrode-skin contact and physiological or environmental artifacts may also affect the quality of the recorded EEG (Kappenman and Luck, 2010; Blankertz et al., 2011). These influences could affect classifier configurations differently because of their different signal representations, spatial filtering and regularization strategies. For example, spatial filtering and covariance regularization can affect ERP classification performance (Blankertz et al., 2011; Rivet et al., 2011). P300 classification methods have shown different sensitivities to experimentally imposed latency shifts and temporal jitter (Barachant and Congedo, 2014). It is therefore plausible that session-dependent changes in target-non-target separability, channel-specific noise, and ERP timing contributed to the observed changes in classifier rankings. However, the present analysis did not isolate these factors or their interactions. In related work, we have provided first steps toward more detailed investigations in such directions (Ziebell et al., 2024). Future studies should assess signal quality, recording conditions and user state alongside classification accuracy in further detail to evaluate potential systematic influences of such factors on performance variability across recording days for individual end-users.

The feasibility of these classifiers for online use remains to be established. On a regular laptop the computation time stayed well within limits (M: 7.42s, SD: 13.71s, for both, calibration and classification of data of an entire session). End-to-end processing time for the updated implementations remains to be measured on the intended hardware, including data preparation, covariance estimation, spatial filtering, model fitting and prediction.

The present classifier comparison is conditional on the selected preprocessing pipeline. Recent multiverse evidence indicates that filtering, referencing, baseline correction, and artifact handling can substantially alter EEG decoding performance (Kessler et al., 2025). Future work should test whether the observed classifier ranking remains stable across plausible preprocessing choices, particularly for noisy home recordings. Further, no systematic hyperparameter tuning was performed for the classifiers. The performance differences observed therefore apply to the evaluated configurations and may not reflect the best attainable performance of each approach. Hyperparameter optimization could alter both absolute accuracies and the relative ranking of classifiers.

Although WT still prefers his eye-tracker for everyday use over our current BCI approaches, exploring communication via BCI remains important for two reasons. On the one hand, as WT reported, the control of the eye-tracker becomes more and more imprecise and tiresome, hence an alternative vision independent system for communication is highly desirable. On the other hand, early and frequent BCI practice with non-visual modalities may facilitate its continued use once the patient might lose reliable control of eye movements.

5 Conclusion

In the offline comparison, FGMDM and tangent-space logistic-regression approaches combined with xDawn achieved higher mean accuracies than the SWLDA reference. Thus, we will consider these algorithms for future work. We recommend evaluating xDawn together with the chosen classifier, because it improved mean accuracy for most approaches with a few exceptions. For future evaluation, the strongest candidates were FGMDM_xDawn and TS_LG_xDawn, and TS_LG_res_xDawn. The calibration schedule may also be evaluated, as with three calibration sessions (Trans3) competitive mean accuracy was achieved. Because training data quantity and the number of source sessions increased together, their individual contributions to this improvement could not be determined. ShrinkLDA remains a candidate where computational resources are limited. Nonetheless, no classifier exceeded 70% accuracy in every evaluated session. Our findings highlight the importance of classifier selection and the need for further improvement in the overall classification process. Future research should emphasize BCI data collection in daily life at the enduser's home, preferably those in the LIS.
