Reporting p values imprecisely (e.g., p < .05) reduces transparency, reproducibility, and re-use (e.g., in p value meta-analyses). Best practice is to report exact p-values with three decimal places (e.g., p = .032) unless p values are smaller than 0.001, in which case you can use p < .001.

Power analyses need to contain the following information to be interpretable: the type of power analysis, the statistical test, the software used, sample size, critical alpha criterion, power level, effect size, and an effect size metric. How Power Analysis Check works

This module uses regular expressions to identify sentences that contain a statistical power analysis. If specified by the user, it also uses a large language model (LLM) to extract information reported in power analyses, including the statistical test, sample size, alpha level, desired level of power, and magnitude and type of effect size.

The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. Without the use of an LLM, the module uses regular expressions to classify the power analysis as a-priori, sensitivity or post-hoc. With the use of an LLM, it checks if the power analysis is reported with all required information.

The regular expressions can miss power analyses, or fail to classify them correctly. The type of power analysis is often difficult to classify, which can easily be solved by explicitly specifying the type of power analysis as ‘a-priori’, ‘sensitivity’, or ‘post-hoc’. Note that ‘post-hoc’ or ‘observed’ power is rarely useful. The LLM can fail to identify information in the paper, and will not have access to information in paragraphs in the paper other than those that contain the word ‘power’. This package was validated by the Metacheck team on articles in Psychological Science.

How Preregistration Check works

Retrieve information from preregistrations in a standardised way, and make them easier to check.

The Preregistration Check module identifies preregistrations on the OSF and AsPredicted based on links in the manuscript, retrieves the preregistration text, and organizes the information into a template. The module retrieves text from the OSF with its API, and from AsPredicted with ResearchBox’s API when a ResearchBox key is set (see rbox_token()), or else from the preregistration’s web page. The information in the preregistration is returned. An AsPredicted link that could not be read is named in the report, with the reason.

The module can’t extract information from non-structured preregistration templates (i.e., where the preregistration is uploaded in a single text field) and it can’t retrieve information in preregistrations that are stored as text documents on the OSF.

If you want to extend the package to be able to download information from other preregistration sites, reach out to the Metacheck development team.

How StatCheck works

Check consistency of p-values and test statistics

The Statcheck module runs Statcheck. Statcheck searches for regular expressions that match a predefined pattern, and identifies APA reported statistical tests. More information on the package can be found at https://github.com/cran/statcheck. The module only returns Statcheck results for t-tests and F-tests, as these are the only tests which have been validated, see https://osf.io/preprints/psyarxiv/tcxaj_v1/.

Statcheck was developed by Michèle Nuijten and Sascha Epskamp.

Statcheck considers p = 0.000 an error, as you should report p < 0.001. Furthermore, p < 0.03 is an error if the p-value was 0.031, and one should simply report exact p-values (p = 0.031). When the sentence of a test says it is one-sided (“one-tailed”, “one-sided” or “directional”), a p-value that fits a one-sided test counts as consistent (statcheck’s OneTailedTxt setting; #695). When the paper says anywhere that its tests are one-sided, a p-value that fits a one-sided test in either direction counts as consistent too: half the two-sided p, or 1 minus that half for an effect against the predicted direction. Equivalence tests (TOST) are left out, as their p-values do not test the difference. A statistic written with “<” or “>” is read as a bound, and in a sentence about equal variances an F-test’s two-sided p (twice the one-tailed p) counts as consistent. For more information, see StatCheck.

This module only checks statistical results reported in the running text of the manuscript. It cannot (yet) process statistics reported only in tables.

This module was developed by Daniel Lakens and Lisa DeBruine

Therefore 0% of true instances were missed, and 43% of detections were false positives. See https://osf.io/preprints/psyarxiv/tcxaj_v1/ for more details of the validation.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

This module was developed by Lisa DeBruine and Daniel Lakens

How Non-Significant P Value Check works

This module checks for imprecisely reported p values. If p > .05 is detected, it warns for misinterpretations.

The nonsignificant p-value check searches for regular expressions that match a predefined pattern. The module identifies all p-values in a manuscript and selects those that are not reported to be smaller than or equal to 0.05. It returns all sentences containing non-significant p-values.

In the future, the Metacheck team aims to incorporate a machine learning classifier to only return sentences likely to contain misinterpretations. If you want to help to improve the module, reach out to the Metacheck development team.

How Codebook Check works

This module checks whether the data columns in a repository are documented in a codebook or README. How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

A link to a file-sharing service (Google Drive, Dropbox, OneDrive, Box, WeTransfer, MEGA, iCloud Drive, Baidu Netdisk, SURFdrive; see [file_share_links()]) gets a warning and makes the light yellow: such services are not repositories, as files can be changed or deleted at any time, get no DOI, and the link stops working when the account is closed. The report advises a stable repository such as Zenodo instead. Their files are not read, and summary_table$file_share_n counts the links.

Deposits in archives for sequence and expression data (GEO, the INSDC archives BioProject, SRA, ENA and DDBJ, and ArrayExpress; see [seq_archive_links()]), mostly named by accession number, are read for whose deposit they are. The authors’ own are listed with what they hold ([seq_archive_size()]) and are not downloaded or checked as data and code; summary_table$archive_own_n counts them.

R packages on CRAN ([cran_links()], [cran_info()]) are the paper’s own when a paper author is a package author and the paper presents the package; the paper’s own are listed with their version and not checked (summary_table$cran_own_n). A Handle link (hdl.handle.net/...) that leads to a repository read here is checked as a link to that repository ([handle_links()]).

Listing a repository’s files never requires an API key, but some hosts answer faster or more completely with one: OSF allows 100 requests/hour unauthenticated versus 10,000/day with a token (see [osf_pat()]), and Dryad enforces a strict per-IP daily quota on repeated listing (see cache below). Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Since this module only lists files and never downloads their contents itself, that limitation applies to data_check and code_check (which do download content), not here – see their own documentation.

When a linked OSF page is a registration, its registered_from project (the one it was registered from, which the manuscript itself may never link directly) is also checked: if that project is public its files are listed under its own URL, and if it is closed or otherwise inaccessible the report flags it explicitly, since some registrations only describe their content rather than mirroring it.

Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). On a round of labelled links the rules had not been written from, the three groups were right for 98% of links in the main text (93 of 95) and 90% in reference lists (74 of 82); the labels were made by Claude agents from each link’s evidence, and disputed ones checked against the deposits. Telling this paper’s own deposit from the authors’ earlier one is less certain.

Only the deposits that are this paper’s own are checked. A deposit linked in the text that holds other people’s work (others_data, others_code) or the authors’ earlier work (own_earlier_data, own_earlier_code) is listed in the report, with the reason, but its files are left out of table and kept in table_not_checked: they count toward nothing here (files that do not belong in a repository, naming, READMEs, studies, the traffic light), and code_check, data_check and reproducibility_check, which read table, do not check them either. reproducibility_check still puts the files of theirs that the paper’s code names in the folder the code runs in, as a re-analysis needs the data it re-analyses. When every linked deposit is set aside, the traffic light is “na”. A deposit that is the paper’s own is counted as such when its README, title or description names the paper (its title or DOI).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability).

Provenance, kept so that a TRACE Research Object (TRO) declaration of the run can be written later from a stored result (metacheck #404; the helpers are in R/provenance.R). Only when code was run (execute = TRUE): * run_results$started_at, run_results$ended_at: when each run of a script started and ended (ISO 8601, UTC, milliseconds); NA for a script that was not started. A script run again in a later pass has the times of its last run. A TRO uses them for each trov:TransparentResearchPerformance. * run_results$exit_status: the exit status of the process that ran the script (0 = ended normally); NA when the process did not report one (a time limit, or Docker failing to start the container). * artifacts: one row per file, with stage (deposit: as downloaded from the repository, hashed from the downloaded file; before_run: the run folder just before the first script ran, after metacheck’s own changes, such as rewritten paths and unpacked archives; after_run: only the files the scripts made (status new), changed (changed) or removed (removed), as an unchanged file is the one listed before the run), path (relative to the run folder, as valid UTF-8, a byte of another encoding written as <xx>), size (bytes), sha256, mime_type (by extension, NA when unknown), source (the file’s address in the repository, for deposit). The package libraries metacheck installs in the run folder are left out, as are metacheck’s own files there (a script’s runner, and the statistical output it writes in statistical_output/). Files metacheck itself copied or made between passes (see modifications, output_copied, file_placed) show in after_run too. A TRO uses the rows as trov:ResearchArtifacts and each stage as a trov:ArtifactArrangement. * modifications$sha256_before, modifications$sha256_after: the hash of the changed script as downloaded and as it ran; NA when the script is not at the same path in both (a script made from an R Markdown file). * environment: the system that ran the code (trov:TransparentResearchSystem in a TRO): metacheck_version, started_at, ended_at, host (R version, platform, operating system), sandbox, network_isolated (TRUE only when every Docker run had --network none; the process sandbox does not stop the network), internet, timeout_per_script, total_timeout, python_local (the Python run outside Docker and its version), and docker: runs (for each kind of run, r_run, r_install, python_run, python_install, the image and the docker run arguments, such as --network none, --read-only, --cap-drop ALL, no-new-privileges, the process limit and the memory and processor limits) and images (for each image, its ID and digests from docker image inspect, its creation time and the R and Python versions its environment declares).

run_results$checked says what the run of each script shows about the code, in five groups, so that a script that does not reproduce is kept apart from one the check could not test: ran (it ran to the end); code_error (it did not reproduce: it stopped with an error of the code or the deposit, could not be read, or needs a file the deposit does not hold); dependency (a package or program was not available: a package that could not be installed or was not loaded, a program outside R and Python, a system library, or R crashing in a package’s compiled code); time (it did not finish within the time limit for one script, or was not started because the time for all scripts had run out); and not_checkable (it could not be checked automatically: it needs a person, the internet, a key or another setting of the authors’ computer, one platform such as Google Colab, Windows or OpenSAFELY, more memory than the run allows, a file that was not downloaded, a screen, or a program that runs it, or it is a file of a package of the code that Python runs only as a module of that package). It is NA for files run inside another script, files that are not an analysis, files not read, and a Docker failure. summary_table counts each group (repro_ran_n, repro_code_error_n, repro_dependency_n, repro_time_n, repro_not_checkable_n), and the report’s first sentence gives them. The traffic light reflects the static readiness signals by default; a script in code_error that stopped with an error makes it red, as a script that crashes on its own analysis is a genuine reproduction failure, and a script in one of the other three groups keeps it from being green. Calls that need a screen, which the run does not have (dev.print(), dev.copy2pdf(), dev.copy2eps(), savePlot(), windows(), win.graph(), x11(), quartz(), View()), are replaced before the run by calls that need none, which modifications records as screen_call_replaced. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Sequential priming tasks are a family of methods widely used in psychology. However, implementing sequential priming tasks typically requires custom programming and deployment through third-party platforms. To address these challenges, we developed a free tool that requires no coding skills -the Sequential Priming Builder (SP-Builder: spbuilder.org). This tool uses a graphical user interface that enables researchers to easily build different types of sequential priming tasks, which can be integrated into the widely used online survey platform Qualtrics. We assessed the tool's reliability and timing accuracy in online environments across two studies. In Study 1, we showed that it correctly presented the predefined stimulus sequence and accurately recorded elapsed time. We also evaluated the timing error of stimulus presentation under conditions where typical online participant interactions were simulated. We conducted Study 2 using a preregistered Affect Misattribution Procedure (AMP; N = 92), a widely used sequential priming task. We built the study with SP-Builder, and the results replicated the published findings.

Sequential Priming Builder: A Free, No-Code Tool for Implementing Sequential Priming Paradigms

Sequential Priming (SP) paradigms have been used for decades to study implicit social cognition (Meyer & Schvaneveldt, 1971; Neely, 1977; Wentura & Degner, 2010). It comprises a variety of tasks such as but not limited to lexical decision task (e.g., Banaji & Hardin, 1996; Meyer & Schvaneveldt, 1971; McNamara, 2005), evaluative priming task (EPT, e.g., Fazio et al., 1986 Fazio et al., , 1995;; Klauer & Musch, 2003), and affect misattribution procedure (AMP, E.g., Payne et al., 2005; Mann et al., 2019). Different from self-report measures, SP paradigms assess implicit cognitive processes that are typically efficient, uncontrollable, unintentional, or sometimes unconscious (Bargh, 2014; Chaiken & Trope, 1999; Spruyt et al., 2011). Instead of directly asking people what they think about the target of interest, as with self-report measures, SP paradigms indirectly measure people's attitudes toward different objects, usually by inferring evaluations toward the target of interest from response times or responses to unrelated stimuli.

Unlike self-report measures in which participants may easily construct their answers to align with what they perceive as socially appropriate, SP paradigms bypass the limitations of selfreport measures. For example, individuals may report having no racial bias in a survey simply because such attitudes are socially undesirable (Hofmann et al., 2005). Similarly, when individuals dislike a group, they may suppress these reactions and offer responses they consider reasonable or acceptable in self-report measures (Crandall et al., 2002; van de Mortel, 2008).

Substantive work has documented dissociations between SP responses and self-report measures across domains (e.g., Dovidio et al., 1997; Gawronski & Bodenhausen, 2006; Scinta & Gable, 2007). More importantly, SP measures are predictive of behaviors. Meta-analytic evidence indicates that sequential priming measures are moderately correlated with behavior (r ≈ .28), and this relationship remains significant even after controlling for self-reported attitudes (Cameron et al., 2012). These results showed that SP paradigms are an important family of tasks for understanding human attitudes and behaviors, providing additional insight beyond self-report measures.

Although online studies have become increasingly popular over the years, SP paradigms cannot be easily implemented online because of several features of the paradigm. A common procedural theme in SP paradigms is that stimuli are presented very quickly in a sequence within a trial, which requires high precision in controlling the timing of stimulus presentation. In addition, SP paradigms usually consist of dozens to hundreds of trials. Randomizing the stimuli pool across trials requires advanced randomization functions. Lastly, these paradigms require recording reaction times and/or key-pressing responses. These functions require hardware and software validation before implementation. Given these technical hurdles, to our knowledge, no tool has provided a no-code environment for researchers to carry out SP paradigms. Current Workarounds for Implementing SP Paradigms

For researchers seeking to implement SP paradigms, there are currently three main approaches. First, researchers can write their own code and use third-party hosting services to deploy studies online. Some tools, such as PsychoPy (Peirce, 2007), lower the barrier, but researchers still need to spend time learning to program. For researchers with no programming background, this approach requires substantial learning and is time-consuming. In addition, researchers must pay for hosting services to allow online participants to access their experiments and to store the resulting data (e.g., Pavlovia.org). Second, researchers can use commercial behavioral research platforms, such as Gorilla (Anwyl-Irvine et al., 2020), which provide integrated tools for building and deploying online experiments. Despite the accessibility of powerful tools that enable researchers to build SP tasks much more easily, these services typically charge based on the number of participants. As a result, research costs can substantially increase. Thus, this approach is not budget-friendly for researchers at institutions with limited resources and may exacerbate disparities in research quality due to unequal funding (for research funding inequalities across organizations, see Wu et al., 2018). The third approach is to use free, open-source platforms, such as lab.js (Henninger et al., 2022), which allow researchers to set up tasks similar to the SP paradigm without requiring extensive programming skills. Lab.js is designed as a general-purpose experiment builder. Although it allows users to create a wide range of experimental paradigms, this flexibility comes at the cost of ease of use. The learning curve is naturally steeper for a platform that was intended to support a wide range of paradigms.

To build a specific sequential priming task such as the Affect Misattribution Procedure (AMP), researchers still need a programming background to understand the underlying code for modification and meet randomization needs. As a result, even though lab.js is a highly functional tool for experimental psychologists in general, it is less efficient than tools tailored to a specific set of experimental paradigms.

The issues of heavy code dependence, high cost, and low efficiency of the current options for building the SP tasks pose significant hurdles for researchers who are otherwise interested in using these paradigms, leading many to rely primarily on self-report measures (for limitations of self-report methods, see Coles et al., 2025; Paulhus & Vazire, 2007). To make sequential priming paradigms easy to use, we developed the Sequential Priming Builder (SP-Builder: spbuilder.org).

We drew inspiration from the open-source tool, IATGEN, which researchers developed specifically for the Implicit Association Test (for IATGEN, see Carpenter et al., 2019; for IAT, see Greenwald et al., 1998). Our tool allows researchers with no programming background to easily build their tasks in a web application and integrate them into surveys created in Qualtrics.

Researchers can therefore work in a familiar environment, reduce learning effort, and seamlessly incorporate built-in Qualtrics question formats and functions.

Introduction of the SP-Builder

The Sequential Priming (SP) paradigm comprises a family of tasks (e.g., lexical decision task, evaluative priming task, affect misattribution procedure) that typically involves dozens or hundreds of trials. Within each trial, multiple stimuli are often presented consecutively, including text or images, with each stimulus's presentation precisely timed. After each trial, participants are asked to respond to the target stimulus by pressing the corresponding key on the keyboard.

Depending on the specific type of SP task, participants' key presses and reaction times are recorded for data analysis. As discussed before, sequentially presenting stimuli from different categories with complex randomization, precise control over brief presentation times, and accurate keypress recording cannot be easily achieved using platforms designed solely for survey research or by researchers with no programming experience. SP-Builder helps researchers program these types of experiments and run them in Qualtrics. Table 1 summarizes the type of SP tasks that can be implemented in Qualtrics using SP-Builder. For illustrative purposes, in this paper, we used the AMP, one of the commonly used SP tasks that reflect the core features of SP, to demonstrate the use and test the functionality of SP-Builder. We have included other SP tasks in the tutorial (see https://spbuilder.org/#/user-manual). SP-Builder enables researchers to generate required code through a user-friendly interface that can be directly integrated into Qualtrics. We chose Qualtrics as the platform for integrating experimental code with surveys because it allows the embedding of customized code. This way, researchers with diverse needs can implement complex experiments within the platform. One of the key features of the SP-Builder is the inclusion of built-in code that enables rapid presentation of stimuli from predefined categories and orders with high timing precision.

To minimize the potential impact of participants' internet speed on stimulus presentation accuracy, the platform includes code that ensures all stimuli are fully loaded before the task begins. Because participants may use different devices and browsers, the generated code has been optimized for compatibility across major browsers (i.e., Chrome, Safari), allowing SP paradigms created with SP-Builder to run reliably with satisfactory timing accuracy and precision (see Study 1). All relevant code is available in our publicly accessible materials.

Another key feature of the SP-Builder is the easy implementation of complex randomizations. Researchers can randomize different stimulus types independently. Before each participant begins the experiment, the platform generates the randomized stimulus sequence and then presents the stimuli accordingly. Researchers can also specify how many times each stimulus may appear and randomize the order of stimuli within a candidate pool. For example, in a 20-trial AMP using four faces as one stimulus type, each face may need to appear in five trials while the overall presentation order remains random. On SP-Builder, researchers can upload the four faces, set each face to appear five times, and activate the shuffle function to randomize the order. Researchers can create as many stimulus pools as needed and arrange these pools according to the desired sequence within each trial. Timing Precision of Online SP Tasks

SP tasks place particularly high demands on timing precision. Stimuli in these tasks are typically presented on the millisecond (ms) level. For example, in an SP task examining whether people form implicit impressions of facial trustworthiness, the faces were displayed for 75ms and then immediately followed by unrelated images, after which participants reported their preferences for the unrelated images (Shen & Ferguson, 2021). Therefore, SP tasks require not only that the experiment is presented according to the intended procedure (e.g., the order of stimulus presentation) but also that the presentation duration of each stimulus is sufficiently accurate.

These issues are even more critical and challenging in online SP tasks because they must operate across participants' different browsers, operating systems, and hardware configurations.

Previous evaluations of stimulus presentation timing and response-time recording across different browsers, operating systems, and devices have shown that, although modern browsers and hardware do not yet achieve laboratory-level precision, their timing accuracy is generally sufficient for SP tasks (Anwyl-Irvine et al., 2021). However, different tools (e.g., Gorilla, lab.js) use different underlying timing, scheduling, and rendering mechanisms, which can result in substantial variation in timing accuracy and precision. Thus, the timing precision of newly released tools cannot be assumed to be satisfactory by default. To determine whether the required level of precision for SP tasks has been achieved, it remains essential to use both hardware-and software-based measurement approaches to evaluate stimulus-presentation timing and response-time recording for online tasks generated by SP-Builder.

A Test Case: Affect Misattribution Procedure

Affect Misattribution Procedure (AMP) is one of the commonly used tasks in the family of SP paradigms (Payne et al., 2005). This task contains the typical features needed in SP paradigms: consecutive presentation of stimuli, advanced randomization of stimuli, and extremly short amount of presentation time that need to be highly controlled. Yet, it usually employs less overall trials compared with the Evaluative Priming Taks or the Semantic Priming Task, thus making it a great test case for testing the function and the validity of the SP-Builder.

A typical AMP task consists of dozens of trials. Each trial includes three stimuli. First, a prime picture is presented quickly on the screen, followed by a quickly presented target picture that is neutral in valence, and ending with a noisy pattern image as a mask. Between the prime and the target picture presentation, there is a brief pause of 125 ms during which nothing is displayed on the screen. Both the prime and the target image are presented for a very short duration (75 ms-100 ms). Participants' task was to indicate their evaluation of the target picture by pressing the corresponding keys. Although participants are asked to avoid the prime picture's influence on their target evaluations, the prime still influences how people evaluate the target (Kurdi et al., 2024; Mann et al., 2019). Thus, people's evaluations of the prime can be inferred from their responses toward the target.

Because AMP follows a standardized structure, we use it as a representative example to evaluate and demonstrate the use of SP-Builder for generating SP paradigms. In the following section, we provide a tutorial on how to use SP-Builder to create an AMP task and deploy it on the survey platform Qualtrics. Tutorial for Generating an Affect Misattribution Procedure Using SP-Builder

We followed the AMP task used in Shen & Ferguson, 2021, Study 1, Time 1, and used the same material and design as an example to illustrate SP-Builder. In their study, four trustworthy and four control faces were used as the prime pictures. For each trial, a prime picture, either a trustworthy face or a neutral face, was presented for 75 ms, followed by a blank screen (125 ms) before a target image (abstract paintings) appeared for 100 ms. Then, a noise pattern image replaced the target image until participants responded. The AMP includes 40 trials: 20 trials with trustworthy faces as the prime and the other 20 trials with control faces as the prime. Each control face was randomly selected and served as the prime picture five times. The order of all 40 trials was randomized. After each trial, participants were asked to judge whether the target picture was more or less pleasant than average. They were instructed to press the "K" key on their keyboard if they thought the target picture was more pleasant than average, or to press the "D" key if they thought the target picture was less pleasant than average. Integrating AMP into Qualtrics. After researchers complete the AMP setup in SP-Builder, the tool automatically converts the configuration into JavaScript and HTML that can be used within Qualtrics. Data Recording and Analysis.

Qualtrics's server enables researchers to collect and export data into readable formats for data cleaning and analysis (e.g., Excel files). SP Task Functionality Test

We tested whether tasks generated by SP-Builder operated as intended. Specifically, we compared the designed stimulus selection and presentation sequence with the actual sequence during task execution to assess SP-Builder's functionality. To do so, we used SP-Builder to generate an AMP task replicating Study 1 of Shen and Ferguson (2021), as described in the tutorial above. We embedded it within a Qualtrics survey for testing. The only modification was adding one extra trial to the original 40 trials, resulting in 41 trials total, to meet the requirements of our automated local script.

First, each stimulus added to a task programmed in SP-Builder is automatically assigned a unique identifier. For example, the first face image shown in Figure 3a is assigned a unique code indicating that it is Stimulus 1 in "Stimuli Pool 1." Thus, before launching each AMP task, the predefined code generated a sequence of 41 numerical identifiers specifying the order in which the stimuli would be presented. In the present task, for example, each completion generated a sequence of 41 numbers corresponding to the order in which the face images were presented, and these records were stored in the Qualtrics data file associated with the AMP task.

Second, we used a preprogrammed local script to automatically open the browser, access the Qualtrics link containing the AMP task, and complete the experiment. This script instructed the operating system to automatically complete the same preprogrammed AMP task 50 times in the Chrome browser on a Mac computer. Simultaneously, we recorded all fifty sessions using screen-recording software (QuickTime Player, 60 frames per second [fps]) to determine whether the task operated as designed under realistic conditions. Third, we used a local script to identify the face image presented on each trial from the recordings and converted these presentations into corresponding stimulus identifiers, again producing a sequence of 41 numbers for each task completion. Finally, we compared the sequences recorded in the Qualtrics data with those reconstructed from the screen recordings across all 50 task completions. We found perfect agreement between the two, suggesting that the sequence of stimuli presented during task execution was identical to the sequence recorded in the Qualtrics data.

We examined whether the presentation sequence matched the intended task design. The results confirmed that the presentation order followed the specifications described in the tutorial: one face was randomly selected from the four trustworthy faces and presented 21 times, and these trials were then randomly intermixed with the four neutral faces, each presented five times.

We therefore conclude that the AMP task generated by SP-Builder fully met the task's design requirements and that the tool functioned as intended. The local scripts used to automatically launch and complete the Qualtrics survey containing the AMP task, as well as the scripts used to identify face images from the screen recordings, are available in the open materials.

The Accuracy and Precision of Presentation and Reaction Timing

We confirmed that the AMP task generated by SP-Builder operated exactly as designed when embedded in Qualtrics. Next, we turned to the more critical issue of presentation and reaction time accuracy and precision. Here, accuracy refers to the mean discrepancy between the intended and actual stimulus presentation times (or recorded reaction times), whereas precision refers to the standard deviation of this discrepancy. Smaller mean discrepancies indicate that the programmed presentation or reaction times more closely match the true times, and smaller standard deviations indicate less variability in these discrepancies across trials. Detailed information about the hardware, operating systems, and browser software used in the timingaccuracy assessments in Study 1 is provided in the Supplementary Materials.

Presentation Timing

For SP tasks administered online, delays in presentation timing may arise from four sources. These include (a) scheduling delays, which occur when the browser is processing other tasks and cannot execute a scheduled event immediately; (b) webpage execution time, which refers to the time required for the script to perform computations and modify page content, such as displaying an image or recording a keypress; (c) browser and operating system processing delays, which occur when the browser renders visual content, processes events, handles images, redraws the page, or passes keyboard events to the webpage; (d) hardware-related delays, such as those caused by monitor refresh times and the time required for keyboards to convert physical keypresses into digital signals. Since each stimulus onset and offset is scheduled independently at the beginning of a trial, delays in one display event do not necessarily propagate to subsequent events and therefore do not accumulate frame by frame. More detailed theoretical analyses of presentation-timing errors are provided in the Supplementary Materials.

Methods.

To directly measure stimulus presentation timing errors in SP tasks generated by SP-Builder, we designed an AMP-like task in which each trial contained three stimuli. The first two stimuli were designed to present for 500 ms each, whereas the third stimulus remained on the screen until the participant responded. The next trial began immediately after participants made a response. The three stimuli presented on each trial were, in sequence, a face image, an abstract painting image, and a gray mosaic image. Researchers completed the task in environments commonly used by online study participants. The task was run in the Chrome browser on computers using Windows and macOS. We recorded the entire task simultaneously with a high-speed camera at 240 frames per second. Because of the high-speed camera's memory limitations, it was able to record 17 out of the 41 trials, yielding 17 observations for each stimulus type. We compared the time intervals between the onset and offset of each stimulus captured by the high-speed camera with the intended 500 ms interval and calculated the mean timing error and its standard deviation.

Results.

We observed that the first stimulus (a face image) presented on each trial had a mean timing error of 7.11 ms (SD = 16.97 ms) on Windows and -9.58 ms (SD = 10.57 ms) on macOS. The second stimulus (an abstract painting image) had a mean timing error of -3.92 ms (SD = 18.54 ms) on Windows and -7.50 ms (SD = 5.98 ms) on macOS. Notably, although all tasks were run in Chrome, stimulus presentation was more stable on macOS than on Windows.

The mean timing error on Windows was positive for the first image, indicating a slightly longer presentation duration than intended, but negative for the second image, indicating a slightly shorter presentation duration than intended.

In contrast, for tasks run on macOS, the mean timing errors for both stimuli were negative and similar in magnitude, indicating a small but systematic tendency for stimuli to be presented slightly earlier than intended. Because this deviation was relatively consistent, it may be less problematic for studies that require accurate timing. Timing precision was also better on macOS (SDs = 5.98 -10.57 ms) than on Windows (SDs = 16.97 -18.54 ms), as the timing standard deviations were smaller. Importantly, a stimulus becomes visible only after browser rendering and monitor refresh, with standard 60-Hz displays introducing quantization in approximately 16.7 ms intervals. This means the mean time errors shown here have reflected this monitor's refresh rate.

The timing accuracy and precision of studies generated by SP-Builder are comparable to other widely used online experiment platforms, such as Gorilla.sc (M = 13.44 ms, SD = 15.41 ms), Lab.js (M = 9.79 ms, SD = 4.69 ms), PsychoJS (M = -6.24 ms, SD = 12.99 ms), and jsPsych (M = 26.02 ms, SD = 17.40 ms). The results for the other platforms, including Gorilla.sc, lab.js, PsychoJS, and jsPsych, were taken from Anwyl-Irvine and colleagues' (2020) tests of the accuracy and precision of online experiment platforms. Reaction Timing

To test reaction time accuracy and precision, we used both software-based and hardwarebased approaches. The software-based approach is more flexible and allows comparisons across different operating systems and browsers. In contrast, the hardware-based approach more closely approximates real participant behavior because it incorporates errors introduced by physical devices, such as keyboard input.

Methods: Software-based Approach.

The software-based approach used a local script that automatically completed the AMP task described in the tutorial by sending responses at predetermined times and comparing the intended response times with reaction times calculated from the timestamps recorded in Qualtrics (Reimers & Stewart, 2015). We used the same dataset from the AMP task employed to test SP-Builder's functionality, as it recorded timestamps. Two local devices, a Macintosh computer and a Dell computer, were used to complete the AMP task 50 times under each of the seven operating system and browser combinations (i.e., macOS and Chrome; macOS and Firefox; macOS and Safari; macOS and Edge; Windows and Chrome; Windows and Edge; Windows and Firefox). Because the local automated script had no reference point for determining when to send the keypress response on the first trial, we could not accurately estimate the response time for that trial. Accordingly, we excluded the first trial from the analysis by design. After excluding the first trial, 40 trials per session were retained for analysis, yielding 14,000 observations in total (7 combinations × 50 sessions × 40 usable trials per session). 4The local script generated a response every 525ms, equivalent to pressing the "K" key. As described in the tutorial, each trial of the AMP task allowed responses 300 ms after the onset of the trial (stimulus 1: 75 ms + interval: 125 ms + stimulus 2: 100 ms; See Figure 3b). The embedded JavaScript code records participants' reaction times through timestamps and calculates the interval between when a response becomes available and when it is made. Therefore, the expected reaction time for each trial was 225 ms (525 ms -300 ms). Recorded reaction times below 225 ms indicate that the response was recorded earlier than expected, whereas values above 225 ms indicate that the response was recorded later than expected. The closer the mean across the 40 trials is to 225ms, the better the timing accuracy. The standard deviation reflects timing precision, with smaller values indicating less variability across trials and, therefore, more desirable performance in online experiments. Accordingly, both the proximity of the mean to 225ms and the magnitude of the standard deviation were evaluated.

Results: Software-based Approach.

We reported the descriptive statistics for the software-based reaction time measurements for each operating system and browser combination.

The average timing error ranged from -0.13 ms (SD = 0.83; macOS and Firefox) to 3.43 ms (SD = .28; macOS and Safari).

Methods: Hardware-based Approach.

The hardware-based approach used the reaction time data obtained from the same task used to measure presentation timing. The participant used the same hardware and software setup, with Chrome running on either Windows or macOS.

Specifically, we compared reaction times derived from the high-speed camera recordings with reaction times calculated from the timestamps recorded in Qualtrics, allowing us to estimate the mean timing error and its standard deviation. As in the presentation timing assessment, the task consisted of 17 trials. The participant responded using an external keyboard that illuminated each time a key was pressed. We calculated the participant's true reaction time as the interval between the onset of the third stimulus on each trial, when a response could first be made, and the onset of the keyboard illumination indicating a keypress. These true reaction times were then compared with the reaction times computed from the timestamps recorded by the code in Qualtrics.

Results: Hardware-based Approach. The mean discrepancy between the true reaction times and the recorded reaction times was 27.93 ms (SD = 14.46 ms) on Windows and 38.51 ms (SD = 8.58 ms) on macOS. This error primarily reflects hardware delays, such as the time required for a monitor to refresh its pixels or for a keyboard to convert a physical keypress into a digital signal. We are not aware of comparable tests of reaction time accuracy and precision for other platforms, so these data do not allow us to determine whether SP-Builder records reaction times more accurately than other platforms. Instead, we report these results to inform researchers about the expected discrepancy between recorded and true reaction times when designing studies that rely on precise response timing.

Discussion

Study 1 examined the stimulus presentation sequence, stimulus presentation timing accuracy and precision, and reaction time accuracy and precision of SP tasks generated by SP-Builder. We demonstrated that SP tasks generated by SP-Builder functioned exactly as designed when administered through Qualtrics. In addition, we evaluated timing accuracy and precision using both hardware-based and software-based approaches. Overall, the code SP-Builder generated and executed within Qualtrics provided sufficient timing accuracy and precision. In the software-based assessment of reaction time recording, the smallest error was observed for the macOS and Chrome combination, whereas the largest error occurred for Windows and Chrome.

After completing the AMP task, participants rated both the trustworthy and neutral faces on several 7-point scales, including likability, trustworthiness, bad-good, mean-pleasant, agreeableness, caring, and cruel-kind.

Implicit Evaluations

The design and materials of the AMP task are the same as described in the Tutorial section of this paper. Participants judged the target picture (the abstract paintings). They were asked to press the D key if they thought the target picture was less pleasant than average, and the K key if they thought the target picture was more pleasant than average. Because the task included 40 trials, 40 key press responses were recorded for each participant's evaluations of the faces (the prime pictures) can be inferred from their responses to the target pictures.

Explicit Evaluations

We assessed participants' explicit evaluations of the trustworthy and neutral faces using items "How likable is this person?" (1 = Very unlikable to7 = Very likable) and "Please place this person on the following scales," which included six dimensions (1 = Untrustworthy to7 = Trustworthy;1 = Bad to7 = Good;1 = Mean to7 = Pleasant;1 = Disagreeable to7 = Agreeable;1 = Uncaring to7 = Caring;1 = Cruel to7 = Kind). Along with the questions about the trustworthy-looking person, we presented the trustworthy picture selected for the participant's session. We randomly selected one of the four neutral faces to present along with the questions about the neutral-looking person.

Results

Implicit Evaluations

We calculated the proportion of trials in which participants indicated that the painting was more pleasant than average for trustworthy and neutral faces, respectively. We conducted a pairwise t-test to test whether participants evaluated trustworthy faces more positively than neutral faces. Consistent with previous results, there was a significant effect of facial trustworthiness. Participants implicitly evaluated trustworthy faces (M = 0.57, SD = 0.24) more positively than neutral faces (M = 0.50, SD = 0.21), t(91) = 2.54, p < .05, Cohen's d = 0.27.

Detailed descriptive statistics are reported in Table 2a.

Explicit Evaluations

We computed a composite score for explicit ratings given that the questions showed high reliability (trustworthy faces α = 0.96, neutral faces α = 0.97). As with implicit evaluations, we used a pairwise t-test to examine whether trustworthy faces were evaluated more positively than neutral faces. As predicted, participants evaluated the trustworthy faces (M = 4.74, SD = 1.02) significantly more positively than neutral faces (M = 3.30, SD = 1.19) on the explicit measure, t(94) = 9.88, p < .001, Cohen's d = 1.03. Corresponding descriptive statistics are reported in Table 2b.

Discussion

The results of Study 2 replicated the findings of Shen and Ferguson (2021, Study 1, Part 1), suggesting that using SP-Builder to set up AMP tasks in Qualtrics is a reliable approach for implementing SP paradigms. This approach offers an easy way to quickly build SP tasks, such as the AMP, in Qualtrics and administer them online. It offers advantages not available in alternative approaches, including greater efficiency and more straightforward and secure data management.

General Discussion

We introduced a new tool, the SP-Builder, for building SP tasks. To our knowledge, this is the first user-friendly tool that enables researchers without programming skills to create SP tasks. Researchers can easily incorporate the tasks into Qualtrics for online implementation.

Study 1 assessed the platform's key functions: randomization and presentation, and reaction timing. In Study 2, we replicated previous findings in an experiment that is set up and executed by the SP-Builder.

Because SP paradigms rely on presenting stimuli rapidly and within precise time intervals, it is essential to ensure that the tool can execute accurate timing in browser-based implementations. One difficulty with executing precise timing for online studies is the uncontrollability of participants' internet speed. To minimize this influence on loading and presenting stimuli, our approach preloads all materials before participants proceed to the task. In addition, we conducted two studies to validate the tool's reliability. Study 1 examined the critical issue of functionality and timing precision in using SP-Builder. We confirmed that generating SP tasks with SP-Builder and administering them through Qualtrics is fully feasible and provides sufficient timing accuracy and precision for typical SP tasks. However, different browser and operating system combinations yielded varied accuracy and precision in reaction-time recording.

Timestamp data recorded in the embedded Qualtrics code indicated that timing precision was highest when the experiment ran on Chrome on macOS and relatively lower on Chrome on Windows. In study 2, we used a published AMP study (Shen & Ferguson, 2021) to illustrate how to use the SP-Builder interface to generate tasks that can be embedded in Qualtrics. We also ran this study online and replicated results from prior findings.

Although SP paradigms are a long-standing set of tasks for studying implicit social cognition, no tools make it easy to implement these tasks in online studies. Current approaches require programming skills, add extra cost, or lack the functions needed to create SP tasks. These practical issues prevent researchers from using SP paradigms even when they are interested in doing so. With SP-Builder, however, researchers interested in employing SP tasks can easily set up the intended tasks and run them online, making the study of implicit social cognition more accessible.

Given the strict requirement of SP tasks on stimulus presentation times, we used multiple approaches to test the timing accuracy and precision of SP-Builder-generated tasks through Qualtrics. Specifically, we used both high-speed video recording and local automation scriptgenerated responses to assess reaction-time accuracy and precision. The two approaches produced different estimates, with the local script method showing better timing accuracy and precision than the high-speed video method. This difference was expected because the former captures only software-related delays, whereas the latter reflects both software-and hardwarerelated delays. Hardware delays may arise from factors such as monitor refresh rate, keyboard transmission latency, and measurement error introduced by the high-speed camera. In contrast, software delays arise from task execution, webpage processing, the browser, and the operating system. In principle, software-related timing error should be substantially smaller than the total error observed when hardware delays are also included. Thus, the local automation script helps estimate error attributable primarily to the software system, whereas the high-speed camera recording method more closely reflects the timing error that may occur in real-world online data collection. These estimates therefore reflect not only the performance of SP-Builder but also broader sources of timing error inherent in online experiments. Researchers can use these results to judge whether SP-Builder provides sufficient timing precision for their specific research needs. We also acknowledge that the high-speed video tests were based on a relatively limited sample. Because of resource constraints, camera memory limited the amount of data we could collect, and we could not test a broader range of hardware configurations. Our findings therefore should not be generalized to all hardware systems but may serve as a useful reference for researchers who require precise reaction-time measurement.

In addition, although we tried to test as many browser and operating system combinations as possible, limitations in our equipment and available resources prevented us from evaluating a broader range of browser and operating systems. Consequently, the reported estimates reflect the timing performance of only the specific configurations that we tested. Online participants who complete experiments on their own devices may use myriad hardware and software combinations. The timing accuracy and precision can thus differ from our results. Researchers should determine whether the timing precision associated with their available operating system and browser combinations is sufficient for the requirements of their specific experiment. Future work focused on timing accuracy and precision could either recommend participants use the computer configuration that performed best in our testing or record participants' computer configurations and examine whether results vary by individual builds. Lastly, consistent with our goal of developing this tool, that is, to provide a simple and accessible platform for researchers with no programming background, SP-Builder was designed to be integrated with Qualtrics seamlessly. By integrating with Qualtrics, researchers can use Qualtrics survey functions as they are familiar with, while also avoiding concerns about data recording and storage. All data, including SP tasks set up by SP-Builder and survey data in Qualtrics, are retrievable from one place, making it much easier for researchers to manage their data and follow analyses. We believe making SP-Builder compatible with Qualtrics, one of the most widely used survey platforms in higher education, is the best way to provide researchers with an easy yet powerful solution for running online studies that involve SP tasks. However, we acknowledge that Qualtrics is a paid service and is not available to everyone. For researchers with programming expertise, they may adapt portions of the generated code from SP-Builder for use on other platforms. We also aim to expand compatibility of SP-Builder to additional platforms in future development.

SP-Builder for Other Paradigms

Although we used AMP as an example to illustrate SP-Builder's use and functionality, our application is designed to help researchers quickly create SP paradigms and embed them within Qualtrics surveys. For example, evaluative priming tasks and semantic priming tasks can also be easily set up and implemented on Qualtrics following similar steps illustrated in this work. Moreover, SP-Builder's functionality can be extended to other implicit measures that do not strictly follow a sequential priming structure (see Table 1). For example, the Go/No-Go Association Task (Nosek & Banaji, 2001) can be implemented using this tool. In such tasks, a visual or textual stimulus is presented for a brief period, and participants are required either to press a key (e.g., the spacebar) or to withhold a response, allowing the trial to end automatically before proceeding to the next one. In general, any tasks that involve a serial presentation of stimuli and key-pressing responses can be readily created using SP-Builder. Detailed instructions are provided in the user manual (https://spbuilder.org/#/user-manual) and examples can be found and downloaded in ResearchBox https://researchbox.org/9775 (code: TBMUHI).

Conclusions

Overall, the results of these two studies support the feasibility of using SP-Builder to create sequential priming paradigms that can be embedded and run within Qualtrics surveys.

Given its ease of use and efficiency, we believe our tool has the potential to increase the adoption of sequential priming paradigms in research by providing an alternative measurement approach when self-report is insufficient to capture target psychological constructs, and by offering implicit evidence alongside self-report to enhance the validity and reliability of psychological research findings.
