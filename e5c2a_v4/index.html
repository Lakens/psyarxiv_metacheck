The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. How StatCheck works

The Statcheck module runs Statcheck. Statcheck searches for regular expressions that match a predefined pattern, and identifies APA reported statistical tests. More information on the package can be found at https://github.com/cran/statcheck. The module only returns Statcheck results for t-tests and F-tests, as these are the only tests which have been validated, see https://osf.io/preprints/psyarxiv/tcxaj_v1/.

Statcheck was developed by Michèle Nuijten and Sascha Epskamp.

Statcheck considers p = 0.000 an error, as you should report p < 0.001. Furthermore, p < 0.03 is an error if the p-value was 0.031, and one should simply report exact p-values (p = 0.031). When the sentence of a test says it is one-sided (“one-tailed”, “one-sided” or “directional”), a p-value that fits a one-sided test counts as consistent (statcheck’s OneTailedTxt setting; #695). When the paper says anywhere that its tests are one-sided, a p-value that fits a one-sided test in either direction counts as consistent too: half the two-sided p, or 1 minus that half for an effect against the predicted direction. Equivalence tests (TOST) are left out, as their p-values do not test the difference. A statistic written with “<” or “>” is read as a bound, and in a sentence about equal variances an F-test’s two-sided p (twice the one-tailed p) counts as consistent. For more information, see StatCheck.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.), reported as exactly zero (e.g., p = .000), or impossible (below 0 or above 1, e.g., p = -.22).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold”, “legend” or “named”).

A p-value with the name of a correction or a test after the p (“pFWE < .05”, “padj < 0.05”, “p Wilcoxon = .02”) is flagged only when a test statistic comes before it in its clause (“t(37) = 7.17, p FWE < .05”). Without one it is mostly the rule that decided what was significant (“genes with padj < 0.05 were selected”); such a p-value is “named” in not_a_test. Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

A p-value below 0 or above 1 is impossible; it is listed apart and not also as imprecise. Often the statistic before it, or its minus sign, was copied into it (“t(134) = -2.32, p = -.13”, “Z = 3.091, P = 3.091”). A value above 1 is listed only after a test statistic in its clause: without one, a “P” above 1 was nearly always another quantity (a proportion, pH, a group’s mean, a model parameter). A number in scientific notation whose power of ten was lost when the PDF was read (“p = 2.4 x 10 -9” read as 2.4) is not listed. A “p” that is the subscript of another symbol (“r p = .64”, “²p = .02” for partial eta squared, “Δp = .33”), or a quantity with a unit, a logarithm or a ratio (“P = 2.9 µm”, “-log10 P = 7.5”, “Ca/P = 1.67”), is not read as a p-value at all (see extract_p_values()). Each p-value has its own row, also when the same one is written twice in a sentence.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Repository Check works

This module retrieves information from repositories.

The Repository Check module lists files on the OSF, GitHub, ResearchBox, DSpace (PsychArchives and other legacy- and DSpace 7-based installations), Zenodo, Dataverse, Figshare, Dryad, ReShare, 4TU.ResearchData, Mendeley Data, DataONE (Arctic Data Center, KNB, and other member nodes), and LDbase based on links in the manuscript.

A link to a file-sharing service (Google Drive, Dropbox, OneDrive, Box, WeTransfer, MEGA, iCloud Drive, Baidu Netdisk, SURFdrive; see [file_share_links()]) gets a warning and makes the light yellow: such services are not repositories, as files can be changed or deleted at any time, get no DOI, and the link stops working when the account is closed. The report advises a stable repository such as Zenodo instead. Their files are not read, and summary_table$file_share_n counts the links.

Deposits in archives for sequence and expression data (GEO, the INSDC archives BioProject, SRA, ENA and DDBJ, and ArrayExpress; see [seq_archive_links()]), mostly named by accession number, are read for whose deposit they are. The authors’ own are listed with what they hold ([seq_archive_size()]) and are not downloaded or checked as data and code; summary_table$archive_own_n counts them.

R packages on CRAN ([cran_links()], [cran_info()]) are the paper’s own when a paper author is a package author and the paper presents the package; the paper’s own are listed with their version and not checked (summary_table$cran_own_n). A Handle link (hdl.handle.net/...) that leads to a repository read here is checked as a link to that repository ([handle_links()]).

Listing a repository’s files never requires an API key, but some hosts answer faster or more completely with one: OSF allows 100 requests/hour unauthenticated versus 10,000/day with a token (see [osf_pat()]), and Dryad enforces a strict per-IP daily quota on repeated listing (see cache below). Dryad is a special case beyond rate limits: listing a Dryad dataset’s files works without a key, but actually downloading file CONTENTS from Dryad fails with HTTP 401 unless a key is set, even for a fully public dataset (see [dryad_pat()] or [dryad_auth()]). Since this module only lists files and never downloads their contents itself, that limitation applies to data_check and code_check (which do download content), not here – see their own documentation.

When a linked OSF page is a registration, its registered_from project (the one it was registered from, which the manuscript itself may never link directly) is also checked: if that project is public its files are listed under its own URL, and if it is closed or otherwise inaccessible the report flags it explicitly, since some registrations only describe their content rather than mirroring it.

Whose deposit is each link? The ownership table gives, for every repository linked in the text and (with references = TRUE) every deposit cited in the reference list, one of six labels: own_this (made by the authors for this paper), own_earlier_data or own_earlier_code (the authors’ own, from earlier work), others_data or others_code (made by other people, reused here), or not_data (a publication such as a preprint, not a deposit), with ownership_group (“own”, “others”, “not_data”) and the reason. It is decided without a language model, from the sentence or reference that cites the link, the paper’s authors (names, ORCID iDs, affiliations), and what the deposit’s own record and files say (who made it, what it names, when, whether it is a software package; for an OSF project cited only in the reference list, its record alone). On a round of labelled links the rules had not been written from, the three groups were right for 98% of links in the main text (93 of 95) and 90% in reference lists (74 of 82); the labels were made by Claude agents from each link’s evidence, and disputed ones checked against the deposits. Telling this paper’s own deposit from the authors’ earlier one is less certain.

Only the deposits that are this paper’s own are checked. A deposit linked in the text that holds other people’s work (others_data, others_code) or the authors’ earlier work (own_earlier_data, own_earlier_code) is listed in the report, with the reason, but its files are left out of table and kept in table_not_checked: they count toward nothing here (files that do not belong in a repository, naming, READMEs, studies, the traffic light), and code_check, data_check and reproducibility_check, which read table, do not check them either. reproducibility_check still puts the files of theirs that the paper’s code names in the folder the code runs in, as a re-analysis needs the data it re-analyses. When every linked deposit is set aside, the traffic light is “na”. A deposit that is the paper’s own is counted as such when its README, title or description names the paper (its title or DOI).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability).

Provenance, kept so that a TRACE Research Object (TRO) declaration of the run can be written later from a stored result (metacheck #404; the helpers are in R/provenance.R). Only when code was run (execute = TRUE): * run_results$started_at, run_results$ended_at: when each run of a script started and ended (ISO 8601, UTC, milliseconds); NA for a script that was not started. A script run again in a later pass has the times of its last run. A TRO uses them for each trov:TransparentResearchPerformance. * run_results$exit_status: the exit status of the process that ran the script (0 = ended normally); NA when the process did not report one (a time limit, or Docker failing to start the container). * artifacts: one row per file, with stage (deposit: as downloaded from the repository, hashed from the downloaded file; before_run: the run folder just before the first script ran, after metacheck’s own changes, such as rewritten paths and unpacked archives; after_run: only the files the scripts made (status new), changed (changed) or removed (removed), as an unchanged file is the one listed before the run), path (relative to the run folder, as valid UTF-8, a byte of another encoding written as <xx>), size (bytes), sha256, mime_type (by extension, NA when unknown), source (the file’s address in the repository, for deposit). The package libraries metacheck installs in the run folder are left out, as are metacheck’s own files there (a script’s runner, and the statistical output it writes in statistical_output/). Files metacheck itself copied or made between passes (see modifications, output_copied, file_placed) show in after_run too. A TRO uses the rows as trov:ResearchArtifacts and each stage as a trov:ArtifactArrangement. * modifications$sha256_before, modifications$sha256_after: the hash of the changed script as downloaded and as it ran; NA when the script is not at the same path in both (a script made from an R Markdown file). * environment: the system that ran the code (trov:TransparentResearchSystem in a TRO): metacheck_version, started_at, ended_at, host (R version, platform, operating system), sandbox, network_isolated (TRUE only when every Docker run had --network none; the process sandbox does not stop the network), internet, timeout_per_script, total_timeout, python_local (the Python run outside Docker and its version), and docker: runs (for each kind of run, r_run, r_install, python_run, python_install, the image and the docker run arguments, such as --network none, --read-only, --cap-drop ALL, no-new-privileges, the process limit and the memory and processor limits) and images (for each image, its ID and digests from docker image inspect, its creation time and the R and Python versions its environment declares).

run_results$checked says what the run of each script shows about the code, in five groups, so that a script that does not reproduce is kept apart from one the check could not test: ran (it ran to the end); code_error (it did not reproduce: it stopped with an error of the code or the deposit, could not be read, or needs a file the deposit does not hold); dependency (a package or program was not available: a package that could not be installed or was not loaded, a program outside R and Python, a system library, or R crashing in a package’s compiled code); time (it did not finish within the time limit for one script, or was not started because the time for all scripts had run out); and not_checkable (it could not be checked automatically: it needs a person, the internet, a key or another setting of the authors’ computer, one platform such as Google Colab, Windows or OpenSAFELY, more memory than the run allows, a file that was not downloaded, a screen, or a program that runs it, or it is a file of a package of the code that Python runs only as a module of that package). It is NA for files run inside another script, files that are not an analysis, files not read, and a Docker failure. summary_table counts each group (repro_ran_n, repro_code_error_n, repro_dependency_n, repro_time_n, repro_not_checkable_n), and the report’s first sentence gives them. The traffic light reflects the static readiness signals by default; a script in code_error that stopped with an error makes it red, as a script that crashes on its own analysis is a genuine reproduction failure, and a script in one of the other three groups keeps it from being green. Calls that need a screen, which the run does not have (dev.print(), dev.copy2pdf(), dev.copy2eps(), savePlot(), windows(), win.graph(), x11(), quartz(), View()), are replaced before the run by calls that need none, which modifications records as screen_call_replaced. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Longitudinal learner corpus research (LCR) has grown substantially in recent years, resulting in richness and variety in study designs, analyses, and findings. Yet its design, measurement, and analysis practices have not been systematically assessed. To address this gap, this review synthesizes 120 longitudinal learner corpus studies published between 1996 and 2025, identified through systematic database searches and supplementary searching of the Learner Corpus Bibliography. Many studies collected data at two to four time points; written and same-genre data predominated, and task counterbalancing was rare. Additionally, analytical sophistication rose markedly over time, with mixed-effects models increasingly used in recent studies. We identify five priorities for the field: aligning observation schedules with developmental trajectories, transparently reporting time-based parameters, designing tasks with clear rationale, matching analytic tools to learner-language data, and adopting longitudinal statistical models more widely.

These priorities offer a roadmap for studies yielding cumulative, comparable evidence about L2 development over time.

1. Introduction

Learner corpus research (LCR) has substantially advanced understanding of second language (L2) learners' language production, particularly how language use varies across learner characteristics, proficiency levels, and tasks (McEnery et al., 2019; Paquot & Plonsky, 2017). LCR and second language acquisition (SLA) research are closely connected, but they are not equivalent (see Le Bruyn & Paquot, 2021): LCR refers to research based on the systematic collection and analysis of "continuous and contextualized language use by L2 learners" (Callies & Paquot, 2015, p. 1), while SLA provides a broader theoretical context for many of the developmental questions studied in LCR (Granger, 2021; Myles, 2015). LCR encompasses not only corpora as data sources but also annotation tools and analytic measures developed for analysis of learner language (Biber, 1988; Biber et al., 2011), including concordancers, syntactic analyzers, and computational indices (e.g., AntConc, Anthony, 2023; Coh-Metrix, McNamara et al., 2014). Following Granger (2009), we define an L2 corpus broadly as contextualized learner language elicited through open-ended production tasks that allow learners to make lexical and grammatical choices. This definition is consistent with Myles's (2015) SLA-oriented view, which also recognizes classroom-based learner production, such as essays, as legitimate corpus material when systematically collected and analyzed. Within this framework, LCR has generated extensive evidence regarding L2 development across a wide range of linguistic domains and learning contexts (e.g., Alexopoulou et al., 2017; Lei et al., 2023; Lu, 2023; Vandeweerd et al., 2023). In the current study, we use LCR as the primary term for the body of research reviewed here, given (a) our study sampling methods and (b) our focus on the longitudinal design of corpus research involving L2 learners.

To date, much of the progress in LCR has been driven by cross-sectional analyses of largescale learner corpora, such as the EF-Cambridge Open Language Database (EFCAMDAT; Geertzen et al., 2014) and the International Corpus Network of Asian Learners of English (ICNALE; Ishikawa, 2013). Although such analyses provide valuable evidence regarding differences between learner groups and proficiency levels, they approximate developmental change by comparing language use at a single point in time between different individuals (i.e., between-subjects design). For example, claims about routes of development are based on comparisons of different learners at different proficiency levels. In contrast, longitudinal corpus research involves repeated observation of the same learners over multiple time points (i.e., withinsubjects design), allowing researchers to examine developmental trajectories, intra-individual variability, and transitions in learner language over time (e.g., Ployhart & Vandenberg, 2010; Tracy-Ventura & Huensch, 2018; Verspoor et al., 2020). Importantly, study duration alone does not define longitudinal designs (Ployhart & MacKenzie, 2014). Duration defines the developmental window over which change is observed, but the number of observation points constrains the kinds of developmental patterns that can be examined. The relationship between two observations will always be linear and therefore cannot show the shape of a developmental trajectory (e.g., bell-shaped, J-shaped, cyclical). To this end, at least three observations are needed to begin distinguishing different patterns of change (Barkaoui, 2014; Ployhart & Vandenberg, 2010). This repeated-observation design is what distinguishes longitudinal designs from crosssectional approaches that infer development by comparing different learner groups at a single point in time (e.g., Kuiken & Vedder, 2019; Wisniewski, 2020). Given these features of longitudinal research, their use in LCR introduces additional methodological considerations not as present in cross-sectional studies as well as challenges related to sampling across time, task comparability, participant retention, and repeated-measures analysis (Lu, 2023; Ortega & Iberri-Shea, 2005; Tracy-Ventura & Huensch, 2018).

Because longitudinal LCR has grown substantially (e.g., through projects like the Languages and Social Networks Abroad Project (LANGSNAP; Mitchell et al., 2017)), a systematic evaluation of its research practices is now necessary. Even though Paquot and Plonsky's (2017) systematic review of LCR included some longitudinal learner corpus studies, the methodological challenges specific to longitudinal corpus design were not the focus of their investigation and were thus not examined in detail. Issues such as observation duration, sampling frequency and interval, task comparability across waves, and the use of statistical methods appropriate for repeated observations require distinct methodological scrutiny (Barkaoui, 2014; Ortega & Iberri-Shea, 2005). Without such evaluation, not only do longitudinal studies in LCR risk producing findings that are difficult to interpret, compare, or replicate, but wide variations in study designs create challenges for disciplinary growth and theory-building. This concern is heightened by the rapid proliferation of longitudinal corpus designs, which are particularly valuable for building knowledge about L2 development.

To address this situation, this paper systematically examines longitudinal LCR studies conducted between 1996 and 2025, a period corresponding to the modern development of LCR.

By mapping current methodological practices and gaps, the study aims to inform future longitudinal LCR and support the development of more rigorous design, measurement, analysis, and reporting practices.

2. Literature review

>Literature review

2.1 Longitudinal LCR studies and L2 development

Over the past three decades, extensive efforts to bridge SLA and LCR have highlighted the invaluable role of learner corpora in advancing SLA theory and the importance of SLA-informed approaches in shaping corpus design and analysis (Granger, 2021; Lu, 2023; Lu & Wang, 2026; Myles, 2015). While the synergies between LCR and SLA have been widely acknowledged and discussed, further integration is needed (Granger, 2021; Le Bruyn & Paquot, 2021; McEnery et al., 2019). From an SLA perspective, one of the limitations of LCR has been the predominantly crosssectional nature of learner corpora (Paquot, 2024; Tracy-Ventura & Huensch, 2018). Crosssectional corpora are most useful for documenting between-group differences, typically at a single point in time, and identifying variables that predict production quality and learner groups (e.g., Kyle & Crossley, 2017). In contrast, longitudinal corpora are widely recognized as better suited for investigating many of the field's central questions, including how individual L2 development changes over time, what key transitional stages exist in L2 development, and what commonalities exist among groups with similar learning curves (Myles, 2008; Nagle, 2021; Ortega & Byrnes, 2009 , Ortega & Iberri-Shea, 2005).

In response to this need, early efforts compiled and analyzed longitudinal L2 corpora through small-scale, in-depth case study designs. For example, Vyatkina (2012) tracked both group-level development and the individual trajectories of two L2 German learners over four consecutive semesters of college instruction. By collecting 19 writing samples from each learner at dense intervals, approximately every three weeks, the study enabled fine-grained analysis of writing complexity over time. The findings showed both overall increases and substantial individual variability in syntactic and lexical complexity. Similarly, Chan et al. (2015) analyzed 100 written and 100 oral texts produced by two L1-Chinese identical twins over an eight-month period, with data collected two to three times per week. Their study revealed transitional stages in syntactic development, illustrating how developmental reorganization and individual variability emerge over time. In both examples, these LCR studies are longitudinal not because of the study duration alone but because of repeated observations of the same individuals over time. Taken together, these examples show how longitudinal corpora can provide critical insights into developmental variability, individual trajectories, and transitional phases by making visible developmental patterns that would have been difficult to capture through cross-sectional comparisons alone.

In addition to tracking development, longitudinal L2 corpora provide a basis for empirically testing SLA hypotheses. For instance, Crossley et al. (2019) investigated absolute frequency effects, a key construct in usage-based theories, in L2 lexical development by analyzing monthly oral production data collected at four time points from 50 L2 English learners over four months.

Their findings showed that learners produced increasingly frequent vocabulary over time, but frequency-based measures alone were limited in predicting lexical development. These results suggest that factors such as salience, contingency, and recency play additional roles in shaping learners' lexical growth. Similarly, Verspoor et al. (2020) applied a Complex Dynamic Systems Theory perspective to syntactic and lexical development in 22 Dutch learners. By analyzing 23 narrative writing samples from each participant over a seven-month period, they were able to trace variability in usage over time and capture dynamic interactions among linguistic subsystems that differed across developmental phases and between individuals. Crucially, both studies illustrate insights that cross-sectional data could not have yielded such as how the predictive role of frequency shifted across time points within the same learners and the dynamic reorganization of linguistic subsystems across developmental phases (see also McManus et al., 2021; Murakami, 2016).

Despite repeated claims that longitudinal corpora are needed to provide valuable insights into the nature and routes of L2 development, they remain limited in the field, as shown in Paquot and Plonsky's (2017) review of 378 LCR studies published between 1991 and 2015. This review showed that longitudinal designs accounted for only 13% of the sample (k = 49). They noted, however, that longitudinal designs were becoming more common toward the end of their review period, increasing from 3% in 1991-1999 to 16% in 2008-2015. As a result, they explicitly recommended the construction of corpora with more frequent and extended observation points. In the present study, we build on this work by investigating trends specifically within longitudinal LCR, including developments from the past decade since their review as well as the design and implementation of these studies. While their review provides important guidance for LCR more broadly, it is crucial to recognize that longitudinal learner corpus research presents a distinct set of methodological challenges not typically encountered in cross-sectional designs.

2.2 Challenges for longitudinal learner corpus research

No prior review has specifically focused on longitudinal LCR. However, methodological and narrative reviews of longitudinal SLA research and LCR have noted several relevant challenges (e.g., Barkaoui, 2014; Myles, 2008; Ortega & Iberri-Shea, 2005; Paquot & Plonsky, 2017). These reviews converge on three recurring issues: temporal design, measurement validity, and the statistical analysis of change.

First, temporal design requires particular attention in longitudinal LCR research. Study duration, observation frequency, and trade-offs among timeline length, sample size, and feasibility must be carefully considered. In LCR studies that draw data from naturally occurring or elicited language production, time itself becomes a structuring property of the study (Lu, 2023; Ortega & Iberri-Shea, 2005). That is, conclusions about observed change depend partly on when observations are made and how much time elapses between them. If observation intervals are not informed by prior research about the pace and timing of L2 development, key developmental patterns may be missed or overestimated. At the same time, overly dense data collection schedules can add substantial transcription and annotation burden with little additional information, creating a trade-off between temporal resolution and feasibility. It is therefore important that longitudinal corpus designs, including study duration and data collection intervals, be informed by prior research before data collection begins.

Second, measurement validity can be especially complex in corpus research, where repeated language samples are often task-based and open-ended, such as essay prompts used to collect L2 writing samples (e.g., Yoon & Polio, 2017). Using identical tasks across time can lead to practice effects (Skiba et al., 2009), whereas varying tasks can introduce construct-irrelevant variability due to differences in topic or genre (Lu, 2023). To mitigate these risks, some studies have implemented task or topic counterbalancing (e.g., Crossley & Kim, 2022; Mazgutova & Kormos, 2015; Yoon & Polio, 2017). Collectively, maintaining construct stability across repeated observations remains a central methodological challenge in longitudinal LCR.

Third, analyzing developmental change in learner corpora often necessitates advanced statistical tools. Longitudinal corpus data may often be unbalanced across learners and time points, and linguistic variables may display non-linear and individual-specific trajectories (Larsen-Freeman, 2006; Murakami, 2016). Traditional statistical methods such as ANOVA are often insufficient for capturing this complexity because they tend to aggregate across learners and reduce variability across samples (Barkaoui, 2014). Recent reviews and empirical studies therefore recommend techniques such as mixed-effects modeling, growth curve analysis, and time-series methods, which are better suited to modeling intra-and inter-individual variation over time (Barkaoui, 2014; Linck & Cunnings, 2015; Verspoor et al., 2020). Such variation is precisely the kind of developmental evidence that longitudinal designs are intended to document and explain.

In sum, although these three challenges arise in longitudinal research generally, corpusbased studies face them in distinctive forms: each observation must yield language samples of sufficient quantity and comparability, task design constraints are inseparable from measurement validity because the data are learner language, and statistical modeling must accommodate automatically extracted linguistic indices whose reliability itself requires validation (Kim & Lu, 2024; Skiba et al., 2009). However, no prior work has examined how longitudinal LCR studies have responded to these methodological demands. This absence makes it difficult for researchers to assess current practices, identify recurring design problems, and/or build on existing methodological innovations. Accordingly, we examine how these challenges have been addressed to date in order to strengthen the methodological basis for future longitudinal studies in LCR.

3. The present study

Previous recommendations based on reviews of LCR studies, L2 research, and longitudinal designs each address relevant aspects, but none has specifically reviewed longitudinal LCR studies.

Yet this body of research has expanded substantially in recent years (Tracy-Ventura & Paquot, 2020), and its methodological practices have not been systematically examined. This gap is important because longitudinal learner corpus studies are methodologically distinct: they analyze repeated, open-ended language production over time that introduces temporal, corpus-construction, and analytic challenges that differ from those typically encountered in cross-sectional learner corpus studies or in longitudinal research outside corpus linguistics. Accordingly, the current study provides a focused synthesis of the design, measurement, corpus-building, and analysis practices used in longitudinal learner corpus studies. To this end, the current study addresses the following research questions: RQ1. What participant, contextual, and temporal sampling practices characterize longitudinal LCR? RQ2. How are learner-language data elicited and operationalized in longitudinal LCR, particularly with respect to mode, task design, and target linguistic features?

RQ3. What corpus-analysis procedures, language-analysis tools, and statistical methods are used to analyze longitudinal LCR?

4. Method

>Method

4.1 Study retrieval and identification

Guided by methodological practices for research synthesis in applied linguistics (e.g., Park et al., 2022; Plonsky et al., 2023; Riazi et al., 2018) and Plonsky's (2014) recommendations for delimiting studies across substantive, locational, and temporal dimensions, we defined the eligibility criteria for this methodological synthesis in advance of the literature search. We included empirical studies that (a) explicitly identified their dataset as an L2/learner corpus and conformed to established definitions of learner corpora, namely collections of connected, open-ended learner texts that allow lexical and grammatical choice (Granger, 2009; McEnery et al., 2019; Myles, 2015); (b) employed corpus-linguistic methods, such as annotation and analysis of learner language (Lu, 2023); (c) implemented a longitudinal design, operationalized as at least two waves of data collection enabling within-participant comparison; and (d) were published in English. No minimum study duration or participant threshold was imposed; both were treated as methodological characteristics rather than eligibility criteria. The review was restricted to Englishlanguage publications for feasibility and to ensure consistent application of the screening and coding procedures. We excluded conceptual and/or methodological articles, including narrative reviews; corpus-compilation reports without data analysis; studies based on metalinguistic tasks that did not elicit connected discourse, such as acceptability judgments or vocabulary tests; and phonology/phonetics studies based on read-aloud data, which did not constitute semi-spontaneous learner production. We also excluded studies that collected longitudinal data but analyzed them as a single aggregate, that is, without time-based contrasts or within-participant analysis.

Following the Preferred Reporting Items for Systematic Reviews and Meta-Analyses (PRISMA) 2020 guidance (Page et al., 2021), we searched the following databases between July 23 and July 28, 2025: ERIC, LLBA, PsycINFO, ProQuest, ScienceDirect, JSTOR, SAGE Journals Online, Wiley Online Library, Web of Science, and Scopus. Search strings combined corpusrelated, L2-related, and longitudinal keywords, including ("corpus" OR "corpora") AND ("second language" OR "L2") AND ("longitudinal" OR "over time"), with syntax tailored to each database.

For interdisciplinary platforms, such as Scopus, we restricted searches to Linguistics, Psychology, Education, and Social Sciences. The complete database-specific search strings are provided in Appendix A.

The review covered studies published between January 1996 and July 2025. We selected 1996 as the starting point because it marked an early consolidation phase in modern LCR, particularly following the introduction of Contrastive Interlanguage Analysis (Granger, 1996).

Foundational developments such as Learner English on Computer (Granger, 1998) further contributed to the expansion of LCR in the following decades.

6. Discussion

Viewed against longstanding calls for longitudinal evidence that can capture L2 development as it unfolds, the 120 studies reviewed here show that longitudinal LCR has expanded substantially. Studies published between 2020 and 2025 already outnumbered those published across the decade before. This growth, however, coexists with continuing limitations in research design. Across the three domains examined, temporal design remains shaped largely by institutional schedules and sparse observation frequencies, mode and feature coverage have become more diverse than in earlier reviews, and analysis practices have grown more sophisticated.

At the same time, the temporal and sampling foundations needed to support strong developmental inference appear to have changed more slowly.

Regarding temporal design (RQ1), studies were distributed relatively evenly across observation windows: the most common windows were 6-12 months (26.7%, n = 32) and 13-24 months (25.8%), followed by 1-5 months (20.0%), and 25+ months (15.8%). This spread suggests that the field accommodates a range of timelines rather than converging on a single norm, which is appropriate given that different developmental questions require different observation windows.

However, few studies articulated a developmental rationale for the observation period, interval, or frequency they adopted. Where reasoning was provided, it more often reflected institutional schedules or practical constraints, such as data availability or program duration, than principled expectations about when the targeted linguistic feature would change. Several studies explicitly anchored their observation windows to a semester or school year (e.g., Crosthwaite & Jiang, 2017; Duan & Shi, 2024), suggesting that academic calendars, rather than developmental timelines, frequently determined the temporal scope of data collection.

This pattern is understandable. Corpus compilation and annotation is labor-intensive, and academic terms offer bounded, administratively manageable periods for data collection. However, this alignment also has methodological consequences. Ortega and Iberri-Shea (2005) cautioned that longitudinal studies should be guided by developmental logic rather than convenience alone, and the present synthesis suggests that this concern remains only partly addressed. When research timelines are shaped more by institutional schedules than by developmental considerations, the kinds of questions that can be asked are limited. A semester-aligned design can be appropriate for some research questions, but its adequacy depends on whether the targeted linguistic feature is expected to show detectable change within that time frame.

Observation frequency raises a related concern. Two-to-four-point designs were the most common observation pattern (46.7%), and two time points were the single most common design (21.7%). As Barkaoui (2014) notes, two-point designs can show whether change occurred, but they cannot show the shape of that change. They cannot distinguish, for example, between linear, curvilinear, accelerating, decelerating, or variable developmental patterns. At least three measurement occasions are generally needed to begin distinguishing different patterns of change, with additional observations providing stronger support for modeling more complex or nonlinear trajectories (Ployhart & Vandenberg, 2010). The prevalence of designs with relatively few observation points therefore places practical limits on what can be inferred about development, regardless of the statistical tools applied.

Sample size further limits the kinds of analyses that many studies can support. More than half of the studies (58.3%) included 30 or fewer participants. This matters not only for generalizability but also for modeling individual developmental trajectories. Multilevel models and latent growth curve models, which are among the frameworks best suited to modeling change over time, typically require larger samples than repeated-measures ANOVA designs (Barkaoui, 2014). The demographic distribution of the sample also points to a narrow empirical base. Adult learners (72.5%) and post-secondary settings (50.0%) dominated the corpus, whereas children (6.7%) and adolescents (17.5%) were much less represented. Longitudinal LCR is therefore heavily weighted toward adult learners and post-secondary settings. As a result, questions about child and adolescent L2 development, age-related developmental patterns, and comparisons with L1 developmental trajectories remain comparatively underexplored.

It is also worth noting that the cross-tabulation in Table 4 suggests that researchers often calibrate these two design dimensions: short intervals were most common in 1-5-month studies, whereas long intervals were most common in studies spanning at least 13 months. Although variable and unreported schedules limit this comparison, the pattern may be read as a positive sign: researchers working within shorter observation windows appear, in many cases, to compensate for limited duration by collecting data more frequently. That said, the appropriateness of any durationinterval combination, again, depends on the developmental phenomenon under study (Ortega & Iberri-Shea, 2005). Shorter studies do not automatically require dense sampling, and longer studies do not necessarily justify sparse sampling; both decisions should be linked to expectations about the pace, variability, and detectability of change in the targeted feature.

Reporting of temporal design parameters remains an important issue. Study duration was unreported in 4.2% of studies, while observation interval (19.2%) and observation frequency (15.0%) were more often unreported. Paquot and Plonsky (2017) identified incomplete reporting as a broader weakness in LCR, and the present findings suggest that temporal information is a particular blind spot in longitudinal learner corpus studies. This information is not incidental. Time is what makes a study longitudinal. Without clear reporting of how long data collection lasted, how often learners were observed, and how far apart observations were, readers cannot evaluate whether the design was appropriate for the developmental question, replicate the study, or compare findings across studies.

Turning to measurement practices (RQ2), the field's reliance on written data and English has narrowed, although it has not disappeared. In the present sample, 53.3% of studies used written data, 42.5% used spoken data, and 4.2% combined spoken and written data. This distribution is less skewed than the 74/29/3 distribution reported by Paquot and Plonsky (2017) for LCR more broadly. English coverage also declined from 88% in their review to 66.7% in the present sample.

These patterns suggest broader coverage, but not a simple linear move toward diversification.

Spoken data dominated the pre-2010 longitudinal subset, written and spoken data were closer to parity in 2010-2019, and written data became more common in 2020-2025. This shift in mode may partly reflect the historical relationship between longitudinal SLA research and LCR.

Longitudinal SLA has a long tradition of intensive, often naturalistic spoken-data collection (Mitchell et al., 2008), whereas LCR has developed strongly around systematically compiled written learner corpora (McEnery et al., 2019). More recent work has also benefited from the expansion of written learner corpora and automated text-analysis tools such as Coh-Metrix, TAALES, and L2SCA. These tools have made written-data studies easier to scale, whereas spoken corpora still require substantial time for recording, transcription, cleaning, and anonymization.

However, mode should not be treated as a direct marker of disciplinary orientation: both spoken and written learner corpora can address questions central to L2 development. English also remains the dominant target language, so broader coverage of spoken data and non-English target languages is still needed before the field can make stronger claims about general patterns of L2 development.

Task design was another area where methodological choices were uneven. Repeating the same task across waves can introduce practice effects, whereas changing topics or genres across waves can introduce construct-irrelevant variance if the tasks are not comparable (Kim & Lu, 2024; Skiba et al., 2009). In the present sample, same-genre or same-text-type designs were most common (45.8%), followed by variable-task designs (40.0%), same-task repetition (11.7%), and counterbalancing (1.7%). Same-genre or same-text-type designs may reflect an attempt to balance two competing concerns: avoiding practice effects from repeating the exact same task while maintaining comparability across waves. However, Figure 6 suggests that task design is also closely tied to task type. Formal writing tasks were usually same-genre designs, informal conversation consistently used variable-task designs, and picture/story description tasks consistently used same-task designs. In other words, task design often appears to follow from the elicitation format itself rather than being treated as a separate methodological decision.

This dependency has important implications. If task design is shaped largely by elicitation format, then researchers need to be especially clear about how construct stability is maintained across waves. This is particularly important when tasks vary over time. In such cases, changes in learner performance may reflect development, but they may also reflect differences in topic, genre, prompt difficulty, or discourse demands. Counterbalancing comparable topics or tasks across participants is one way to address these issues and has been recommended in longitudinal corpus research (Crossley & Kim, 2022; Mazgutova & Kormos, 2015; Yoon & Polio, 2017). Yet only two studies in the present sample reported a counterbalanced design, even though more than onethird of studies rotated tasks across waves. The implication is not simply that studies should use more varied tasks. Rather, task selection itself should be treated as a measurement decision. When tasks change across waves, researchers should explain how the tasks remain comparable and, where feasible, use counterbalancing to reduce prompt-order and content effects.

The distribution of target linguistic features also suggests a broadening of scope relative to earlier LCR. Paquot and Plonsky (2017) found that lexis accounted for 65% of target features in LCR. In the present sample, lexis remained the most frequently investigated feature, but it accounted for a smaller proportion of studies (30.0%). Other features were also represented, including syntax (16.7%), morphosyntax (10.8%), and pragmatics (10.0%). This comparison should be interpreted cautiously because the coding schemes are not identical. Paquot and Plonsky's "grammar" category was broader than the current study's "morphosyntax" category and likely included phenomena coded separately here as syntax, morphosyntax, and syntax/discourse.

When studies in the multiple-feature category are additionally counted under each domain they examined, lexis accounts for 40.8% of the sample, and syntax, morphosyntax, and syntax/discourse combined account for 46.7%, similar to Paquot and Plonsky's 46% grammar figure. Overall, the findings suggest that longitudinal LCR extends beyond a primarily lexical focus, although lexis remains central. The growing attention to morphosyntax and pragmatics may reflect increasing interest in more complex dimensions of interlanguage development and the expanding capacity of corpus-analytic tools to examine them.

Concerning analysis practices (RQ3), three patterns stand out. First, software-assisted analysis is now common, appearing in 79.2% of studies. Second, inferential statistics were reported in roughly three-quarters of studies (78.3%). Third, the statistical methods used in longitudinal LCR have become more sophisticated over time. Using Goodwin and Goodwin's (1985) threelevel framework, as applied in applied linguistics by Khany and Tazik (2019), the present review found that advanced statistical procedures became more common in 2020-2025 than in 2010-2019. This trend is consistent with recommendations to use methods that can model repeated observations, handle unbalanced data, and capture both between-and within-learner variability (Barkaoui, 2014).

The clearest example of this shift is the rise of mixed-effects models. In Paquot and Plonsky's (2017) review of LCR, mixed-effects modeling was included under "other" methods and was reported in less than 2% of the studies. In the present longitudinal subset, linear mixedeffects models appeared in 21.3% of studies that used inferential statistics. Although nonparametric or categorical tests (37.2%), correlation (36.2%), and ANOVA/ANCOVA (24.5%) were more common, mixed-effects models were more frequent than non-mixed regression (16.0%).

This change likely reflects the fit between mixed-effects models and the structure of longitudinal learner-corpus data. Such data are often nested, unbalanced, and incomplete, with repeated observations clustered within learners, unequal numbers of waves, irregular spacing, and missing data. These features are difficult to accommodate within ANOVA-based designs but align more naturally with random-effects modeling approaches (Barkaoui, 2014), implemented in packages such as lme4 and glmmTMB.

At the same time, statistical tools have advanced faster than some of the designs needed to support them. Many studies still include too few observation points to model developmental trajectories directly. The most common observation frequency was two points (21.7%), and studies with two to four points accounted for 46.7% of the sample. Prior methodological work suggests that estimating the rate and shape of change requires at least three measurement occasions, with four or more preferable for non-linear forms (Preacher et al., 2008; Singer & Willett, 2003).

As a result, many studies can only compare performance across time points rather than model time as a developmental process. This is not necessarily a weakness of statistical choice. In many cases, it reflects the limits of what the design can support. However, it restricts what can be learned about the rate, shape, and variability of development, which are central concerns in usage-based and dynamic systems approaches (Crossley et al., 2019; Verspoor et al., 2020).

Methods capable of capturing non-linear change and individual variability, such as generalized additive models, random-slope mixed models, and moving-window correlations, appear in the reviewed studies but remain uncommon. When used in dense-sampling designs, these methods can reveal both shared developmental trends and learner-specific pathways (Chan et al., 2015; Vyatkina, 2012). Their limited use therefore points to an underused opportunity for theory building.

Taken together, the findings suggest that the field does not simply need more advanced statistical methods. That shift is already underway. The more important need is to align analytic methods with designs that can support developmental inference. In practice, this should involve collecting data at three or more time points where feasible, reporting individual data-collection schedules, and selecting analytic methods suited to the number and spacing of observations.

Dense-sampling designs may be particularly valuable when the goal is to examine how L2 development unfolds, rather than simply whether change occurs. At the same time, these recommendations should be understood in light of the substantial labor required to build longitudinal learner corpora. Longer and denser designs require sustained participant access, repeated data collection, transcription or cleaning, annotation, and, in many cases, tool validation.

Progress in longitudinal LCR will therefore depend not only on methodological refinement, but also on institutional and funding support that makes sustained, well-documented data collection feasible.

7. Conclusion

This review has both limitations and strengths. On the limitations side, the synthesis necessarily relies on what authors chose to report, so coding in some categories was constrained where reporting was incomplete; to mitigate this, we applied a pre-specified protocol and doublecoded a subset of studies to monitor reliability. Even so, ambiguity in author terminology may have introduced some residual misclassification. Database searches were complemented by snowballing and a supplementary cross-check of the Learner Corpus Bibliography to capture early LCR publications, but some published in less readily indexed venues may still have been missed.

The restriction to English-language publications may have excluded relevant research published in other languages and may therefore underrepresent methodological practices in some research contexts. Full-text screening intercoder reliability was assessed retrospectively on a subset of 28 records and yielded κ = .774, suggesting that screening decisions were applied consistently, though the retrospective design limits the extent to which this estimate reflects prospective replicability.

Finally, the review describes and maps methodological practices rather than meta-analyzing effect sizes, so claims about what caused practices to change over time are beyond its scope.

On the strengths side, the review focuses specifically on longitudinal LCR, which was treated as a subset of broader reviews discussed above. It covers studies published between 1996 and 2025, a period that spans both the early development of modern longitudinal LCR and its recent expansion, allowing trends to be tracked across nearly three decades rather than a single snapshot. The coding scheme captures a broad range of sampling and design, measurement, and analysis features under a transparent protocol, providing a level of methodological granularity that supports concrete recommendations rather than general calls for improvement. Together, these features position the review as a methodological resource that both maps current practice and identifies actionable next steps for the field.

In sum, longitudinal LCR is increasingly equipped with the analytic tools and statistical methods needed to investigate the timing and shape of L2 development. Moving from feasible to stronger developmental designs, however, will require observation schedules aligned with developmental trajectories, more deliberate task design, closer attention to the suitability of analytic tools for learner-language data, and wider use of longitudinal statistical models, alongside broader linguistic and learner coverage. For journal editors and reviewers, persistent gaps in temporal reporting suggest that requiring authors to specify observation duration, interval, and frequency would meaningfully improve the evaluability, replicability, and comparability of the literature. These steps would place the field in a stronger position to build cumulative and developmentally interpretable evidence on how second language ability changes over time.
