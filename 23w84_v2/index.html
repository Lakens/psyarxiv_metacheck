Meta-scientific research has shown nonsignificant p values are commonly misinterpreted. It is incorrect to infer that there is ‘no effect’, ‘no difference’, or that groups are ‘the same’ after p > 0.05.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.) or reported as exactly zero (e.g., p = .000).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold” or “legend”). Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

How Replication Check works

This module checks references and warns for citations of original studies for which replication or reproduction studies exist in the FLoRA database.

The Replication Check module compares the reference list against studies in the FLoRA (FORRT Library of Replication Attempts) database based on the DOI. If a study in the database is found, a reminder is provided that a replication or reproduction of the original study exists, and should be cited. No reminder is given when the paper already cites that replication or reproduction (matched by its DOI).

The module requires that the reference has a DOI: the DOI in the paper’s reference list, or one looked up with add_bib_match() before the module runs (see ref_table()). References without a DOI are not checked.

It is possible the original study was cited for other reasons than the empirical claim tested, or that the replication/reproduction in the FLoRA database is for only one of the studies in the paper, and not the study the authors discuss.

The database can be manually updated with the FLoRA_update() function. For more information, see https://forrt.org/FLoRA/.

Abstract

Measures of actual pro-environmental behaviour are increasingly in environmental psychology due to their increased ecological validity over self-report measures. Here we introduce a new such measure, the One-Shot Download Task (OSD), a brief online behavioural measure in which participants choose between incurring personal costs (completing a tedious task) or environmental costs (downloading unnecessary files associated with carbon emissions). Two studies were conducted (Study 1: N = 104; Study 2: N = 96) that assessed the OSD's criterion validity by examining associations with measures of eco-anxiety, environmentally minded consumer behaviour and environmental attitudes, while Study 2 also tested whether social influence in the form of exposure to "watching eyes" stimuli increased pro-environmental choices in the task. It was found that OSD scores positively correlated with environmentally minded consumer behaviour and the Preservation dimension of environmental attitudes, but not with eco-anxiety or Utilization attitudes. Furthermore, participants exposed to watching eyes selected significantly more environmentally friendly options (higher scores on the OSD).

These findings provide initial evidence for the validity of the OSD as a measure of actual pro-environmental behaviour, demonstrating expected relationships with established environmental constructs and sensitivity to social influence. Given its simplicity, low cost, and accessibility, the OSD offers a practical addition to the growing range of behavioural measures available to environmental psychological researchers, although further validation is warranted.

1. Introduction

There has been an increased emphasis recently on the need to be able to accurately and objectively measure actual pro-environmental behavior (Lange, 2022; Lange et al., 2023). Such measures can offer more validity than self-report measures and can therefore be of greater predictive value. This can benefit more applied investigations of pro-environmental behavior and/or successful real-world interventions.

As a result of this, several such measures have recently been introduced. These include the Greater Goods Game (Klein et al., 2017), the Pro-Environmental Behavior task (Lange et al., 2018), the Tree task (Essl et al., 2025) the Work for Environmental Protection task (Lange & Dewitte, 2021), the Carbon Emissions task (S. Berger & Wyss, 2021) and the Behavioral Allocation task (Lange & Rieger, 2025). All of these have been shown to be valid measures of pro-environmental behavior and subsequently used in further research.

However, as noted by Farrelly et al., (2024), these measures have practical limitations in terms of either requiring specialist equipment and/or requiring additional financial costs (such as payments to charities or participants [based on their decisions in the tasks] or for carbon offsetting). In response, Farrelly et al., (2024) created the Email Conservation Task (ECT), an online measure of actual pro-environmental behavior that required participants to incur either the personal costs of taking time to complete a menial task or the environmental costs of receiving an unnecessary email which result in the release of CO 2 emissions.

As with other online measures of prosocial behaviour that rely on time (rather than finances) as the cost incurred (e.g., Farmer & Farrelly, 2023) it requires no further financial costs, making it a more accessible, cheap and inclusive measure of pro-environmental behavior for future research (Farrelly et al., 2024).

The current studies test a novel follow-up measure to the ECT which investigates individuals' proenvironmental behavior in a single choice rather than across a series of choices, as the ECT does. Here we introduce the One-Shot Download Task (OSD), which is based on the potential environmental costs of another online activity, the downloading of large files (Farrelly, 2025). In this task, participants will, as with the ECT, be required to choose to either incur the personal costs of time spent on a menial task (a number discrimination task as is used in the ECT) or the environmental costs of downloading unnecessary files.

Unlike the ECT, the OSD features a single choice an individual needs to make with varying levels of personal costs (number of trials of the number discriminations) and environmental costs (size of file to download). Individuals therefore who choose options with greater personal cost and lesser environmental costs in the OSD will display higher levels of pro-environmental behavior. As a result, it is hoped that the OSD will also be beneficial in terms of accessibility and inclusivity that the ECT provides but will also now offer a quicker and more immediate measure of pro-environmental behavior, in a single question.

In order to test the validity of the OSD, two separate studies were conducted. Firstly, to assess its criterion validity Study 1 explored how scores on the OSD related to other existing self-report measures of environmentalism, that of eco-anxiety (Hogg et al., 2021) and environmental consumer behavior (Sudbury-Riley & Kohlbacher, 2016), whereas Study 2 explored environmental attitudes (Milfont & Duckitt, 2010). This is similar to other measures of pro-environmental behavior that have been compared to a range of measures of pro-environmentalism (Delcourt et al., 2024). Furthermore, Study 2 explored how social influence may affect people's behavior on the OSD.

Previous research has shown how this can increase pro-environmental behavior (Berger, 2019; Farrelly & Bhogal, 2021; Griskevicius et al., 2010), highlighting how the visibility of such behaviors allow individuals to signal their environmentalism (O' Keefe et al., 2026). The effects of social influence however are mixed, and other research has found no evidence of its effect (Brick & Sherman, 2021; Lange et al., 2020; Lazarevic et al., 2025; Palomo-Vélez et al., 2021), so Study 2 used a different method to measure the effects of being observed on pro-environmental behavior, that of "watching eyes" (e.g., Bateson et al., 2006). This phenomenon, whereby the presence of eyes can affect prosocial behavior generally, has been shown in a recent meta-analysis to have a potentially significant effect (Wang et al., 2024), so Study 2 will examine if this also extends to pro-environmental behavior.

The present studies therefore will test the following hypotheses: Hypothesis 1. Participants' scores on the OSD will positively correlate with scores on the Hogg Eco-Anxiety Scale (Hogg et al., 2021), the Ethically Minded Consumer Behaviour scale (Sudbury-Riley & Kohlbacher, 2016), and the Environmental Attitudes Inventory-24 (Milfont & Duckitt, 2010). Study materials and datasets from both studies are available in the Open Science Framework project page here: https://osf.io/n48zm/overview?view_only=290afc50485e4175a775121930439730.

2. Methods

>Methods

2.1 Participants

Power analyses were conducted using JAMOVI to determine the required sample size for each study.

For study 1, a medium effect size (r = .3) (as with previous studies [Farrelly et al., 2024; Lange et al., 2018]), and 80% power with a corrected alpha level of .025 (due to controlling for multiple comparisons) required 102 participants. In total there were 104 (mean age = 21.3 years, SD = 4.6, 87% female) participants in Study 1. For study 2, the analysis to test Hypothesis 2 was used as this would require the larger sample. To detect a medium effect size with 80% power and an alpha level of .05 required a total sample size of 128 participants. Due to practical constraints of participant availability this was however not achieved and instead there were 96 (mean age = 21.4 years, SD = 6.2, 94% female) participants in Study 2. A total of 10 participants' data was removed across both studies due to not passing the inclusion criteria for the attention check questions (a minimum of two correct answers). All participants were undergraduate psychology students who completed the study in return for course credits. This study was approved by the authors' university's institutional ethics committee.

2.2 Materials

2.2.1 The Environmental Attitudes Inventory-24 (EAI-24) (Milfont & Duckitt, 2010).

Environmental attitudes are measured across twelve subscales, with two questions in the EAI-24 for each subscale. These combine to measure to higher order factors, Preservation (i.e., preserving nature and other species from human interference) and Utilization (i.e., using nature for human objectives). Participants' scores for these two were used, and Cronbach's alpha of .74 for Preservation and .73 for Utilization were found in the present study.

2.2.2 The Hogg Eco-Anxiety Scale (HEAS) (Hogg et al., 2021).

This 13 item self-report measure assesses the frequency of thoughts of climate related worry over the past two weeks using a 4-point Likert scale, with higher overall scores indicating greater levels of eco-anxiety. A Cronbach's alpha score of .9 was found for HEAS in this study.

2.2.3 The Ethically Minded Consumer Behaviour scale (EMCB) (Sudbury-Riley & Kohlbacher, 2016

). This 10 item self-report questionnaire assesses sustainable purchasing behaviours (e.g., buying ecofriendly products). Responses were provided on a 5-point Likert scale, with higher scores indicating greater engagement in sustainable consumerism. A Cronbach's alpha score of .89 was found for EMCB in this study.

2.2.4 Watching Eyes Stimuli.

The London Face Database (DeBruine & Jones, 2017) was used to source images, and three male and three female images were randomly selected to be used. Once selected, the eye section only of the faces were cropped to be used as stimuli. These were then placed alongside university logos in a small banner (see figure 1 below). For conditions with no eyes stimuli, the banner was included with just the university logos. These banners were included in Study 2 only, at the top the page when the task is introduced and also when participants chose their option.

2.2.5

The One-Shot Download task 1 . This task was created using JsPsych (de Leeuw, 2015) and hosted online on local servers. In this task participants were presented with different options, and they had to choose one option to progress in the study. Each option included a number of number discrimination trials (odd/even) as was used in the ECT (Farrelly et al., 2024) and the downloading of a dummy file. The different options were as follows: 1.

Complete 64 trials and no file download.

2. Complete 48 trials and download a 100MB file.

3. Complete 32 trials and download a 200MB file. 4. Complete 16 trials and download a 300MB file.

5. Complete no trials and download a 400MB file.

Participants were also informed of the approximate CO 2 emissions of each file downloaded (e.g., 100Mb is approximately 6 grams of CO 2 ). They will be informed that the download will begin automatically and informed that these are just dummy files with no content or risks involved 2.

2.3 Procedure

After the information sheet and providing informed consent, participants were asked to provide demographic information (gender, age). Following this, they completed either the HEAS and EMCB (Study 1) or the EAI-24 (Study 2). 1 The full materials of this task are available in the Open Science Framework project page here: https://osf.io/n48zm/overview?view_only=290afc50485e4175a775121930439730 2 These dummy files are synthetic placeholder files created specifically for this study. They are generated programmatically using Python and contain no text, images, audio, or any functional data. Instead, they are filled with non-informative binary data (null bytes), making them completely inert. Their only purpose is to simulate the experience of downloading a file of a specified size. The files pose no privacy, confidentiality, or security risks, and contain no content of any kind.

On the next page, participants were introduced to the OSD. It was explained to them that they will have a number of different options that they will need to choose from that will possibly include downloading a file and completing a number of boring and trivial number discrimination tasks. They are also informed here that these are dummy files and also that once they have completed the number of trials they select in their option, the study will be completed.

The next page informed participants of the environmental costs of downloading unnecessary files and asked them to read details about this before answering questions about this content on subsequent pages. Like Farrelly et al., (2024), participants were introduced to the environmental issues involved, including a link to a recent news articlefoot_0 and an approximate indication of the CO 2 emissions related to downloading files ("downloading an album [approximately 100MB] from the internet can lead to carbon emissions of up to 6g of CO 2 ."). Participants were finally asked to consider avoiding downloading unnecessary files in the future to help in the fight against climate change. On the following pages, participants were asked three true/false questions about the information they had just read (the CO2 emissions from a 100MB download, the equivalence of this to other energy use, reducing downloading files to tackle climate change). If participants chose the incorrect option, there would be a brief reminder of the correct information provided on the screen. These questions also acted as attention checks, as mentioned in section 2.1.

Following this, participants were then presented with the task and told of the five options they could select from (see Figure 1 below). Once they made the selection, the download of the dummy file began automatically while they were redirected to the subsequent page to complete their chosen amount of number discrimination trials (0 -64). Once these were completed, participants were debriefed and thanked.

3. Results

>Results

3.1 Hypothesis 1

Pearson's correlations were conducted and sequential Bonferroni adjustments used to calculate an initial alpha level of 0.025 by dividing the standard alpha level (0.05) by the number of tests (2) in each study to control for multiple comparisons. It was found that scores on the OSC task significantly correlated with scores on the EMCB (r = .28, p = .004, 95% CI [0.45, 0.09]) and the Preservation factor of the EAI-24 (r = .28, p = .006, 95% CI [0.45, 0.08]), but not with either the HEAS (r = .01, p = .95, 95% CI [0.2, 0-.19]) or the Utilization factor of the EAI-24 (r = .11, p = .3, 95% CI [0.30, -0.09]).

4. Discussion

Firstly, there was partial support for Hypothesis 1, as it was found that participants' scores on the OSD were significantly and positively correlated with their EMCB score and also the preservation factor of their EAI-24 score. This is consistent with the links between self-report measures and other pro-environmental behavior tasks, as are the size of these relationships that were found (Delcourt et al., 2024). No such relationship however was found with the HEAS, which is perhaps not surprising, as a recent meta-analysis found a great variation in possible links between eco-anxiety and pro-environmental behavior (Davì et al., 2026) and was particularly weak for individual behavior (such as was the case with the OSD). Furthermore the lack of a positive correlation between the OSD and the Utilization factor of the EAI-24 was also perhaps to be expected, as the latter's more anthropocentric focus has previously been found to not relate to environmental behaviors (Milfont & Duckitt, 2006). Overall these findings provide further support for the multidimensionality of pro-environmental behavior (Lange, 2024).

Contrastingly, there was full support for Hypothesis 2 as the presence of watching eyes led to increased pro-environmental behaviour in the OSD task. This suggests that individuals responded to this cue of being observed to signal their environmental behavior (O' Keefe et al., 2026), thereby providing strong support for the validity of the OSD. Caution should be exercised however in interpreting this finding, because of the lower power of Study 2 due to the reduced sample size (see section 2.1). Despite the relatively large effect size observed here, a reliability power analysis suggests that it had only 70% power to detect such an effect. This coupled with the mixed overall findings for the watching eyes effect (Wang et al., 2024) suggests that further investigation of the possible role of social influence on the OSD is warranted. The existing findings are however promising, and further research that examines social influences on pro-environmental behaviours such as signalling in mating contexts (e.g., (Farmer & Farrelly, 2023; Farrelly & Bhogal, 2021; Palomo-Vélez et al., 2021) can make use of the OSD task in the future.

As well as reduced power in Study 2, other limitations include the relatively low environmental costs of the OSD (file downloads) as was similarly the case with unnecessary emails in the ECT. Also, similarly to the ECT, the OSD is however intended to act as an experimental means to measure pro-environmental behavior and as such utilises environmental costs that are of similar size to those of other similar measures (Lange et al., 2018; Farrelly et al., 2024). Future research can therefore investigate how varying the personal and environmental costs in the OSD task alters individuals' choices.

Overall the findings presented here suggest the OSD task can make a valuable contribution to the existing canon of experimental measures of actual pro-environmental behavior and further address the necessity for more diversity and ability we have to measure pro-environmentalism (Lange et al., 2023; Nielsen et al., 2024). Due to its low financial costs and simplicity of its single item measure, the OSD can act as a valuable experimental method that is more accessible to a wider range of environmental psychology researchers than other existing measures. As a potential starting point for new research paradigms, the OSD can provide the preliminary answers as to how we can alter people's behavior when it comes to climate change, laying the foundations for further real-world applications and interventions.
